# State and the tree

The Riverpod providers, the seams the agent layer attaches to, and the tree's model, builder and view.

## 7. State: providers

| Provider | Type | Responsibility |
| `projectProvider` | `AsyncNotifier<FilmProject>` | Loads the sample at start — as a writable session copy on every platform, whatever development mode says (`ProjectController.sampleOpensAsSessionCopy`, items 9 and 10: following the mode, whose switch is in the preferences every build shares, opened it read-only whenever another build had turned the mode off) — with the library from `libraryProvider` (which it watches: choosing another library folder re-reads the open project). `openDirectory(path)`, `openSample` replace the page (loading spinner) and, on success, put the folder at the top of the recent list; each ends a closed state. `close` writes every open draft (`OpenDrafts.settleOpen`) and sets `projectClosedProvider`, logged as `project.closed`. `createProject(...)` writes the folder (or a session-only project where there is no disk) and opens it, answering a `CreatedProject`: the new `pj` stem and the stem of the scene the script starts with, which the caller opens. `addChild`, `removeChild` and `moveChild` change the script's lists (§9.2): an add writes the entity first and the parent second, a move the destination first and the origin second, and both answer — `AddedChild.notListed`, `MovedChild.notRemoved` — what kept the second write from landing, rather than throwing it, since the first has landed and the caller has to say so, and a move also answers `MovedChild.alreadyListed` where the destination named the folder or scene already, which the caller says too; **`mediaStoreProvider`** (`filmopen_state/media_provider.dart`) answers the store of the open project's media root, or why there is none — `unsupported` for a locator type no source is registered for, `unavailable` for a folder the loader could not open. It is derived from `projectProvider`, so every load, every re-read and every change of viewer answers a store of that project's own. Null while no project is open.

**A change made below the forms** (`ProjectController.patchEntity`) is the one door such a change goes through: a job's reference or text, and the script's own lists, which are `_changeChildren` on top of it. `patchEntity(projectKey, stem, change, {viewer, holds, key, against, reseed, changedMeanwhile})`.

- **The film by its key, and the person with it.** `projectKey` is the film the change was asked for *in* (§5.15's `projectKeyOf`) and must be the film open now, or nothing is written and the answer is `ProjectNotOpenException` — a job begun in one film and ending after another was opened waits rather than writing into the stranger on screen, and so does one that ends after ***Close project***, whose index stays in memory (`projectClosedProvider`) although the page shows no film. **The key and never the index**, since every load, every `forViewer` and every re-read builds another index of the one film (§6.11's `RunBinding`). The `viewer` is passed in for the same reason and is the door's **own** write: a handle typed while a job ran would otherwise write half its work as somebody else, and the script's two writes could go out as two people. A change routed **through a form's draft** is written by that form's saver, as the person at the keyboard, so the bound viewer does not reach it; the two differ only while a form is open on the file and the handle changes under it, and the worst that then happens is a refusal, never a write as the wrong author, since identity comes from the filename (§13).
- **Through the draft a form has open on that file**, when one has — one writer per file, so nothing half typed is lost, no box is reset and no autosave is refused as stale afterwards (`OpenDraft.apply`, §9.3) — else as a save of the file as it was read. The draft keeps its identity and is changed *in place*: every key the change dropped goes, every key it left or added stays, which is the general form of the one key `children` used to move. With `reseed` the boxes whose seeded value the change altered take their new text, the road a copy-left takes (§9.3) — which a **text** written from below needs, nothing else re-seeding a box before the write lands 700 ms later, and which a reference does not, having no box.
- **`against` is the file as the caller checked it**, for a caller that checked one: a move re-reads the folder between its two writes, and a second write made against the copy looked up afresh would take an outside change for its own starting point instead of refusing it as stale (§13). Without it the file is looked up in the index as it is now, and a stem the index does not name is `EntityChangedMeanwhileException`.
- **One change at a time per file.** Two jobs ending together would each write against the text it read, and the second would be refused as stale although no person had touched the file; they take their turn instead, and the turn is kept by the **last** change to join the queue, so one asked for while another is still running waits too. Files are independent of one another.
- **Success is read from the file re-read**, never from the write's own answer: `holds` says whether what was asked for is in the file, by a re-read that was *taken* (one overtaken by another leaves the index from before the write, so it is made again, three times at most). A change that **changes nothing is not written** — a job replayed after a crash whose reference is already in the file has nothing left to do — **and is read back all the same**, because what it was compared against may have been the draft, and a draft holds what is typed and not yet written: settling it writes what the person typed, and the re-read then says whether the file really holds what was asked for. That road settles **this file's draft only**, and waits for the writes no form waits for any more (`OpenDrafts.settleDetached`, §7.1), one of which may be landing on this very file. The answer is what refused the change, else null; `changedMeanwhile` names the refusal for a write that landed without the file holding it, which is how the script keeps `ChildrenChangedMeanwhileException` and its own sentence. **Every refusal the door answers rather than throws is logged** as `entity.patchRefused` with the stem and one word of the door's own (`otherFilm`, `filmClosed`, `noFile`, `notHeld`, `write`) and never a message, a thrown one being logged as `entity.patchFailed` where it happened.

**Adding to and removing from the script** (`ProjectController.addChild`, `removeChild`). `addChild(type:, tag:, name:, kind:, parentStem:)` writes the viewer's first version of a new folder or scene and lists it at the end of the `children` of the file `parentStem` — the project file the script is read from, or a version of a folder — **the entity first, the parent second**, as a fork writes its file before its pick. Before anything is written: a taken short name is refused (`EntityExistsException`, the dialog's own sentence); every open draft is settled, and one that cannot be written refuses the add; the parent is looked up **by its stem in the index as it then is** — never the entity a caller held, whose text a settle may have replaced — and must be one whose list the viewer may change (`PageAccess.childrenLock`, below), with a `children` that is a list or absent and a change that changes something; and the parent's save is tried dry (`ProjectWriter.checkSave`) **against what the write will start from** — the file on disk, or, where a form still has something to write on that file, the document that form would write (`OpenDraft.pending`, §7.1), so that a keystroke that landed after the settle refuses the add before the new file is made rather than after it. One viewer, read once, writes both files. The parent's change then goes through **`patchEntity`** (above), which is where all of that now lives: the draft a form has open on the file written through rather than beside, the entity that was checked handed in as `against` rather than looked up again, one change at a time per file, and success read from the file re-read. What the script adds is its own: the list read back out of the re-read for `holds`, `children` named as the key that changed, and `ChildrenChangedMeanwhileException` as `changedMeanwhile`, so that a write that landed without the list holding it still reads as the script's own sentence rather than the general door's. The answer is an `AddedChild`: the new stem and, where the parent could not be written after it, what refused that (`notListed`) — an answer and not an exception, because the new file exists, under *Not in the script*, written as the handle the dialog set, which an exception's way out would put back. `removeChild(parentStem:, entry:, occurrence:)` takes the entry out as it is written, the `occurrence`-th of equal ones, under the same checks and the same routing, deletes nothing, and throws what refused the write. Log: `entity.created` as before, `folder.childAdded`, `folder.childAddFailed`, `folder.childRemoved`, each with the parent's and the child's stems and never a name. **`folder.childrenWriteFailed` is gone** with the `catch` that raised it: a write that fails inside the door is `entity.patchFailed` and a refusal the door answers is `entity.patchRefused`, both with the stem alone, and the script's own `folder.childAddFailed` still says which parent and which child.

**`PageAccess.childrenLock`** (`page_access.dart`) says why a version's `children` may not be changed — `noHandle`, `readOnly`, `notYours` — and `canEditChildren` that it may: the form's own answer (`editable`) with its reason, since the parent is written as the viewer's own version or not at all (in development mode, anybody's). The tree's menu and the pages read it, so a disabled *Add folder…* says the same thing everywhere: *Set your username in Settings first*, *This project is read-only here*, *Fork this folder first…* or *Fork the project file first…*. The structure is content: a director has no special path.

**`WriteProblemText`** (`write_problem_text.dart`), the sentence for a refused or failed write wherever it is shown, moved here from `filmopen_forms` with the dialog's move to the tree: the state is below every package that writes and above the store, whose refusals these are. **`writeProblemCode`** stands beside it for a layer that carries codes and not sentences — a job's `stateCode` in the journal (§6.12), which a widget turns into a sentence of its own — and does not replace it, because a code cannot say *whose* file it was: `notYourVersion` names the author and `identityChangedMessage` the key, and the script's own operations still hand the refusal itself to a page. A record outlives the run that made it, and a sentence in a journal would be in whatever language the person had chosen that day. The codes are `filmopen_jobs`' vocabulary and only grow; a refusal this does not know is `writeFailed` rather than a developer's text, which never travels.

### 7.1 The seams for the agent layer — `filmopen_state`

What the product carries is five seams with no-op or silent defaults, in `filmopen_state` so that every package above it can reach them and no product package ever imports the agent's own packages (`filmopen_automation`, `filmopen_mcp`):

- **`AutomationHost`** (`automation_host.dart`) — what an agent may ask: `state`, `navigate`, `setTab`, `tap(identifier)`, `setField(stem, key, text)`, `screenshot`, `semantics`, `logTail`, the doors of the project menu and Settings (`openProject(path)`, `setViewer(handle)`, `setLocale(code)`, `setTheme(mode)`). The recorder's ops are not on this interface: `Recording` (`record_start`, `record_stop`, `record_state`) is `filmopen_automation`'s optional host interface beside `SemanticsTaps` and `AppExit`, which `DriverAutomationHost` implements (§4.3, §6.8). `AutomationHost.current` is the `NoOpAutomationHost` (`isAvailable` false, every answer "not available") unless an entrypoint outside `lib/` — the agent build, `test_driver/agent_main.dart` — `install`s another before `main` runs; `main` builds the `ProviderContainer` and hands it to whichever host is installed (`attach`). `AutomationHost.rootKey` is the `RepaintBoundary` that `app.dart` wraps the page in, so a host can take a screenshot from the render tree on every platform; `AutomationHost.windowKey` is the one `app.dart` builds above the navigator (`MaterialApp.builder`), the whole view with every route, dialog and menu, which the issue recorder shoots and which `page_shot` now paints too (§4.3, §6.8).
- **`FieldRegistry`** (`field_registry.dart`) — the forms open for editing, by the stem of the file each edits. A `FormSide` registers its own setter when it makes its saver and leaves when it drops it (by identity, so a departing form never removes a live one's entry). An agent's `setField(stem, key, text)` finds the field the form names by that key and calls the field's own setter, `FormFieldSpec.set` — the same function its `onChanged` runs, so a birthdate is parsed, an age becomes a number under `appearance`, an empty name is an inline error rather than a removal — after putting the text in the box; the autosave, the identity lock and the stale refusal then hold for an agent as for a person. A control that takes no text (the kind pull-down, the genre picker, the epochs editor) declares no setter, and it, like a key no field owns, answers false.
- **`OpenDraft.stem`, `OpenDraft.pending`, `OpenDraft.apply` and `OpenDrafts.of(stem)`** (`drafts.dart`, `pending` 5.11b) — how a change made **below the forms** reaches a file a form is open on. A folder or scene added to, removed from or moved in a file's `children` is the controller's write (§7), and the file may be the one on screen — the project file's page, a folder's. Written beside the draft, the change would be kept out of a dirty draft (§9.3: an outside change while dirty is kept out), whose next autosave would then be refused as stale, and *Discard and re-read* would lose what was typed meanwhile; re-seeding a clean draft instead resets every box under the person's hands, trailing space and caret included. So there is **one writer per file while its form is open**: `OpenDrafts.of(stem)` answers the draft registered last for that exact file, and `apply(change, key:)` takes the change as the draft takes a keystroke and writes it now (`DraftSaver`: `change` then `settle`), answering what refused the write — a failed state, nothing less: `settle` also answers false when something was typed during a write that landed, and the saver's `error` keeps an older failure after a later success. No box is reset, the recorder hears one `draft` line for the key, and `FieldRegistry` is untouched, since no field owns `children`. With no form open the registry is empty and the controller saves the file as it is on disk. `DraftsNotSettledException` is what an action that writes beside the drafts throws when `settleOpen` answers false, as a fork says *finish saving first*. **`pending`** is the whole document the draft would write while it has anything to write, and null when it has not, the file on disk then being what a write starts from: what a change made below the forms is tried dry against, so that the check and the write are made against one document (§7).
- **`DraftObserver` / `DraftObservers`** (`drafts.dart`) — `onChange(entity, key, value)`: the saver tells the observers each change with its key (null when a copy or a block edit touched several) and, since the issue recorder needs to hear what changed and not only that it did, the draft's value at that key, deep-copied once per observer so an observer can never write into a draft or into another observer's copy; the value is null when the key is null. `OpenDrafts` in the same file is the set of drafts a form holds open, which a fork and *Copy to a folder…* settle through this seam without knowing the forms.
- **`RouteEvents`** (`route_events.dart`) — one `NavigatorObserver` `app.dart` installs on the app's navigator, silent until something listens: a dialog, a menu or a sheet opening and closing, named by its kind from the route's own type (never its type's name, which a release build minifies) and by its name when it has one. The issue recorder is its one listener; a failing listener is logged by its error's type and never reaches the navigator.
- **`PluginRuntime`** (`plugin_runtime.dart`, §6.11) — the plug-in runtime as the pages, Settings, Provider keys and the agent layer see it, in the state's own types (`PluginSummary`, `PluginSection`, `PluginField`, `PluginKeyOwner`, `PluginKeySlot`, `PluginProvider`, `PluginCallControl`, `PluginCallOutcome`, `PluginKeyCheck`): the plug-ins, the key slots, a type's sections, the providers of a hook, the changes Settings → Plugins makes, the calls — `runAction`, `runEntityHook`, `call` and `verifyKey` — and `changes`, a `Listenable`. `PluginRuntime.current` is `NoPluginRuntime` (no plug-in exists) until `lib/main.dart` installs the host, which no product package imports. Beside it, `legacy_keys.dart`: `ensureLegacyKeysMoved` moves the older key names once, and `movePreferences` their states; Provider keys, dictation and the key door call them. The seam is deliberately the whole of what the app asks of plug-ins, and its types are the state's own — a page's view of a plug-in, resolved and in the app's language — apart from the manifest's types in `filmopen_plugins` (kept as on 17 September 2026): the screens, the forms and Provider keys import neither the host nor the plug-ins package, and a fake runtime tests them; a plug-in feature therefore touches the seam, the host and a screen.
- **`DeviceRegistration`** (`device_registration.dart`) — where the account says who is signed in, for the device's registration (§6.6b): `signedIn(DeviceAccount)`, `signedOut` and `registers` (whether a sign-in here would register at all, for the account card's sentence), a no-op answering false until `lib/main.dart` installs `filmopen_device`'s `DeviceRegistrar` off the web, so that no test and no agent build reaches a store or the network through it. Not the agent layer's, but a seam of the same shape: the account does not know the device package, nor it the account.
- **Semantics identifiers** on the controls an agent drives (§13): what a recorder writes into a tape and replay acts on, so the product never contains a line that says "if recording". The walk that finds a control by identifier or by label and names the one under a point (`filmopen_state/semantics_walk.dart`) is shared by `DriverAutomationHost` and the issue recorder, so both name a click's target the same way; `selectionToJson` (`selection.dart`) is shared the same way, since the tape writes a selection too.

**`OpenDrafts`** holds the drafts open across the application and the writes no form waits for any more. `settleOpen` settles every draft and waits for those writes, for an action that reads files the way they are on disk — a fork copies one (§13.1). **`settleDetached`** is the wait **without** the settling, for a road that writes nothing and still has to read a file back (`patchEntity`'s unchanged road, §7): such a write may be landing on the very file about to be read, and success read before it lands is success against a value the file does not hold — while settling every form for a change that wrote nothing would force each past its debounce. A write handed to `track` must never complete with an error, since it is awaited for callers that answer a code rather than throw. None of these starts a listener, takes a dependency or changes what a person sees; `filmopen_state/test/seams_test.dart` proves the no-op host does nothing, that the registry and the observers route as described, and that the route seam is silent with no listener and names what a listener hears; `test/identifiers_test.dart` proves the identifiers are unique and the registry's typing reaches the box.

**The seam by role** (H6). `PluginRuntime` was one abstract class of 25 members for Settings, consent, keys, entity hooks, platform calls and the developer page, which every package that touched any of it had to take whole. It is **four interfaces it implements**, over one they share: `PluginCatalogueView` (what is installed and what it says of itself — the plug-ins, the key slots, a page's cards, a hook's providers, the contract's revision), `PluginSettingsControl` (what the person may change — on and off, *Allow*, a grant, a setting, a preferred provider, an install, the development folder), `PluginInvocation` (what may be run — an action, *Check*, an entity hook, a key check, a platform hook) and `PluginDevBench` (the developer page's own road). `PluginRoleBase` carries the two every caller shares, `isAvailable` and `changes`; `attach` belongs to no role, since nothing but the entrypoint calls it.

**One object and one static**: `PluginRuntime.current` is unchanged and `NoPluginRuntime` untouched, so the fourteen test fakes that extend it needed no edit. What changed is that **a package names the role it uses**: each role answers `<Role>.current`, and `filmopen_forms`, `filmopen_keys`, `filmopen_plugin_dev` and `filmopen_plugins_ui` name no more than the roles they call — a test reads their sources, outside their comments, and fails on any that names the seam whole, or the base, which every role already answers. **What still names `PluginRuntime` is what installs one**: `lib/main.dart`, the host, and the fourteen test files that install a fake. `lib/screens/settings_page.dart` holds `PluginSettingsControl` at every one of its sites, the base's two members among them — which `plugin_roles_test.dart` pins as the set of roles that file names.

## 8. The tree

### 8.1 Model — `filmopen_state/tree_node.dart`, `filmopen_state/selection.dart`

`TreeNode`: `id` (stable, path-like), `label`, `detail` (muted secondary text), `tooltip`, `icon` (a `TreeIcon`: an entity type, or a glyph for a grouping row — the model names the thing, and `filmopen_tree/tree_icons.dart` chooses the Flutter icon, so the model imports no Flutter), `selection` (what clicking shows; null for pure groupings), `children`, `initiallyExpanded`, `isOfficial` (star), `isPick` (the viewer's pick, a green check), `isStalePick` (the project made another version official after the viewer picked this one, §13.2: the label and the check are drawn in the error colour, with a tooltip), `hasProblem` (warning icon, error-coloured).

`Selection` is sealed: `ProjectOverviewSelection`, `CategorySelection(type)`, `EntitySelection(type, tag, {epoch, stem})`, `BatchSelection(stem)`, `OtherFilesSelection`. Each exposes `matchKeys`, most specific first (`entity:<stem>`, `entity:<type>:<tag>@<epoch>`, `entity:<type>:<tag>`), which `TreeModel` indexes so a link from the detail pane can find and highlight the right row even when it names a version the tree does not show.

`Selection` is a sealed class, switched over exhaustively in three places — the detail pane, `selectionToJson` and the agent host's target check — and **`ScriptSelection`** (`{"kind": "script"}`, match key `script`) is what the tree's Script row carries: the row has a page of its own (§9.3). **What a row of the script says** is `ScriptRowText.of(l10n, row)` (`script_row_text.dart`): its label, its detail, its tooltip, the short name a filter finds it by, the page it opens and whether a reader flags it, from the walk's `ScriptRow` — the tree builder draws it, and the Script page and a folder's contents read the same function, so the three cannot come to say different things; `folderKindDetail` is the folder's kind in words.

A row of the Script branch also carries its **`ScriptPlace`** (`TreeNode.place`): the file whose `children` lists it (`parent`: the project file in use, or the version of the folder drawn above it; null for the Script row and for a row under *Not in the script* that no list holds), the `entry` as that file writes it with its `occurrence` among equal entries — what the list's edits take — the file an *Add* there goes into (`container`: the project file for the Script row, the version drawn for a folder's row; null for a scene, and for a second listing and a cycle, whose contents are under the first), and the `name` a message calls it. `ScriptPlace.ofRow(row)` makes it, for the tree and for a page's row alike; since step 7 it also says where the entry stands in its list (`index`, `siblings` — every entry of a list is a row, readable or not, so a row's place is the entry's), and carries the entry of a row no list holds, which *Move to…* files under that name. The model says where things are; what a row's menu offers is the pane's to say (§9.2). `TreeNode.shortName` is the entity's short name where the row shows it nowhere — a folder's, whose detail is its kind — so that the filter still finds a row *by name or tag*.

### 8.2 Builder — `filmopen_state/tree_builder.dart`

Top-level rows, in order:

1. **Project** — name, tag, its `pj` versions as children with the official star; flagged when a choice is pending.
2. **Script** — the row opens **the Script page** (`ScriptSelection`, §9.3). Beneath it, the script as the viewer sees it, drawn from **the one walk**, `scriptOutline` (§5.12), which the builder makes once: the project file's `children` in its order, each folder's beneath it, to any depth; the Script row counts them as *items*, entries that name nothing included, where 1.11 counted *roots*. **Every row of the branch names its entity first**, as the library's rows do: a **folder** row is the folder's name with its kind in words as the detail (`Labels.folderKindLabel`: the vocabulary's words in the reader's language and in lower case, as every detail of the tree is; another token **as written**, capitals and all, since it is the author's word; nothing where the folder has no kind), the folder icon, and is open at first; a **scene** row is its name with its short name as the detail; a **shot** and a **cue** row likewise. The **stem is the row's tooltip** (§8.3), since the row no longer shows the short name of a folder at all. Beneath a folder: its **Versions** row where it has more than one version, its **Cues** row where a cue belongs to it, then what it holds. Beneath a scene: **Versions**, **Shots**, **Cues**. A *Shots* row lists the scene's explicit `shots` or, absent that, every `<scene>.<n>` group in natural order; a *Cues* row the scene's explicit `cues` or, absent that — and always for a folder — the cues that belong to it (`cueGroupsOf`, §5.12: a cue that names a `folder` is never a scene's); the tooltip says which, and a folder's says that its cues are the ones that name it, since a folder lists none. An explicit list that names one shot or cue twice gives the second row `#2`, as `children` does. **A row's id is its parent's id, `/`, the entry's type and what the entry writes after it** (`script/fo:f1/sc:1`; `entry:<index>` for an entry that names no type), and since that is whatever a file wrote, the signs an id is built with are written as their codes in it — `%25`, `%2F`, `%23` for `%`, `/`, `#` (`TreeBuilder._idSegment`): an entry `fo_f1/sc:1` would otherwise claim the id of scene 1 inside folder f1, and a drop or a move looked up by id (`TreeModel.nodeOf`) would land elsewhere. A short name and a stem hold none of the three, so every ordinary id reads as it always did. Empty wrappers are omitted; folders, scenes and warning rows never are. A *Versions* row has one row per author (the same rule as under an epoch), so another author's scene is one click away although the row shows the version in use; a Compare column heading opens its version as well. **What a reader reports is a flagged row with its reason, never a guess** (the format's §8.5): an entry that names neither a folder nor a scene is shown as written with its `ChildProblem`'s sentence (a bare tag, another type); an entry that names nothing, or whose version cannot be chosen, is shown **as written** — never blank — with the resolution's reason, and where the project has the folder or scene its page and its *Versions* row are still reached from it; a second listing is the entity's name with *Listed a second time in the script*, and a folder that lists one above it is a *circular story reference* row; neither is followed. A row's id is its parent's and the entry — `script/fo:s1/fo:e2/sc:5`, a pinned entry by its full stem (`script/sc:sc_1_ann_v1`), an unread entry by its place (`script/entry:3`) — and a second equal entry under one parent gets `#2`, since an id is unique; a shot's and a cue's id hangs on its owner's (`…/sc:5/sh:5.2`), and the wrappers are `…/versions`, `…/shots` and `…/cues`. 2a. **Not in the script** (`unfiled`) — only when something is: every folder and scene of the project that no list names (`ScriptOutline.unfiled`), flagged, each with the rows a folder or a scene has beneath it (`unfiled/fo:f6/sc:6`), so that a file taken out of a folder, or one whose add did not finish, never disappears. A project made before folders shows its scenes here and an empty script.
3. **Characters, Locations, Props, Styles, Misc, Documents** — each entity by tag, then its epochs in the project's declared order (§8.2), then **one version row per author** showing that author's latest version (`author vN`, with the version label or `from <stem>` as detail; official star; the version in use — the pick, `pickAt` — as a green check. Only an explicit pick wears it: official in use with nothing picked carries the star alone, and official comes before an author's own latest (§6.1)). The tree does not list every iteration: beneath an author's row sit only the older versions of theirs that still matter — the official one and the pick. An epoch (or an entity without epochs) where nothing is in use — several authors, nothing official, no pick — is flagged with the warning icon and says so in its tooltip. Dotted tags nest under their parent (outfits under a character as **Outfits**, areas under a location as **Areas**); one whose parent file is missing is listed at the top level with a warning. The same version rule applies to the project's own versions and to models, platforms and plugins. An entity row is named by the version in use (`FilmProject.nameOf`: the pick at the project's default epoch, else at the entity's first epoch), and so are the epoch overview's heading and the category lists, so a rename in the version being used shows everywhere the entity is named as a whole.
4. **Models, Platforms, Plugins** — entity, then versions.
5. **Render batches** — `r<id>` with author, kind and item count.
6. **Other files** — present when the folder holds companion or unknown files.

A pick an official version overtook (`Pick.staleSince`) is drawn in red on the version row that carries the check **and** on every row above it up to the entity — the author's latest row when the pick is an older version beneath it, the epoch row, the library or spec entity row, a folder's or a scene's row and its *Versions* wrapper, a shot or cue row (which has no version rows of its own), the Project row — so a collapsed tree still shows that a page has something to ask. A folder's or a scene's row that shows a version pinned by a full reference is not the pick and is not painted, although its *Versions* row still is; the *Shots* and *Cues* wrappers, like the category rows, sit above the entity and are not painted. Nothing about resolution changes: the pick is still what the row shows (§7).

Every visible string comes from the `AppLocalizations` the builder is given.

### 8.3 Widget — `filmopen_tree`'s tree view

**Five files** (the tidy after folders): `tree_view.dart` the list, its filter and the edge scroll; `tree_row.dart` the row — what it draws, the drop it takes and the drag it starts; `tree_drag.dart` the drag's doors (`TreeDragDrop`, `DropPlace`), how long a drag rests on a closed folder before it opens (`treeOpenOnRest`, which the view names `TreeView.openOnRest`) and the drop's geometry as a pure function, `placeIn(share, places)`; `tree_drag_widgets.dart` what follows the pointer and the two device-restricted draggables; `tree_icons.dart` the one place that chooses a Flutter icon for a `TreeIcon`. Nothing of the view is exported beyond what always was.

A flat, virtualised `ListView` over the visible rows. A row shows indent, chevron (toggles), icon, label plus muted detail as one rich text, then the star, the check or the warning icon. A stale pick paints the label and the check in the scheme's error colour and puts the reason in a tooltip on both. **Any other row that has a tooltip says it on hover of its label** (before it the view drew a row's tooltip on a flagged row's warning alone, so a wrapper's *order from the list* and a library row's *from the shared library* were never seen); a flagged row keeps saying its own on the warning, and the theme's 600 ms wait keeps a pointer moving down the tree quiet. Tap selects when the row has a selection, otherwise toggles. There is deliberately no double-tap handler: it would delay every single tap by the double-tap timeout. With a filter, only rows that match or have a matching descendant are shown, fully expanded. **A row's menu**: the view takes `menuOf(node)`, a list of `TreeMenuItem`s (identifier, label, icon, what it does, and the reason it is disabled, shown as its tooltip), and **asks for it when the menu is opened** and not while the row is drawn: a tree draws every visible row on every frame, and what a row offers is walked out of the project. A row that is **a place of the script** gets a **⋯** button (`tree:<node id>.menu`) — on the row the pointer is over, on the selected row, and on a row that cannot be selected, a flagged entry that names nothing, since a touch has no other way to it (a long press is a drag's, step 8) — and opens the same menu on a right click, where it was asked for. *A place of the script* is the same rule as *a row with something to offer*, since every place offers at least one item: a list to add into, an entry to move, or the list that holds it to be taken out of. The Script row is a place only where **a project file is in use** — with two authors' project files and none official the reader asks which first (§6.1), and until it is answered the script has no list to add into, so the row offers nothing and wears nothing. A menu that answers nothing all the same opens nothing, rather than reaching Flutter's own assertion. The button and the menu are `row_menu.dart`'s (`RowMenuButton`, `showRowMenu`, `TreeMenuItem`), which a page's rows use too, so a row is operated the same way wherever it is drawn. A row is 30 px with or without the button; it is built only while it shows, so it takes no tap it cannot be seen to take.

**Dragging** (§3.11). The view takes a `TreeDragDrop` — `canDrag(node)`, `placesOn(target)`, `refusal(dragged, target, place)`, `onDrop(dragged, target, place)` — and knows nothing of the script: what may be picked up, what a row takes and what a drop does is the pane's to say (§9.2). A row that may be dragged is one **with the mouse at once** — as the pointer moves past the slop, so a click stays a click — and **with a finger or a pen after a long press**, a tap and a scroll staying what they are: two recognizers, each taking its own kind of pointer (`_MouseDraggable` — the mouse alone: a trackpad's click-and-drag arrives as a mouse, and its two-finger pan is the list's scroll, `_TouchDraggable`), nest around the row. Since a long press is then the drag's, the label's tooltip on such a row answers to the mouse's hover alone (`TooltipTriggerMode.manual`): it sits deeper in the tree and would otherwise win the same press. What follows the pointer is the row's icon and name; the row left behind fades. **Every row is a target while a drag is on**, and the pointer's height on it says the place (`DropPlace`): a row that takes a drop *into* it and *beside* it gives its upper and lower **thirds** to *before* and *after* and its middle third to *into* — 10 px each of a 30 px row, since a finger hides the row it is on and a quarter was 7 px; one that takes only the edges splits in half; one that is no part of the script has no place. **A place the drop may go shows**: the row's ground turns `primaryContainer` for *into*, a 2 px line in `primary` at the row's upper or lower edge, from the label's indent, for *before* and *after*. **A place it may not go shows nothing**, and a drop there moves nothing and says the reason (`showMessage`) — a target therefore accepts every drag but its own row's, which is a drag given up and says nothing, and hears nothing of it while it is over itself. **The pane is asked once for a place** — the answer walks the script — and not again while the pointer moves within it. A closed folder the drag **rests** on *into* for `TreeView.openOnRest` (700 ms) opens, so that what it holds can be reached without letting go: the time is counted from where the pointer last stopped (6 px of wander allowed, a held finger never being still), so a drag sweeping across the row opens nothing. Within `TreeView.scrollEdge` (40 px) of the list's top or bottom the list scrolls that way, 8 px a frame — **one timer for the length of the stay**, reading the direction at each tick, so a pointer sliding along the edge scrolls as one that holds still does — until the drag leaves the edge or ends. **The end of a drag is heard however it ends**: by the row that started it (`onDragEnd`, `onDragCompleted`, `onDraggableCanceled` — the second being the only one Flutter calls once that row has been scrolled out of being, which the edge scrolling does) and by the list itself when the pointer comes up (`Listener`), since a timer left running would hold the list at its end for good. A drag cannot be made by an agent nor replayed by the recorder (§14): every move a drag makes is a menu item too.
