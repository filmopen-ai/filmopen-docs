# The model layer

How a project folder becomes an index the rest of the application reads: the filename grammar, documents, resolution, epochs, media names and the script's list.

## 5. The model layer

### 5.1 Filename grammar — `filmopen_format/stems.dart`

`FileNameParser.parse(path)` implements Project Specification §5.4 and returns one of a sealed set:

| Class | Filename shape | Holds |
| `VersionStem` | `<type>_<tag>[_<epoch>]_<author>_v<n>` | type, tag, epoch?, `Author`, v; `stem`, `versionsKey` (`ch_main-hero_30yo`), `groupKey` (`ch_main-hero`) |
| `OfficialStem` | `<type>_<tag>[_<epoch>]_official` | type, tag, epoch?; `versionsKey` |
| `CommentaryStem` | `cm_<type>_<tag>_<author>` | target type, tag, author |
| `BatchStem` | `rd_<id>_<author>` | id, author |
| `TakeName` | `<deliverable>_<source stem>_r<id>_<renderer>_<n>.<ext>` | deliverable, source `VersionStem`, batch id, renderer, n, extension; `batchStem` |
| `UnknownName` | anything else | the path |

Rules enforced by the parser: exact token counts per type (library types carry an epoch, spec types do not); `v<n>` with n ≥ 1; take number `n` is a positive integer without leading zeros; the reserved owner `official` is never accepted as an author; a take's batch token is `r` followed by at least one character. `parseStem(stem)` parses a stem without extension, as found in `forkedFrom` and batch `source` fields.

`namingWarnings(parsed)` returns warnings (as codes) for any segment outside `[a-z0-9][a-z0-9-]{0,19}` or longer than ten characters (§5.2). It is applied to every parsed name, including takes and commentary.

`Author` (`filmopen_format/author.dart`) splits `owner[.workspace]`; equality is by full handle.

`EntityType` (`filmopen_format/entity_type.dart`) is the enum of the format's seventeen prefixes — `folder` (`fo`, a spec type) which took `se`, `ep` and `sq` out of it with the Project Specification 1.12 (§5.3), so that a file of one of those types is a name the grammar does not describe and sits under *Other files*, reported and never touched — with `category` (library / spec / commentary / renderBatch), `hasEpoch`, `isVersioned`, and the dotted-tag containment rules `parentType` / `containedType` (outfits nest under characters; areas under locations). `Deliverable` is the enum of take prefixes with `isImage`. Neither enum carries display text.

### 5.2 Documents — `filmopen_format/entity.dart`

- `Entity`: one versioned file. Holds the `VersionStem`, the project-relative `path`, the complete `json` map (unknown fields preserved) and `rawText`, the file's text as read, which a save hands back to the source so a file changed meanwhile is never overwritten. Typed accessors (`name`, `versionLabel` — §7, with the earlier `label` spelling still read, `forkedFrom`, `notes`, `kind`, `stringList(key)`, `blocks`) never throw on a wrong JSON type. `headerMismatches` and `fieldTypeWarnings` return warning codes.
- `OfficialPointer`: from an `_official.json`; `fromJson` returns null when the `official` field is missing, which the loader reports. Keeps its whole `json` so the writer can rewrite it without losing fields.
- `Commentary` / `CommentaryEntry`: one `cm_` file with `pick` and `pickedAt` (`prefer` is the 1.5 spelling, still read) — the author's *pick* — and entries (`on`, `at`, `rating` ±1, `text`, `block`, `field`); keeps its whole `json` for the same reason.
- `RenderBatch` / `RenderItem`: one `rd_` file with its items; totals cost.
- `Take`: a media file discovered by name; never listed inside an entity (§12.1).

Two helpers, `stringField(json, key)` and `numField(json, key)`, are the only way JSON scalars are read. A third, `parseInstant(text)`, is the only way a timestamp is read as an instant: RFC 3339 with `Z`, `z` or an offset (§1.4); a value without a zone would be local time on whichever machine reads it, so it counts as absent, like anything that does not parse.

### 5.3 The index — `filmopen_format/project.dart`

`FilmProject` is immutable after loading and holds:

| Field | Content |
| `entitiesByStem` | every versioned entity by full stem |
| `groupsByKey` | `EntityGroup` per type+tag; each group holds `EntityVersions` per epoch (spec types use the single epoch `null`); versions are sorted by author handle then number |
| `officialsByKey` | pointers by versions key |
| `commentaries`, `batches`, `takes` | as discovered |
| `companionFiles` | named by the grammar but not JSON (a plugin's `.js` beside its manifest) |
| `otherFiles` | not named by the grammar; reported, never touched |
| `warnings` | every `ProjectWarning` raised while loading |
| `projectCandidates` | every `pj` version in the folder, stable order |
| `selectedProject` | the `pj` version in use, or null when the user must choose (`needsProjectChoice`) |
| `projectOfRecord` | the loader's own §4.1 choice — the official `pj`, else the sole author's — which a viewer's pick never replaces; directors are read from it |

Queries: `group(type, tag)`, `groupsOf(type)` in natural tag order, `childGroups(type, parentTag)` for dotted tags one level down, `officialPointer` / `officialEntity` / `isOfficial`, `takesFor(group)`, `commentaryFor(group)`, `batch(stem)`, `groupCounts`. `withSelectedProject(entity)` answers the chooser without reloading.

### 5.3a Project-level knowledge — `filmopen_format/project_kind.dart`, `filmopen_format/epochs.dart`

`ProjectKind` is the enum of §8.1 (`short-film`, `film`, `mini-series`, `series`) with older spellings read as their nearest value (`fromName`: 1.4's `franchise`, and the short-lived `short` / `feature` / `miniseries`), and nothing else: since the format's 1.12 the kind is a word for people, the OMC mapping and a website, optional, naming no levels and choosing no list (§8.1), so `isEpisodic`, `defaultRootKey` and the label of a story level (`unitLabel`) went with the levels. `recommendedGenres` is the vocabulary of Appendix A.9. `EpochDeclaration` / `declaredEpochs(json)` read the project's `epochs` object in the order §8.2 defines (unnumbered first in file order, then by `order`); `encodeEpochs(list, previous:)` writes it back renumbered 1..n, keeping fields the app does not know. `FilmProject` exposes `kind`, `declaredEpochList`, `defaultEpoch` (the first declared, else `default`), `epochLabel`, `sortedEpochs(...)` (declared order, then natural), `isDirector(author)` (§8.3: read from `projectOfRecord`, never from the viewer's own fork of the project file, which `forViewer` selects; where the folder has no file of record, the origin of the selected file decides — followed back through `forkedFrom`, whoever wrote each link, to the project file that forks nothing — so no fork appoints anybody and the original's author can write a first pointer; a loop or a source the folder lacks decides nothing. `ProjectWriter.saveEntity` keeps a project file's `forkedFrom` as it is, so the chain cannot be cut through the app), `commentaryBy`, `ownPickStem`, `pickOf(group, viewer)` and `isPickOf`.

### 5.4 Resolution — `FilmProject.resolve`

Implements §6.1 in a simplified but faithful form. Given a type, a reference (tag or full stem), an optional epoch, whether that epoch was explicit, and an optional viewer:

1. A full stem names its file exactly.
2. No such tag → unresolved (`noEntity`).
3. Epoch: for library types the wanted epoch is the given one or the project's default epoch (the first it declares, §8.2; `default` when it declares none). If there is no file for it: an explicit epoch, or the default itself, is unresolved (`noEpoch`); an implicit epoch falls back to the default and marks `fellBack`; no file at the default either → unresolved (`noEpochOrDefault`).
4. Author — the viewer's **pick** at that epoch (`FilmProject.pickAt`, §6.1 step 2): the viewer's `pick` when it names a file here (a pinned stem, or the official pointer when it is `<versions key>_official`), then — for a workspace handle — their owner's; then the **official** version; then the viewer's own highest version, then their owner's, which is what an author sees while the project has chosen nothing; then, if exactly one owner has versions, that owner's highest. A pick beats official and nothing else does: an author who has said nothing is on official, and forking records a pick, so an author's own work is not lost behind the project's choice (§13.1, §13.4). The project's own `pj` versions skip the own-highest step and count author handles rather than owners in the last one, so the check and the loaded project agree (§4.1). `pickAt` returns a `Pick` (entity, `PickReason`: picked, tracksOfficial, official, own, soleOwner, and `staleSince`) and is the one source the tree, the header and the version menu read. Compare is the exception: its columns are the viewer's own latest and whatever they selected, so it reads `pickAt` only to draw the check on a heading. `Pick.staleSince` names the official pointer that superseded the viewer's own pick — `setAt` strictly after `pickedAt`, both read with `parseInstant` and compared **to the second**, so a fraction another tool wrote does not make equal seconds later (§1.4, §13.2). It is null whenever either time is missing, unreadable or without a zone, when the seconds are equal, when the pick names the official version, when the pick tracks official, and for a pick a workspace inherits from its owner, which the workspace cannot abandon. It never changes what `pickAt` returns: no timestamp decides (§7). `Pick.showsCheck` is what a check is drawn from — false for `PickReason.official`, since the star already says official is in use (§13.4).
5. Otherwise unresolved (`ambiguous`, listing the owners); `hasNoPick` names that state for the UI.

§6.1's other half — a file *named by an official pointer* resolves **through official only** — is `resolve(..., referencing:)`, with `inUseFor(versions, viewer, referencing:)` behind it: for a file an official pointer names, `officialPickAt(versions)` — official, else the sole owner's highest (by handle for the project file, as in `pickAt`), and nothing an author picked; for anything else, `pickAt`. `nameOf` takes the same `referencing`. It is passed where a version's own references are rendered (today the Script tab's speakers) and **not** where the reader is browsing: the tree, the version row and the pages keep showing each viewer the version in use for them, so a fork is still what its author sees. *A proposal sees its author's world; official sees the official world.*

### 5.5 Project selection — `ProjectLoader._selectProject`

Implements §4.1: a valid official `pj` pointer wins; else the highest version when exactly one author *handle* has project files — handles, not owners as §6.1 step 3 counts them, so a workspace's translated fork of the project file asks rather than being opened as the owner's latest; else no selection and the UI asks. Several project *tags* in one folder also ask. An official pointer to a missing file is a warning and falls through as if absent; one naming a version of another entity or epoch is reported (`officialWrongTarget`) and dropped, so it is never anybody's official version. The choice is kept twice: as `selectedProject` and as `projectOfRecord`, which nothing replaces. `FilmProject.forViewer(viewer)` then applies the viewer's own pick for the project entity (their `pick` in `cm_pj_<tag>_<viewer>.json`, §4.1): the provider calls it after every load, so a viewer who forked the project file works from their fork while everyone else keeps the official one.

### 5.6 Diagnostics — `filmopen_format/diagnostics.dart`

`ProjectWarning(kind, args, path)` with `WarningKind` (naming, duplicate stem, header missing or mismatched, field type, official pointer problems, unreadable JSON — including `duplicateKey`, which carries the repeated name so the sentence can be in any language (§18.1) — project selection, the manifest and library kinds: `noManifest`, `manifestTagMismatch`, `dataLocatorMalformed`, `dataLocatorUnsupported`, `dataRootUnavailable`, `dataRootAbsolute`, `libraryStemShadowed`, `libraryUnavailable`, `noEpochsDeclared`, §8.2, and `pickOtherEntity` — a `pick` naming an existing file of another entity — `officialWrongTarget` and `timestampUnreadable`, a `pickedAt` or `setAt` that is not an instant with a zone). A second commentary file with the same stem in another folder is a `duplicateStem`, and the first found is the one kept and written. `ResolutionProblem(kind, type, reference, epoch, owners)` with `ProblemKind` (five kinds). Both have a `toString` for logs only; the UI renders them through the localisation layer. A third set of codes, `ChildProblem` (`childUntyped`, `childWrongType`, `childDuplicate`), belongs to an entry of a `children` list and is §5.11's.

### 5.7 The manifest — `filmopen_format/manifest.dart`

`filmopen-project.json` (Project Specification §4.4) is the one file in a project that is not somebody's versioned work. `ProjectManifest.fromJson` reads `tag`, `data` and `note` tolerantly (a missing or mistyped field is null and the loader warns). `DataLocator` is the typed "where", read from and written to the key **`kind`** (`DataLocator.kindKey`; the format's 1.12 §4.4 and §7, *`kind` says what sort of thing*) — 1.11's `type` is not read, so a manifest that still spells it is `dataLocatorMalformed` and the project opens as if it named no media root, nothing converting it: `LocatorType`, a Dart name older than the key's (`local`, `dropbox`, `google-drive`, `onedrive`, `icloud`, `url`), or an unknown name kept as text (`kindName`); `isLocal`, `isAbsolutePath` (POSIX, drive-letter and UNC forms). `ProjectManifest.template` is what the creator writes. `projectManifestFileName` is the one constant that names the file.

### 5.8 Short names — `filmopen_format/short_name.dart`

The format's *segment* (§5.2) as a person types it: `ShortName.pattern` (`[a-z0-9][a-z0-9-]{0,19}`), `validate` (a `ShortNameProblem`: empty, invalid characters, bad start, too long), `validateHandle` (an author handle, §5.6: `owner[.workspace]`, each side a segment — more dots is `tooManyDots` — and the owner never `ShortName.reservedOwner`, `official`, which is `reserved`; the filename grammar's `reservedOwner` is the same constant), `isLongerThanRecommended` (over ten: warn, never refuse), `normalise` (free text to the nearest segment, never inventing one). The filename grammar in `stems.dart` uses the same pattern, so there is exactly one place the rule lives; `filmopen_ui/short_name_field.dart` is the input box built on it.

### 5.9 Origin — `Entity.origin`, `Take.media`

`EntityOrigin { project, library }` says which root a versioned file came from; `EntityGroup.isFromLibrary` is true when every version of an entity came from the library. `Take.media` is the `MediaLocation` resolved at load time, because a take may sit in the media root rather than the project folder: `AssetMedia(key)` for the bundled sample, `FileMedia(path)` for a folder on disk and `BytesMedia(bytes)` for a session copy's own media, which is in memory and never on disk.

### 5.10 Media names, references and paths — `filmopen_format/media_names.dart`, `media_refs.dart`, `media_slot.dart`, `media_paths.dart`

What a piece of media is, what an application calls an upload, and where a hand-supplied reference goes — one place, because the importer that writes the file, the page that looks for its thumbnail and the filename grammar that must parse what was written all depend on the answers agreeing.

`MediaKind { image, video, audio, other }` and `mediaKindOf(name)` read the lower-cased extension against `mediaExtensions` (Project Specification §6.3); anything else is `other`, which the importer refuses. `uploadPrefixFor(kind, type)` is the one place the rule lives — **a prefix names a file's purpose, never its origin** (§5.5): a picture is a `cs` take, a clip a `cl` take, a character's audio its `vo` voice sample, and any other sound an `am` take, an outfit included, since an outfit has no voice (§9.0). `uploadTakesFor` names the files of one upload action, numbering from 1 **per purpose** and leaving a file that is not media without a name; `nextBatchId(at, taken:)` is **eight lower-case hex digits of the second the import began**, and takes the next free one when that author already has it — the clock proposes, the check decides (§5.2, §12.3). `thumbnailPathFor(ref)` answers `thumbnails/tn_<take stem>.jpg`, relative to the **project** folder, for a reference that is a **take** — by its stem or by its file name — and null for anything else. Only a take's name is unique in a project by design (§5.4: the batch id and the take number are in it), and it stays unique whatever folders stand before it; `stills/front.png` and `posters/front.png` would claim one `tn_front.jpg` between them, so a reference whose basename is not a take's has no thumbnail of its own in this version and the tile draws the kind's stock picture. The grammar says where a name ends, never the last dot, since a workspace handle (`john123.locale-th`) and a dotted tag (`sh_5.2`) carry one. `isInReservedFolder(path)` says which files a reader understands by the folder they are in (§4.2) — `render/`, `thumbnails/`, `conform/`, `plugins/` (a plug-in's locale files, README and assets, its manifest and code are still read by their names), and never `_inbox/`.

**`MediaSlot`** (`media_slot.dart`) is the format's word for **a place references go** (§9.0), and it is resolved here because the rules that resolve it are the format's. `MediaSlot.refs` is the file's own array — the plain array where `refs` is one, the `images` group where `refs` is an object, a new plain array where the file has no `refs`; `MediaSlot.group(name)` is a named group, and `group(imagesGroup)` on a plain array *is* that array, since a plain array is the images; `MediaSlot.voice` is a character's `voice.refs`; and `MediaSlot.path('a.b.c')` is an array of the file's own, for a place §9.0 does not name. `pathIn(json)` answers the keys to walk and depends on the document, because two of the four do. Before this the place was derived from the media's **kind** alone, so of the twelve group names §9.0 recommends, and any a file has of its own, only three could ever be written to (§1).

**`withReferencesInserted(json, slot, references, {first, preview})`** (`media_refs.dart`) puts them there **as one block and in the order given**: `[A,B]` into `[X,Y]` with `first` gives `[A,B,X,Y]`, and a later `[C]` gives `[C,A,B,X,Y]`. One already there is **neither repeated nor moved**, so a job run twice leaves the file exactly as the first run did — which is what makes the ingest replayable (§6.13). The document is copied, never edited in place (§13.1); a plain array becomes `{images: […]}` the first time a group *other than the images* is needed; a place holding a value of another shape is **left alone**, the answer then not naming the references, which is how a caller is told (§17); and a write with nothing left to write makes no empty place. `preview` is the reference to propose where the file has none, and must be **one the place names once the write has happened** — not merely one of those passed in, since a reference the place already held counts, which is how `withReferenceAdded` has always behaved. §9.0 lets a writer propose the first **picture** it adds and never lets it change one the author set; **which reference is a picture is the caller's to say**, a reference being possibly a take stem with no extension at all, so the format refuses only what it can tell is *not* a picture — a clip or a sound by its name — and takes the caller's word for the rest. `referencesIn(json, slot)` reads one place; `referencesOf(json)` still lists what the whole file names, in file order without repeats — what the reference section shows.

**`withReferenceAdded(json, type:, kind:, reference:)` stays**, now a wrapper over the block insert with `slotFor(type, kind)` — the kind-to-place rule it always followed, said as a slot — and every test it had. Rewriting it this way **fixed a latent loss**: the old code built `{images: refs, groupFor(kind): […]}`, and `groupFor` answers `images` for `MediaKind.other` too, so the second entry won and *every picture in a plain array was dropped*. Unreachable in the application, the importer refusing `other` before it gets there (Project Specification §12.3), but the format's own function did it.

**Where a media folder sits** is `media_paths.dart`, and it is one place for the same reason the names are: the *New project* dialog proposes a folder, the creator makes it, the manifest records it and the loader resolves it, and all four have to agree about what `../film-data` means. `splitPath` and `joinPath` take a path apart on either platform's separators; `isAbsolutePath` knows a drive letter, a UNC share and a leading slash; `mediaFolderResolvedFor` answers where a project's media root really is, and `mediaLocatorPathFor` what the manifest should record for a folder a person chose — **relative** where it sits under or beside the project folder and absolute where it does not; `isPortableMediaFolder` is the question the dialog asks so that it can say, while the person can still change it, that an absolute path is one only this machine can follow. Every one of them takes `required bool windows` rather than reading the machine it runs on: a dialog on one platform never types another's paths, and a check on either platform can ask about both.

### 5.11 The script's list — `filmopen_format/children.dart`

Project Specification 1.12 replaces the three story levels with **folders** (`fo`), and the four root lists with one list, **`children`**, on the project file and on a folder (§8.5, §10.1 of the format). This file is the rule in one place, pure Dart, and everything that reads or edits the script reads it. Nothing of 1.11's structure is read: `storyChildListKeys` and the three unit types are gone.

- **The entry grammar.** Folders and scenes mix in the list, so every entry carries its type. `ChildEntry.parse(text)` reads a **full reference** first (`sc_5_maria_v1`, through the filename grammar of §5.1), which **pins** that version (`pinned`, a `VersionStem`), and otherwise a **short stem** `<type>_<tag>`: what stands before the first `_` is the type when it is two lower-case letters (the format's §5.2 and §5.4), and what follows is taken as the tag, whatever it is — one that names nothing is an unresolved reference like any other, found when the reader looks it up. `childTypes` is `{folder, scene}`. `shortStem` (`sc_5`) names the folder or scene whatever version an entry pins, so two entries with one short stem list the same thing twice; `reference` is what `FilmProject.resolve` takes — the full stem of a pinned entry, else the tag. `ChildEntry.of(type, tag)` is the entry a writer adds: the short stem, which follows the version in use.
- **What is reported, never guessed** (`ChildProblem`): `childUntyped`, a bare tag (`"5"`) or anything else that names no type, an entry that is not a string among them (kept in its place, shown as the JSON writes it); `childWrongType`, an entry naming another type (`ch_kira`, a shot, a type the format does not know such as 1.11's `ep_e1`), with the prefix as its argument; `childDuplicate`, a second or later listing of one folder or scene. `storyChildren(json)` answers a file's entries in order and reports a second listing **within that list**; the walk of the whole script reports one in another list the same way, in the order it draws the rows (§5.12). An absent `children`, or a value that is not a list, is an empty script or folder, and 1.11's `seasons`, `episodes`, `sequences` and `scenes` mean nothing. The codes are said in `filmopen_l10n`, as every code is: `Labels.childProblemText(entry)` (`childProblemUntyped`, `childProblemWrongType` with the type the entry names, `childProblemDuplicate`), the reason a flagged row will carry. **The fourth thing the format's §8.5 has a reader report, a cycle, is not this file's**: one file cannot show that a folder lists itself through another, so it is the walk's (§5.12). An entry with a type and no name (`sc_`) needs no code either: it is read as written and is an unresolved reference when it is looked up.
- **The three edits** — `withChildAdded(json, entry, {index})`, `withChildRemoved(json, entry, {occurrence})`, `withChildMoved(json, entry, index, {occurrence})` — copy the document (`copyDocument`) and leave every other key, and every entry they were not asked about, alone. An entry is addressed **as it is written**, so a pinned entry moves pinned and `occurrence` chooses among equal entries — equal **as a reader shows them** (`ChildEntry.text`): an entry that is not a string (`5`, `null`, an object) is addressed by the JSON it is, so that a row and an edit count in one coordinate, a bad entry can be taken out of a list from the app, and of `5` and `"5"` the one that was pointed at goes; an index is clamped to the list, and in a move it is the place the entry has in the result. Adding a folder or scene the list already names — under either spelling — changes nothing, removing or moving an entry that is not there changes nothing, and a `children` of another shape is left for the JSON editor: the caller writes only what differs, and **nothing here deletes a file**.
- **The numbers an application gives what it creates** (the format's §17: a short name says nothing a person may change). `nextSceneTag(project)` is one more than the highest number any scene's short name is, whatever gaps there are, and `1` where none is a number; `nextFolderTag(project)` the same over the folders' short names of the shape `f<n>` (`folderTagPrefix`), the `f` keeping a folder's cues (`cu_f1.1`) from a scene's (`cu_1.1`). Both count over `takenChildTags(project, type)` — every short name a file of that type has, so a file in no list counts, **and every one a `children` list names**, in any version of the project file or of a folder, whether or not a file answers to it: an entry without its file may be a colleague's that has not arrived yet, and a new folder or scene under that short name would be taken for it. The dialog refuses such a short name as taken, and so does `addChild`. Both rest on `nextNumberedTag(tags, prefix:)`, which counts in `BigInt` — twenty digits are a valid segment — and proposes the lowest free number where one more would be longer than a segment may be, so the proposal is always a short name.
- **What a cue belongs to** (the format's §11.2). `cueOwnerOf(json, tag:)` answers a `CueOwner`: the folder its `folder` key names, else the scene its `scene` key names, else the scene of its own short name (`cu_5.1` → scene `5`), `isNamed` saying which; null where nothing names one and the tag has no dot. `folder` comes first where a file carries both, since the two say different things: `scene` whose block ids `blocks` are, `folder` where the cue hangs. 1.11's `unit` is not read.

`folderKinds` (`vocabulary.dart`) is the vocabulary a folder's `kind` is offered from (§10.1 of the format); a file may name another token, or none.

### 5.12 The script as one viewer sees it — `filmopen_format/script_outline.dart`

Every version of a folder has a `children` of its own, so what the script holds depends on which versions are in use for the viewer (§5.4). `scriptOutline(project, viewer:)` is **the one walk** of the script, which the tree, the Script page, a folder's contents and the move dialog read so that they agree: the project file's entries (`FilmProject.selectedProject`) depth-first, each folder's in its own order, as a `ScriptOutline` of `ScriptRow`s. A row is an entry **as written** (`entry`, a `ChildEntry`), the file whose list holds it (`listedIn`), its `index` there and its `occurrence` among equal entries — what §5.11's edits take — its `depth`, the `group` the entry names when the project has such a folder or scene, the `resolution` of looking it up (`FilmProject.resolve`, so a short stem is the version in use and a pinned entry that version alone), and, for a folder that resolved, its `children`.

- **What one file cannot show is reported here.** *A second listing* is decided in the order the rows are drawn — mark an entry, descend, take the next — so the later row on screen carries `childDuplicate`, in the same list or in another, and its first listing is clean. *A cycle* is an entry naming a folder above it (`isCycle`); it is the report where it is a second listing too, being the more exact. Neither is followed: a second listing's contents are under its first. Both compare **short stems**, so a folder is inside itself whichever version the entry pins.
- **A browsing read.** An entry is looked up for **the viewer**, whatever the status of the file that lists it, as the tree's references always were (§5.4): a fork is what its author sees in their script, under an official folder too. §6.1's other half — a file an official pointer names reads the official world — is for rendering a version's own references and for an export; such a reader passes `referencing: listedIn` to `resolve`, and `ScriptRow.listedIn` is there for it.
- **Never guessed.** An entry that names neither a folder nor a scene is a row with its `ChildProblem` and nothing else; one that names nothing is a row with the `ResolutionProblem`. Where the entry names a folder or scene the project has but no version can be chosen — several authors and nothing official, a pinned version that is not there — `group` is still set, so that a reader can reach its versions from the flagged row, and the folder's lists are not followed.
- **Not in the script** (`unfiled`; the format's §8.5). Every folder and scene of the project that no drawn list **names** — named, not resolved, so an entry that pins a missing version does not put its scene in both places — each once: first the folders no other unfiled folder names, each with what it holds beneath it, then the scenes still not drawn, then whatever is left, which only folders that name each other leave behind (the first is drawn and the walk's own cycle report does the rest). A project made before folders therefore shows an empty script and its scenes here. **While the reader has not chosen a project file** (§5.5: several authors, nothing official, no pick) there is no script for anything to be outside of: the outline is empty on both sides until the chooser is answered, rather than every scene being called unfiled. `rowOf(type, tag)` answers where a folder or scene is drawn: its first listing, in the script or beside it.
- `childRowsOf(project, parent, viewer:)` is one file's list alone — a version the script does not draw, such as another author's folder on its own page — with a second listing reported within that list and folders not followed.
- `cueGroupsOf(project, type, tag, viewer:)` answers the cues that belong to a folder or a scene (§5.11's `cueOwnerOf`, read from each cue's version in use, else its first), in natural order, so a cue that names a folder is never a scene's, whatever its own short name is. Where **no version of a cue is in use** none is chosen to speak for it: the cue belongs wherever any of its versions says, so it is shown — flagged, as every ambiguous reference is — in each of those places and hidden in none.

**A folder is, or holds, another.** `folderIsOrHolds(project, moved, destination, viewer:)` answers whether the folder an entry names is the folder `destination` or holds it at any depth — read as the walk reads, each entry resolved for the viewer and a pinned one at the version it pins, wherever or whether the script draws the folder; a cycle the files already hold ends the search rather than turning for ever; a scene, an entry that names nothing and a folder no file has hold nothing. It is the rule a move asks before it writes (§7): a folder cannot go into itself or into a folder beneath it.

### 5.13 A scene's cast — `filmopen_format/scene_cast.dart`

A scene lists its characters in `cast`, one object each: `{ character, epoch?, outfit?, notes? }` (Project Specification §10.2, A.5 — one selection per character, the entry's own `epoch` being the character's where it differs from the scene's). `castOf(json)` answers the entries as copies all the way down (`deepCopy`: a nested value is never the file's own object), an absent key being an empty cast, and **null where the value is not that** — not a list, a bare short name, an entry that names no character — which the form shows as it is and never writes over (never guess). The edits are pure and return a new list: `castWithAdded` (the name alone, at the end, once), `castWithoutAt`, `castWithEpochAt` (the entry's own epoch, or no key for *as the scene*), and `castWithCharacters(cast, names)`, what an agent's typing means — the names in their order, **an entry that stays keeping everything it holds** (its `epoch`, its `outfit`, its `notes`, any key this reader does not know), the k-th time a name is given taking the k-th entry of that character so that typing back what a file says changes nothing, a new entry being the name alone and never a second one for a character. `writeCast` writes the list, or removes the key where it is empty. Pure Dart, tested in `test/scene_cast_test.dart`.

### 5.14 The address of a server — `filmopen_format/server_address.dart`

`ServerAddress` is the one grammar of a `server` setting's value (§6.11, Project Specification §14.4) — one implementation the manifest reader, the door and the box all read, so that no two of them can disagree. `parse` answers an address or null: `http` or `https`, a host, an optional port and an optional base path, with no user info, no query and no fragment; the text is trimmed, the scheme and host lower-cased, the scheme's own port and a trailing `/` left off, so one server is one value (`==` and `hashCode` are over that text). `Uri.parse` removes dot segments as RFC 3986 §5.2.4 says, so a base path can name nothing above the address. `isThisComputer` is `127/8`, `::1` and `localhost` with the names under it; `isPrivate` adds `10/8`, `172.16/12`, `192.168/16`, `169.254/16`, `100.64/10` (where Tailscale lives), `fc00::/7` and `fe80::/10` — **and any host name, since what it resolves to cannot be known here**, so step 3's warning is only ever for an address that is certainly a public IP address. An IPv4-mapped IPv6 address (`::ffff:10.0.0.5`) is read as the IPv4 address it names, and a rooting dot is not part of a name, so `localhost.` is this computer. `resolve(path)` joins a route to the base path and keeps the query the plug-in wrote, and answers null for anything that could leave the address — a path that is itself an address, one starting `//`, any `.` or `..` segment (`%2e%2e` among them), a percent-escape that is not two hexadecimal digits (a sign or a space is not one, so `100% final.png` is refused rather than sent as another route), an escape whose bytes are not UTF-8, a control character, and an empty or trailing-empty segment; a fragment is dropped, never sent. **A segment is read as a server that decodes before it removes dot segments would read it** — what RFC 3986 §6.2.2.2 warns against and several real stacks do — so `..%2F..` is refused exactly as `/../../` is, while `a%2Fb`, neither of whose parts is a dot segment, is a name and passes. **Every segment is escaped exactly once**: the address keeps its path decoded and lets `Uri` write it, and a route's escapes are read back one at a time — the text between them kept as a run, so a character above the basic plane survives — before it is written again, so a base path of `/My%20Comfy` is sent as `/My%20Comfy` and not as `/My%2520Comfy`, and `/ver/año%20x.png` keeps both halves. **`parse` answers an address or null and never throws**, whatever a person types or a manifest ships. `sameOrigin` compares scheme, host and port, a scheme's own port counting as none, and is what a redirect may stay within. `origin` puts an IPv6 literal's brackets back, which `Uri.host` takes off. Pure Dart, tested in `test/server_address_test.dart`.

### 5.15 Which film this is — `filmopen_format/project_key.dart`

`projectKeyOf(FilmProject)` and `projectSourceKey(ProjectSource)` answer **one token per film**, so that work begun in one film can never end in another: a run of a plug-in is bound to its film by this key (§6.11), and the jobs' journal binds a job to it. Two `FilmProject`s cannot be compared for the purpose — every load builds a new index, `forViewer` builds another and a re-read a third, all of one film — so the key is the film's **source**. A source with a `rootPath` answers `folder:<canonical path>`; one without, or one whose path is empty or only spaces, answers `session:<n>`, taken once and kept for as long as that source object lives (an `Expando`, so a source no longer held is forgotten with its token). Two folders holding the same film are two films; one folder opened twice, or re-read, is one, since `ProjectController.refresh` re-reads the same source and a second *Open folder…* makes a new `DirectoryProjectSource` of the same path. A project that lives only in memory — the bundled sample's session copy, a test's fixture, a session-only project where there is no disk — is itself and nothing else.

**This is the one project key**: `projectSourceKeyProvider` (§7.1), which the browser resets its navigation on, answers `projectKeyOf` and has no rule of its own. It used to say `<runtimeType>:<rootPath ?? label>`, which disagreed in both directions — two session copies of the sample were one source, both being a `MemoryProjectSource` of one label, so the browser kept a selection pointing into the copy that was closed; and one folder spelled two ways was two sources, so a re-read under the other spelling reset the navigation.

**A `session:` key is of this isolate and this run of the application**: the counter is library-private and starts again at 0 in every isolate, so such a key may never be written to a file and read back after a restart — two different films would meet under one token. A `folder:` key is text derived from the path, and may be. `canonicalRootPath` is text and never a question put to a disk, the format knowing no `dart:io`: separators become `/`, a run of them becomes one except a leading `//` (a Windows share's root), and a trailing one is dropped from anything longer than a root. That is all — **case is kept**, and a link, a `subst` drive and an extended-length prefix are not resolved. Only what is certainly one folder is joined: folding a drive's or a share's case would join `C:\Films` with `c:\films`, which NTFS does not tell apart, but it would also join two real folders on a share exported from a case-sensitive file system or in a Windows directory marked case sensitive, and the two errors do not cost the same. A false **split** costs a run begun under one spelling not seeing an index re-read under the other — and, where the film changed on disk meanwhile, a refusal in place of a write, since every version goes out with `create: true` and a number already taken takes the whole run with it (`project_writer.dart`). That is the safe direction, and the same thing binding does for a film that was closed. It also counts one folder as two films anywhere something is kept per film — the recents list, the jobs' journal. A false **join** makes a run treat a stranger film's index as its own, which is what the key exists to prevent. `isDurableProjectKey` says which keys may be written down; `folderNameOf` is the **one rule for a folder's own name** — the last segment, either separator ending one — which `DirectoryProjectSource.label` (§6.2) and `DevelopmentFolder.label` (§9.4a) both read rather than each splitting a path of its own. Pure Dart, tested in `test/project_key_test.dart`, on the real folder source in `filmopen_store/test/directory_source_test.dart` and on the provider in `filmopen_state/test/project_provider_test.dart`.
