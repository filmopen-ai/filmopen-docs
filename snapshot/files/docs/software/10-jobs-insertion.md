# Jobs, and bringing media in

A piece of work that outlives the page that asked for it, and the one way media enters a film.

### 6.12 Jobs — `filmopen_jobs`

**A long piece of work is the application's, not a screen's**. Before this package an upload was a `Future` a form's reference strip held and a `bool _busy` beside it, so leaving the page took the only thing that knew the upload existed (and). A **job** is instead a record with an identity, a phase and a place, kept where a closed window cannot take it.

`filmopen_jobs` is the bottom of the graph and the one package whose `dependencies:` block is empty: it knows nothing of films, plug-ins, stores or widgets, and a test reads its pubspec and every import and fails on either (`boundary_test.dart`).

- **`JobRecord`** holds the `id`, the `kind`, the `seq` it was asked in, when it was made, the film's key (`filmopen_format`'s `projectKeyOf`), the place, the `phase` and this package's finer `stateCode` with its `stateArgs`, the attempts, the earliest retry (`notBefore`), the last `JobFailure` — a code and the stage — and a **`payload` that belongs to whoever made the job and that this package never reads**. Keys a newer build wrote travel through a round trip untouched, and never stand in for a key this build owns. There is **no progress in a record**: a percentage changes with every chunk, and a journal written per chunk is a write per chunk (§6.6); progress is live and belongs to the scheduler.
- **`JobPhase`** is the seven words a screen may be told — queued, working, waiting, needs attention, done, failed, cancelled. A phase a build does not know reads back as *needs attention*, never as one that runs.
- **`checkJobPayload`** is a **tripwire against a mistake of this application's own**, not a wall against an adversary: every payload is written by FilmOpen's code, so the check is judged by whether it catches the names that code would really use and lets through the names that code really needs. At the journal's one door and before anything is written it refuses: a key **any run of whose neighbouring words**, joined, is one of `_secretNames` — `apiKey`, `openaiApiKey`, `x-api-key` and `apiKey2` all hold `apikey`, and `sessionId` holds `sessionid`; a key whose **last** word is `key`, `keys`, `token` or `tokens` **and whose value holds text**, which is what tells `falKey: 'r8_…'` from `maxTokens: 1200` and `keyFrames: [0, 12, 24]` — words that only qualify (`tokenHeader`, `keyValue`, `tokenBase64`) coming off first, so those are the credential while `keyArt` and `keySignature` are not; a value that begins the way a credential does, whatever its case; **any `http` or `https` address anywhere in a value**; and a value **no JSON can hold** — a `DateTime` or an object of the caller's own, a non-finite `double`, a map keyed by anything but text, a payload that holds itself — as `unwritable`, so that the question `jobPayloadProblem` answers is the question `put` will act on. The keys a newer build wrote are held to the same rule when they travel out again, since `fromJson` keeps them and `toJson` writes them back verbatim, and so are the **state's args**, which are a runner's free text — *uploading from X* wants somewhere to put X, and a presigned address carries its signature in its query, one field away from what the address rule refuses in a payload; being `Map<String, String>`, only the name and address rules can ever bite one, so a code and a lane name pass untouched. A value of a class of the caller's own is refused **not because `jsonEncode` would throw** — its default `toEncodable` calls `toJson` — but because the walk cannot see inside it, so a credential in a field of such an object would pass every rule here; the cost is that a job carrying one is a job of this session. A name is cut into words at `-`, `_`, `.`, a space, every change to a capital and every change between letters and digits. Three narrower rules were tried and each failed the other way: a **substring** check refuses `author`, `keyframes` and `monkey`; a **whole name** lets twenty-three real credentials through, `secretKey` and `authToken` among them; **single words** refuse `maxTokens`, `keyFrames` and `keySignature`, the ordinary vocabulary of the very jobs this is for. What this rule costs is six names a payload may not use while their value is text — `projectKey` and `placeKey`, which are `JobRecord`'s own fields, and `idempotencyKey`, `cacheKey`, `sortKey` and `groupKey` — and a token count that arrives as text (`maxTokens: '1200'`), since the value is exactly what tells a count from a credential. What it knowingly misses is a name whose only signal is `signature`, because `keySignature` is a piece of music, and the cryptographic furniture that is not itself a secret (`hmac`, `salt`, `nonce`); a presigned address's signature arrives inside the address, which the address rule refuses anyway. A **path on this computer is allowed** — it is what lets a copy the window was closed on be taken up again — and reaches no project file and no log line, though it may reach a `JobView` as its `previewPath`. **The plan's third prohibition, *no name a person typed*, is deliberately not enforced**: a job exists to carry what a person asked for, and what the clause protects against — a credential typed in, an address typed in — is refused already. One consequence for a runner's author: a model's whole catalogue entry carries documentation links (§14.6–§14.9 of the Project Specification), so passing one makes the job unjournalable and a job of this session alone; pass the model's id.
- **The journal** is one file per job, `<id>.job.json`, in a folder the caller names — `filmopen_platform`'s `jobsDirectory` in the application, beside the others of §6.4. A write goes to a sibling **marked as that writer's own** and is **renamed** over the target, as `DirectoryProjectSource.writeText` writes a project file, so a build that stops in the middle leaves the old file or the new one. Writes are serialised within a build; across two builds it is the mark that keeps them apart — two builds sharing a sibling name put one's bytes in the other's file and the record came back neither the old one nor the new one. Two builds renaming over one target is a **sharing violation** on Windows and not a corruption, so the rename is tried a few times over a few milliseconds rather than losing the write. Nothing is deleted once the rename has happened, so a writer never takes its own next sibling out from under itself; `sweepTemporary`, called by `load`, clears siblings whose stamp is more than an hour from now **in either direction** — a clock set forward, or a folder restored from a backup, leaves one in the future, and a plain difference made such a sibling immortal — and never a fresh one, so what a killed build left does not pile up. **Tidying is never the answer**: a sweep that could not run leaves work for the next load and does not fail one. **One unreadable file costs one file**: two builds share this folder, so a read can meet a file the other is renaming over, and such a file is answered among the unknown as `unreadable` while every other job still loads — where a folder that cannot be **listed** is not pretended to be an empty one, and the failure goes to the caller. **The rename is not a copy** — a copy truncates the target. A naive copy is caught behaviourally, since it leaves the sibling behind; one that cleans up after itself is not, and telling that apart from outside needs a crash or an inode, so the rename is also pinned by a test that reads the source. **A file of a schema this build does not know is kept**, answered once as `schema`, and never deleted: a person who opens an older build for an afternoon must not lose what the newer one left; a file this build's own schema that will not parse is answered as `unreadable`, since the two want different words. `MemoryJournal` serves the web, the tests, and every job of a film whose key is not durable (5-2c's).
- **`JobLease`** decides which of two running builds works the jobs, since every build on a machine shares the application's folders: a token and the instant it was renewed, stale when that instant is more than thirty seconds from now **in either direction** — so a clock set forward once does not wedge it — taken over by `acquire` and never by `renew`. **Taking it over means asking**: a build that finds it held asks again at the next thing it is asked to do, since nothing else would ever run its jobs — the other build reads another's records only when **it** opens a film. And **a renewal that finds the lease gone says so**, so that whoever holds bytes in flight can stop them between files: without that, the build taking over requeued the record it found *working*, chose an id of its own, and uploaded beside the first build's copy. **A holder's own lease expires by itself**: `held` is read as the span since the last write and not as the last answer a take gave, so a build that stops renewing — paused under a debugger, a timer its caller forgot to start, a long stall — stops working jobs whether or not anything tells it, which is what the build that finds the lease stale and takes it over is entitled to assume. That span too is disbelieved in either direction. Three things follow, and each closes a way the lease could be held by two builds at once. **`acquire` and `renew` answer the same question `held` does**, not the take's own success: a write and a read-back that together outlast `stale` land a lease already lapsed, and `if (await acquire) work;` would work a job another build had taken over. **A holder whose own span has lapsed may not renew**: renewing writes without reading how old the other holder's stamp is, on the ground that this build already holds the lease, and once that ground can be gone a stalled renew would stamp itself over a newer holder and give both builds the lease for the difference — a lapsed holder goes through `acquire`, which reads the other's age. And **`startRenewing` keeps it**, on this clock, a third of `stale` at a time, stopping the moment a renewal finds the lease gone: `held` expiring by itself with nothing renewing it would have a build that acquired once at start work no job thirty seconds later, silently and for ever, which is worse than what it cured. Every write is **read back**, so two builds that both write before either reads end with one holder. **Could not look is not free**: a read that throws leaves the holder's lease alone and this build waits, where answering *there is no lease* would have it write over the real holder and stop the queue altogether. It does not promise that two operating-system processes can never both believe they hold it for one renewal — closing that needs an exclusive create `dart:io` does not offer — and what it buys is that two builds do not work one job for long (review §8.2: durable intent, not exactly-once).
- **`JobView`** is **everything a widget is ever given of a job**, which is the condition for keeping *pending* in a journal at all: the id, the kind (which picks an icon and nothing else), the phase, the package's own finer `stateCode` with its `stateArgs`, the progress where something measured it, the actions that may be pressed, the place it belongs to, and — where the job's own kind can say — the reference it became, a picture on this computer and a name. A widget draws the phase as a mark, turns the code into a sentence through `labels.dart` (falling back to the phase's own for a code it has never seen), draws one button per action and sends it back; **it never asks why**. `JobAction` is a **code and not an enum**, so that a later `resumeAnyway` can be added inside `filmopen_insertion` with two sentences in `filmopen_l10n` and **no widget changes**. `JobViewParts` is what only a runner knows, since this package never reads a payload.
- **`JobScheduler`** runs them: **lanes** whose capacity is **data** — a lane is a platform and the server or account behind it, never a plug-in — order by `seq` whatever order jobs end in, a **hold** on a lane with the code that says why and the actions that lift it, a **retry** whose time is in the record so that a restart honours it, **cancellation as an intent** the runner honours rather than a thread that is killed, and a **control road** that takes no slot, joins no queue and waits on no capacity, so a person can stop a job while every lane is full. A job whose `kind` has no runner in this build is shown as needing attention and **never dropped**; one found *working* at a restart was left by a build that stopped and is queued again, saying so; a journal that cannot be written never stops the queue. `stop`, `pause` and `dismiss` are decided here and **every other action** — `resume` and `retry` among them — queues the job again with its code under `stateArgs['acted']`, **beside whatever the runner itself wrote there**, since that is a runner's only durable channel and *attach again* needs the take a refused attach recorded. **Only what the view offered may be pressed**: §4.1 makes the actions the contract, so `act` refuses one the view does not carry — without which a tap on the frame drawn a moment before an upload finished ran the finished job again — and `dismiss` is the one exception, always allowed, since it stops the work. A **hold says what lifts it, and reaches the bytes already moving**: a runner is handed the record alone and cannot know its lane is held, so `holdLane` takes the code, the arguments its sentence needs and the actions that lift it, and the view carries those beside the runner's own — which is the overview's §4.1 worked example, `heldMetered` and *Resume anyway*, with no widget change. A job of that lane already working is asked to **pause**, since the first case is *stop an upload because the phone is roaming* and the upload in flight is the one spending the data; **a hold's pause ends with the hold, whenever the job notices** — the lane is asked as the job answers, so one still winding down when the lane is let go goes on by itself rather than waiting under a code nothing answers for, and where another hold has arrived by then it waits under that one — while a job a **person** paused waits for their *Resume* — and **a person's pause carries no lane's mark**, `heldLane` being this package's own key for *a hold paused this*: left on a record a person then paused, it had both requeue roads run a job waiting for its person. **A press a person makes is theirs, in either order**: a hold never writes over one made first, and one made under an existing hold takes the job back from it — either way round, a hold that took a person's press over brought the job back when the lane was let go, which is a second upload and, with an ingest runner, a second render, paid for. A job a **hold** paused records **which lane** held it, so the next start takes it up where that lane is no longer held, while a person's pause waits for their *Resume* this run and the next. A **dismissal is remembered until the file is really gone**, since a `remove` meets the same locked file a write does and the record a runner leaves behind still says *working*; `restore` retries the removal before it reads the folder. **A lane holds a set of reasons**, released one at a time by the code that named it, running again only when none remains, and showing a screen the **first that remains**. Two packages will hold one lane — 5-2f's metered connection beside 5-2g's provider limits — and with one hold per lane the second saying threw the first reason away and the one release that came ran everything the first reason existed to stop. The same code said twice is one reason, replaced in its place, since a watcher that says *still metered* on every poll must not need as many releases as it made polls; and a press lifts the reasons that **named that action** and no others. What takes a hold-paused job up again is the **lane** being free and not the code it happens to carry, since with reasons in turn no one code is true from the pause to the release. **Letting a lane go tells the screens** even where it requeued nothing, since the hold was masking every job of the lane and a tile left with a button `act` now refuses is one a person cannot get past. **Every view carries `dismiss`**, whatever its runner offers, so that a job is never a dead end and the rule that only what the view offered may be pressed needs no exception. **Nor is a change that is still on its way to disk**: every write puts the record in memory and then suspends in the journal's `put`, and for that span the job is right in memory and behind on disk with nothing marking it — so a film opening while a person presses *Stop* on a queued job had `restore`'s load, taken before the write, come back with the record still *queued*, write it over the *cancelled* one and start the job the person stopped. It is the same case as the one below by another name, and skipped the same way; the mark is a count, since two writes of one job can overlap. **A dismissal is skipped by all three of `restore`'s loops**, the one that takes up a hold's pause included — without which a job dismissed while a hold had it waiting, whose file the journal would not remove, was read back, queued and run at the next film open. **A value the journal refuses does not stay in memory**: `remember` checks the merged payload and then writes it, and the journal has a gate of its own — it holds the state's args to the same rule — so one it refuses is refused for ever, and a value left in the record made every later write of that job throw, the outcome's among them. **And an outcome it refuses does not take the scheduler with it**: a runner may answer with args of its own, and unguarded such a write escaped as an unhandled asynchronous error, leaving the job saying *working* with nothing running it; it is told as `outcomeUnwritable` with the gate's own code and nothing of the outcome in it. A write that merely **failed** is another matter and is the mark below's. **A change the journal refused is not undone by a restore**, by either road it takes, which runs at every film open and would otherwise be D35 running backwards; the mark clears the moment a write of that job lands. **The stream is silent for a list that did not change**, since a `List`'s own `==` is identity and the comparison belongs where the views are made. **A cancellation that is only the scheduler going away is not an outcome**: `dispose` asks every running job to stop, and a runner that honours cancellation between steps — which is what one is asked to do — answers `JobCancelled`, which written as *cancelled* is finished, and the next start requeues only what it finds *working*. A person who closed the window during a large upload was told at the next opening that somebody had stopped it, and nothing ever took it up. The file is left saying *working*, which is what a build that was killed leaves and what `restore` is for; re-running a job that had in fact finished costs nothing, the ingest being replayable and an insert neither repeating nor moving a reference. **A person's own press is theirs**, though: `dispose` leaves the same flags a press does, so the press is marked where it is made, and a *Stop* or a *Pause* answered one whole file later — which on a large upload is minutes — is written as they asked rather than discarded. And only a **cancellation** is read this way: a job that finished, failed or asked for a retry while the window was closing is answering for itself, and is written with its `notBefore`. **Nothing counts a retry down**: `attempts` is written on every start and handed to the runner, and the runner decides when to stop asking. Two views of a job that did not change are **equal**, so a screen need not rebuild every tile for every chunk of a long upload.
- **The producer contract** — `Producer`, `ProducerRun`, `ProducedItem`, `ProducedText` — is defined here so that `filmopen_render` and `filmopen_insertion` can meet **without either importing the other** (its §5: the render manager needs no project and knows no insertion). An item is opened as a **stream the producer itself gives**, never an address to fetch, so that an output handed on stays an authorized, opaque source (the).
- **`JobControl.remember`** writes into the job's **own payload**, now, so that a later attempt — after a retry, after a restart — reads what this one decided. It exists because **`stateArgs` is the args of a *state* and every outcome replaces them**, while what a job chose **once** has to outlive the attempt that chose it: the ingest picks its batch id before a byte is written, and an attempt that chose again would make a second take of every file (§6.13). Merged over the payload, never replacing it, and held to `checkJobPayload` exactly as `submit` is — a credential's name or an address is refused here too. **It answers whether the value really landed on disk**: a journal that could not be written leaves the job right in memory and behind on disk on purpose, which is right for a phase and wrong for the one value the next attempt has to reuse, so a caller for whom that matters — the ingest, whose rule is that a name chosen once is written down before a byte moves — does not move the bytes.
- **`Clock`** is what the package asks of time: `now` and `after`. `SystemClock` in a build, `ManualClock` in a test — which is in `lib/`, not a test folder, because three suites drive the same clock and a clock copied three times is three clocks that can disagree. `ManualClock.advance` runs a due callback **inside the call**, where a real `Timer` runs it in a later turn of the event loop; a test asserting on an `async` callback's effect must therefore await a turn first.

### 6.13 Bringing media in — `filmopen_insertion`

**What puts media into a film**, cut out of `filmopen_media` so that the insertion service and the jobs can reach it without reaching a widget, and so that the two halves are named for what each does: `filmopen_media` is where bytes live and how they are read, and this is how they get there. Pure Dart, with `dart:io` (`local_file*.dart`) and `dart:isolate` (`off_thread*.dart`) behind `_io` / `_stub` pairs, so it runs on the web and in a command-line tool as well as in the app; it holds no Flutter, no plug-in and no sentence a person reads — refusals are codes. Nothing moved but its home: the importer's and the thumbnailer's tests moved with them, unchanged.

**What a piece of work is aimed at** is an `InsertionTarget`: the film by its **key** (§5.15), the file by its version stem, a `TargetPlace` — `SlotPlace(slot, first:)` for references (§9.0), **`ByKindPlace` for the place each reference's own kind names**, `ValuePlace(path)` for a text, `TakesOnly` for work that writes nothing into the file — the kinds it will take, and a plain `purpose`. It is **bound when the work is asked for** and never read again from the running application, which is `RunBinding`'s rule (§6.11) applied to a job. Its `placeKey` — the film, the file and the place, and nothing else — is what an element on screen asks its jobs by: two jobs aimed at one strip share it, and two files of one film do not. It goes into the journal, and **anything this build cannot read comes back null**: a place a newer build wrote, a kind this one lacks, a malformed path. Such a job is held as *needs attention* and never run against a guess (§6.12). The film's key is written under **`film`** and not `projectKey`, because the journal's own tripwire refuses a key whose last word is `key` when its value holds text — the rule working, and the cost it was accepted at.

**Where the bytes come from** is an `InsertionSource`: `FilesSource`, `BytesSource`, `AddressSource` or `ProducerSource(kind, request)`. Each says whether it **survives a restart**, and two do not: bytes are in memory and nowhere else, so a record of them is a record nothing could satisfy; and an address the journal refuses outright, since it may carry a token in its query and a journal outlives the moment. Such a job is a **job of this session** — it runs and is shown, and it is gone if the application stops — as is any job of a film whose key is a `session:` one. An address never says what it is, not even to a log.

**`InsertionService`** is what a screen asks. `insert(target, source)` fixes everything the work is of and answers the job's id; `jobsFor(placeKey)` and `changes` are what an element draws from; `act` is a person's press; `restore(projectKey)` takes up the jobs of a film that has just been opened (is never called at start — §3.5): the journal's, through the scheduler, **and the ones already in memory that answered `projectNotOpen`** — such a job is `waiting` with no retry time, so nothing pumps it and no timer is coming, and without this the reference sat in a job that would never run again. It wakes **that film's**, and only those waiting for a film: a person's *Pause* waits for their *Resume* and is no business of a film being opened. It is reached as `InsertionService.current`, with a no-op default whose environment has no film and no disk, so a screen built without an application behind it still draws and nothing is written. Its runner puts a job in a **lane** by where the limit really is: the local root is one lane, and a producer's is its own name. **The root is asked about before a name is chosen**: choosing reads the store, so a film whose remote root has no client in this build — what every contributor without keys builds — would otherwise throw out of the run as the scheduler's *threw*, a job a person is shown with no code anything can act on, where `rootUnavailable` has been the right word all along. A store's **own** word is carried out from that call as it is from the copy: the same `busy` reaches both, and answering *the root could not be reached* for one of them said the wrong thing and said it terminally.

The person is **bound at `insert` with the film and the place** and written into the payload as a handle: a handle typed while a job waited for a lane would otherwise name the takes after whoever is at the keyboard and write the reference into their file. A **stop** the person asks for reaches the copy **between files** (5-2c's) and the job ends *cancelled*, what the action wrote coming back out with it; a runner says what may be pressed in each phase, since a widget can press nothing the view does not name. A failure inside the ingest is logged **by its kind and never by its words**, an `http` exception carrying the whole address and its query.

**The place a reference goes may be its own kind's** (`ByKindPlace`). The reference card has always routed by kind — a picture to the file's own array, a clip to `refs.motion`, a **character's** sound to `voice.refs`, and the first picture proposed as the file's `preview` where it has none (§9.0's `slotFor`) — and a job cannot name one slot when it is asked for: one selection may hold three kinds, and the kind is not known until the ingest has settled it. So the place is resolved **at the attach**, from what each reference turned out to be, with the kinds written down beside the references so that a later attempt reaches the same places without asking the store again. **One write per slot**, in the order the kinds first appear, since a selection of three pictures is one block in one place (§9.0) and three writes would be three re-reads. The entity's **type** is part of the rule and is read from the target's stem, a stem carrying its type (§5.4). The read-back is `referencesIn` **on the place written to** and never `referencesOf`, which spans every place a file names: a reference already somewhere else would otherwise read as one this write had made.

***Done* means the file names the reference, and a refused attach is attached again for nothing**. The references an ingest made are written into the job's own payload the moment the ingest finishes, so every later attempt of that job — a person's *Attach again*, a retry, a requeue after a restart, a film opened again — goes straight to the file **without touching the store at all**: not a second `put`, and not a second read either, which on a remote root would be every file downloaded again to be measured. *Attach again* is offered only where the payload holds references **and** the last failure was raised while attaching, since a button that quietly redid the whole upload would be worse than none. A place whose **shape** the format will not write into — `refs` holding a string — is said as `placeUnwritable` rather than as *changed meanwhile*: the insert leaves such a value alone, so the door takes its *changed nothing* road and answers the word for a race that did not happen, while the take is safe in the store and what a person does next is change the shape. The probe that tells them apart is **two** flags the change closure sets, read after it has run, so the closure stays a pure function of what it is handed (§7): one says it ran at all, because the door answers *changed meanwhile* on a road where it never calls the closure — the file gone between the runner's own check and the door's re-read — and a single flag sent a person to the JSON editor to change the shape of a file that is no longer there. They are consulted **only** where the door said *changed meanwhile*, every other refusal being the writer's own. **And the references are read before the source**, since a job whose bytes were only ever in memory has none after a restart and would otherwise be stranded although it needs nothing but a write.

**A failure that keeps happening is given to a person** (open item). `JobScheduler` counts nothing down on a runner's behalf and is right not to (§6.12): only a runner knows whether a provider's *busy* is worth a tenth try. This runner counts **consecutive automatic retries**, in its payload, and past eight answers *needs attention* with how many it tried. Not `JobRecord.attempts`, which is +1 on every start — a restart's requeue and a person's press among them — so bounding it would end a job because the window had been closed eight times; and **any press begins the count again**, a person asking again being a new beginning. Nothing is undone at the bound: each attempt took back what it wrote, and a take an earlier one landed is found again by its name and its hash.

**What a producer makes**. A `ProducerSource` names a kind and carries a request; `InsertionService.registerProducer` says what runs that kind, and a kind this build has no producer for is shown as needing attention and **never dropped**, exactly as a job kind with no runner is. The run's `toJson` is written down **before anything is waited for**, so that the next start asks `Producer.restore` rather than beginning again — and a `restore` that answers null is a provider that cannot say whether a paid submission was accepted, which is `producerGone` and a person's to settle (review §8.2). Its outputs arrive as **streams the producer itself opens**, one at a time as the import reaches each, never an address to fetch; an output whose name carries no extension — a render comes back as `output` with `image/png` — is named from its **type**, while the original name is untouched and is what the batch record keeps. **A producer's items are kept, each with its own outcome**: an upload's failure half-way takes back everything the action wrote, because the person has only to choose the files again, but a render is paid for and its outputs expire, so one output that will not copy takes back **its own** writes and no others — **whatever kind of failure it was**, a store's own refusal and a stream that errors included, the store's word travelling on as the code — and the job ends *needs attention* saying how many of how many are missing and what each said — each code put through the payload's own gate first, since it is the one caller-supplied word there and reaches the state's args as well. What a producer **recorded** of an output goes into the batch item **before** everything the import measured, so that nothing it says writes over a hash, a size or a path the ingest took itself (§12.2). That count goes **into the payload** beside the references, because every later attempt goes straight to the attach and would otherwise end *done* one take short. A run that made **nothing at all** is a failure of its own, which the producer contract says in as many words. A **stop** is not a failure and is read outside that guard: the person who pressed it did not press it once per output. It is also heard **while the producer is silent**, on this package's own clock, since a render queued behind somebody else's may say nothing for minutes; the subscription is then abandoned rather than awaited, a cancel on a generator suspended on a provider that never answers being the very hang a stop exists to end. Once the references are written down the run is **acknowledged**, and the producer may let go of what it was holding.

**A text is a proposal** (step 6b). A `ValuePlace` job keeps the **hash** of what its place held when the job was asked for — a hash and not the value, since a synopsis may hold an address, which the journal refuses outright, and may be pages long in a file written on every change of a job. If the place holds something else when the text arrives, **nothing is replaced**: the job ends *needs attention* as `valueChanged`, the proposal kept, and the person is offered *replace anyway* beside the *dismiss* every view carries. The proposal is written into the payload only where the payload's own rule takes it; one holding an address lives in this run alone, and a later start says `proposalGone` rather than pretending to have it. The write goes through §7's door with `reseed`, so the text reaches the box a person is looking at as a copy-left does — and only where `canWritePath` allows it, since `setPath` states that as its precondition and a release build would otherwise replace whatever stood in the way with an empty object, destroying what the person had written where `holds` could not see it. **A proposal already in hand is never made again**: the producer is asked only where there is none, so *replace anyway* writes the text the person read and not whatever the model would say now. *Absent* and *empty* do not hash alike, this application deleting a key by emptying it. Proven against a stand-in producer; no feature uses it, and the Project Specification's §14.4 is untouched.

**Bringing it to the running application** is `filmopen_state`'s `insertionServiceProvider`: **a provider and not a static**, unlike the seams whose implementations live in packages the state may not import (§7.1). `InsertionService` is a concrete class in a package the state *may* import, so it is derived state like the media store's — every container has a working one, a widget test that pumps the whole app gets an in-memory journal without arranging anything, and the container is what disposes it. `ContainerInsertionEnvironment` answers the interface from the providers, every answer a `read` and never a `watch`, since a job may have begun before the page that asked for it and may outlive the film that was open; `openProjectKey` and `project` answer **null while the film is closed**, though the index is still there (§9.5's *Close project*), or a job would ingest into a film the person has shut. `jobViewsProvider(placeKey)` is what a screen watches, and gives the list as it is **now** before anything changes, so a person coming back to a page sees the job that is already running.

**A film's jobs are written where that film's jobs belong**: `FilmJournal` routes by `isDurableProjectKey`, so a `folder:` film's jobs go to the folder beside the log (§6.4's `jobsDirectory`) and a `session:` film's to memory. Without it a session copy of the sample wrote records naming a key that means **something else at the next start**: two copies open in one run make `session:1` and `session:2`, and the next run's second copy is `session:2` again — so `restore` took the record up and the attach wrote a reference to a take that copy's store had never held.

**The jobs of a film are taken up when it is opened, never at start** (§3.5): at the one place every road to an open comes through, after the load succeeds — not at start, where there is no film for a job to be of and a folder listing would be waited on for nothing; not on a re-read, a viewer change or a close. It **never fails an open**: a journal whose folder cannot be listed throws, and a person who asked for a film is owed the film. The **lease** is taken lazily, at the first thing the service is asked to do, so that nothing in `main` waits on a file and a build that inserts nothing never holds it; a *done* job is forgotten a day later, swept at the same moment. When the window closes the service is given **eight seconds** to finish what is moving, as an open draft is given ten (§9.5) — asked to finish and never to stop, since a cancellation between files undoes what this attempt wrote while a build that is simply killed leaves the record saying *working* for the next start.

**`InsertionEnvironment`** is the one door from this package to the running application, implemented over the providers by `filmopen_state` and in memory by a test. It answers **codes and never the state's own exceptions** — `writeProblemCode`'s words (§7) — because a job keeps a `stateCode` in a journal that outlives the run, and a sentence in a journal would be in whatever language the person had chosen that day. Its `patchEntity` is §7's door, so a reference reaches a file through the draft a form has open on it when one has, and through the writer otherwise.

**The ingest is replayable** (rule 2). `MediaImporter.chooseBatchId` is called **before a byte is written** and the answer is remembered in the job's payload (`JobControl.remember`, §6.12), so that an attempt cut short and asked again writes the *same* names and makes no second take. A take found under its name whose length and hash measure the same is this work's own and counts as written; one that differs, or that cannot be read back, is `nameTaken`, as it has always been — and a take that **cannot be read back** says so by the kind of the failure and never by its words, a remote root's client exception carrying the whole address and its query and a local one's the person's own path. **The batch record is recognised the same way**: `writeImportBatch` creates, so a replay's second write is refused because the file is there, and a refusal is an error with a stack trace for an entirely expected event — a batch of this id **and this author** already in the index is this work's own and is handed back, while another author's of the same id is not, since the id is only ever chosen clear of *this* author's. A take an **earlier** attempt landed is not taken back by a later attempt's failure: `_undo` removes what *this* attempt wrote and no more.

**Choosing the id is serialised per file, and the ids to avoid are seeded from the journal.** `chooseBatchId` derives what is taken from the index and from the store, so two jobs of one entity choosing against the same index get the **same** id, and the second meets the first's files under its own names and is refused `nameTaken` — a refusal the person did nothing to earn. Nothing but the default capacity of one kept that from happening, and `setCapacity` is public. So the choice and the `remember` that writes it down happen inside one turn of a queue kept by film and stem (`patchEntity`'s shape, §7), and before choosing, every batch id in the journal is read into the set to avoid — which is what makes a build that stopped between the choice and the copy leave its id spoken for. **A source is never handed out**: the service reads its own, since a `BytesSource` is a page of stills in memory and an `AddressSource` carries what this package will not even log.

**One way in** is `MediaImporter.import(entity, inputs, viewer:, run:)` — the takes and the batch the viewer's for an upload, and `<viewer>.<tag>`'s, with a `kind: "plugin"` batch, for a plug-in's render, `run` being its `PluginRun`. A `MediaInput` is a file on this machine, bytes the caller has, or a URL (`http`/`https`, the content type checked before anything is stored, the client always the caller's). Every kind is settled before a byte is written; then, per file, in this order: the bytes stream into the store while their SHA-256 and their size are measured — a picture small enough to thumbnail is kept as it passes, a clip is not, so a file larger than memory copies through — then the thumbnail into the project folder, then, once every file is in, the batch record through `ProjectWriter.writeImportBatch`. A picture too big to hold has no `width` and `height` in its item, which §12.2 makes the right answer: measured on ingest, never invented. The importer **never touches an entity's file**: it answers the `ProjectMedia`, and the caller writes the references into its draft, so the autosave, the identity lock and the stale refusal hold for media exactly as for a typed field. A record that cannot be written is logged and the take stays usable by its name (§12.1). Refusals are codes (`MediaImportProblem`: `notMedia`, `empty`, `tooLarge`, `nameTaken`, `rootUnavailable`, `noViewer`, `badUrl`, `unreadable` — a file gone between the picker and the import), never sentences, and neither a URL nor a server's words ever reach an exception, a message or the log.

**The thumbnail plan** (`thumbnail_plan.dart`) is **the ways to make a thumbnail, tried in order**, and the importer's only road to one. Two exist — a picture decoded, and the kind's stock picture — and two more are wanted that cannot live in this package: a **clip's first frame** needs a decoder the application does not have, and a **store's own thumbnail** is a service's. So a way is an interface, the order is data, and the plan is **given to** the importer by whoever builds it, which makes such a way an addition made outside this package rather than a change to it. A way is asked about one file with as much of it as is to hand — its kind, its path, the bytes the copy kept where it kept any, a stream to read it back, the store and the mime — because a way that took only `Uint8List` could never be a clip's: a clip's bytes are never held as it copies. A way answers **null** where it cannot, which is not a failure and never an exception: the next way is tried. The standard plan ends in the stock picture, which answers for every kind, so it always answers.

**The thumbnail** (`thumbnailer.dart`, §6.3): within 300 × 300, no crop and no enlarging, the EXIF orientation baked in, transparency flattened on the theme-neutral grey `#808080` so one picture serves both themes, JPEG at quality 80 — or 60 when it comes out over 48 KB. It runs off the painting thread where the platform has another (`off_thread*.dart`: `Isolate.run`, and inline on the web); a 24-megapixel photograph takes under a second on this machine. Two bounds keep it from taking the build with it: the bytes kept as a picture streams past are dropped once they go over 128 MB, whatever length the answer declared, and a picture whose header says more than 80 megapixels is not decoded at all — a decode allocates four bytes a pixel whatever the file's own size. Past either bound the stock picture stands in. What will not decode makes no thumbnail, which is a placeholder and never an error. A clip, a sound and anything else get a **stock picture drawn in code** (`stock_thumbnails.dart`: a play triangle, a waveform, a page, on the same grey at 300 × 300), written into `thumbnails/` like any other, so a clone of the project shows it without the application's assets.
