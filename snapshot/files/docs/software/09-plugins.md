# Plug-ins

### 6.11 Plug-ins — `filmopen_plugins`

A plug-in is one folder, `plugins/<tag>/` — in the shared library, in a project (a reserved folder, Project Specification §4.2), and in the repository for the stock ones — holding its manifest `pg_<tag>_<author>_v<n>.json`, its code `.js` beside it, `l10n/<locale>.arb`, and optionally `README.md`, `platforms/<id>.json` and `assets/` (Project Specification 1.11 §14.4). `plugins/README.md` is the reference a plug-in's author and a coding agent work from — where a plug-in lives, the roles and the names, the manifest field by field, **every member of `ctx`** and **every function a plug-in may expose**, each marked *built* or *planned*, then the limits, keys, servers, calls, strings, trust and the developer page. `plugins/REFERENCE.md` holds the shapes — every function with its arguments, its answer, its example, who may call it and whether it is built — and `plugins/filmopen-plugin.d.ts` says the same in types, with what is planned in a namespace of its own so that nothing there reads as callable; both are **generated from the interface definition** (below), and `plugins/template/` is the plug-in to copy. **The generated documents are read against the definition by a test** (§12, `reference_test.dart`) and **the host against it too** (`contract_test.dart`): every door `filmopen_js`'s `doorNames` lists is a member of `ctx` and none is missing, what a running call is given is what the definition says `ctx` carries, and the arguments the host builds for a function are valid against that function's own `args`.

**The contract, as data** (`plugin_api.dart`, `json_shape.dart`). `plugins/filmopen-plugin-api.json` is the one place the interface between the app and a plug-in is written: `$defs` (the shapes that recur), `everyPlugin` (`status`), `interfaces` (each with what a manifest adds when it declares it, and its functions — required or not, who may call it, `args`, `returns`, an `example`, a state and the revision it arrived in), `beyondInterfaces` (actions and offers) and `ctx`. It is **JSON Schema, draft 2020-12, in the keywords it uses and no others** — `type`, `properties`, `required`, `items`, `enum`, `const`, `oneOf`, `additionalProperties`, `minimum`, `maximum`, `description` and `$ref` into `$defs` — so that a standard validator reads it as it is: `JsonShape` knows exactly those, **refuses a keyword it does not know** where a schema is read (`JsonShapeException`, naming the keyword and where it is), and reports a wrong value **by its path** as a code and never a sentence (`outputs[0].mime: missing`), a `oneOf` answering with the problems of the shape that came closest so that the path is one an author can go to. An `integer` is a number with no fraction, as a standard validator reads it. `PluginApi.parse` reads the file whole and refuses it whole: every `$ref` resolving, every function carrying its arguments, its answer, an example, its state, its `since` (never after the file's own `revision`) and who may call it, and **every example valid against its own arguments**. **The app reads it as an asset of its own** — `plugins/filmopen-plugin-api.json`, bundled beside the stock plug-ins — at the host's first load; a build that cannot read it runs no plug-in and says so in the log (`plugins.apiMissing`, `plugins.apiUnreadable`) rather than reading manifests against a contract it does not have, and a test of the root package pins the asset. `ctx.api` is the file's two numbers, `{ api, revision }`, so that a plug-in asks for a door only where the revision says it is there, and `ctx.caller` is `{ tag, stem }` of the plug-in that asked, **null** where the app or the person started the call. **`plugins/filmopen-plugin.d.ts` and `plugins/REFERENCE.md` are generated from the definition** by `python3 scripts/gen_plugin_api.py`, never written by hand, and its `--check` runs in `scripts/test_all.sh` and `scripts/test_all.ps1`; `plugins/README.md` stays the guide, written by hand, and **states no shape the reference does not**: every shape it writes outside its examples, a function's arguments among them, is one of the definition's objects — whole unless it says `…`, each field optional exactly where the definition says — and it names `hooks` and `provides` only where it says api 1 no longer reads them, which `reference_test.dart` holds it to.

**What a manifest declares it implements**. `implements` is the one place a manifest says what the app may call it for — `{ "render": { "platform": "comfyui", "models": ["t2i-z-image-turbo"] } }` — and **`hooks` and `provides` are no longer read**: a manifest that holds one is reported (`replacedField`) and told that api 1 says it in `implements`, with no adapter, since every manifest in existence is ours. Each declared interface is read **against the definition**: one it does not know is reported by name (`unknownInterface`) and left out with the rest working; one declared without what that interface must add — `render` with no `platform` — is reported and left out, since the app could neither route it nor say where it goes; a declared value of the wrong shape is reported by its own path, the definition's `declare` schema deciding. `ImplementedInterface` carries the platform, the catalogue entries it speaks for (an id the catalogue lacks is kept and said on its page) and **the functions the interface holds that this build can call** — a function the definition marks `planned` is listed nowhere, the developer page's list included — copied from the definition as the manifest is read, so that the host asks `implementsFunction('render')` without the definition in hand. `callableByPlugins` is the same reading for §3.3: the functions of those interfaces whose `calledBy` names `plugins`, and every plug-in's `status`. **`minRevision`** is the least revision of the contract the plug-in needs; above this build's, the registry drops its code, the plug-in is **listed with `needsNewerApp` and does not run**, and its page says which revision it asks for — a sentence drawn only where the revision is past this build's, so that a plug-in which cannot run for another reason is never told it needs a newer FilmOpen. **`capabilities.upload`** is known and not yet answered: the plug-in's page says *sending your film's media to its server: not in this FilmOpen yet*, consent names it, and `ctx.upload` — a door of `ctx` like any other — is refused `refused`/`notSupported` in those words. **`x`** is anybody's: kept as written, reported never, shown nowhere. An **offer** may carry `args` and `returns`, schemas of the kind the definition writes, which the developer page holds a call to; one this checker cannot read is reported and left out, the offer still readable. **No offer may take the name of a function of the contract** — every interface's and every plug-in's `status` — nor a name the language gives every object, nor a function one of the plug-in's own actions calls: a function of an interface is reached because the manifest implements that interface and the definition says who may call it, never because it was offered.

**`status`, required by the contract and never a reason to refuse a plug-in**. The seam's `checkStatus(stem)` runs the plug-in's `status` with `ctx` alone and **holds its answer to the definition** before the app reads it: `PluginChecked` with one of the four states (`ready`, `unconfigured`, `unavailable`, `degraded`) and the plug-in's own message; `PluginSaysNothing` where the code has none — *this plug-in does not say whether it is ready, which api 1 asks of it* — after which its other functions still run, since no app can know a function is missing before it has run the code; `PluginCheckFailed` with the call's own outcome, a shape the contract does not hold being `badResult` **with its path**. It starts no render, spends nothing and installs nothing, and runs **only on a person's gesture, or an agent's**: the app draws *Check* (`plugin:<tag>.check`, the answer `plugin:<tag>.status`) on every plug-in's page, and a list of plug-ins calls nothing. **A check may not reach `ctx.ai.complete` or a platform's `run`, nor may any plug-in a check calls, and a `status` is a check however it is reached** — an action's `ctx.call` too — the chain's frame carrying it (`CallFrame.inCheck`) and the door answering `refused`/`status` (`run` and the road through an action since step 7) — since the app presents *Check* as an inspection and that is the one door that always costs money; its own key, its own server and another plug-in's `status` stay open, which is how it answers *is my key there, does my server answer*, and what those cost is recorded as any call's is. *Check* is disabled with its reason while the plug-in is off; `unconfigured` and `degraded` are drawn in the page's warning colour and `unavailable` in the error colour; and **an answer is forgotten when the language changes** — half its words are the app's and half the plug-in's — including one that lands after the change. The log carries `plugins.checked` with the state and **never the message**.

**The manifest** (`plugin_manifest.dart`). `PluginManifest.parse(json, api:, knownPlatforms:)` never throws. It answers a `PluginManifestParse`: the manifest, or null when the plug-in cannot run on this host, and every `PluginIssue` found — a code (`PluginProblem`), the dotted field it concerns and the values a sentence needs. Refused (no manifest): a file that is not `pg`, a tag that is not a segment or is `app` (the owner of the app's own keys), an author that is not a handle, a missing or mistyped `v`, `name` or `api`, an `api` outside `supportedPluginApis` (`apiUnsupported`, carrying the manifest's version and the host's), and an `entry` that does not read (`badCodeFile`, carrying the path it concerns). **`entry` is a file name or an ordered list of them** (the format's §14.1): each a `.js` file of the plug-in's own folder named by a relative path with `/`, no `..`, no absolute path, no drive letter and **no segment beginning with a dot**, none twice, at most `PluginManifest.mostCodeFiles` (32) of them and `mostCodeBytes` (2 MB) in all — the last checked where the code is read, since a manifest knows no sizes. Absent, it is `<stem>.js`; `manifest.entry` is the first, for what reads one. Reported and left out, the rest read: a field the manifest does not know (the common header's fields and `plugins` are known), at its top or inside a key slot, a setting or an action — a mistyped `defualt` among them, a key slot's or a setting's `label` or `help` that is not text, a number's `min` above its `max` (both bounds left out), a hook (`unknownHook`, entity or platform), a setting type (`unknownSettingType`), a setting, action or key slot that cannot be used, a malformed key id in `uses`, an entity type the format does not know, `entitySettings` for a type `applies` does not name, a host in `capabilities.network` that is not a host name, a default of the wrong type (the setting kept without it). A key slot naming a platform no platform file defines is reported and kept. **`kind`** is `platform`, `model` or `tool` — a word for lists, which decides nothing, as a folder's kind decides nothing; the three are said in the reader's language on the plug-in's page, and another token is kept and shown as written. **The `models` of an interface it implements** (`implements.render.models`, `implements.text.models`, `provides.models` until) are the catalogue entry ids the plug-in speaks for (§14.7), since an entry's id does not always fit a tag: one that is not an entry id is reported and left out, and one the catalogue does not define is reported **on the plug-in's page and kept**, since a catalogue grows and a plug-in that names tomorrow's entry is not broken today. **`offers` and `calls`** are read as the architecture document's §4.2 has them: an offer is a plain name on the plug-in's object with a `label` — a locale key of the **offering** plug-in's strings, since it is what the *caller's* consent shows — and optionally `help` and an `example` of its arguments; one without a label is reported and left out, because consent would then say nothing about it. `calls` is `<tag>:<name>`, a list apart from `uses`, since a person reads *the keys it may use* and *the plug-ins it may use* as two things; a plug-in's **own** tag is allowed, which is how the template shows the door with nothing else installed. **A hook may never be offered**, nor a name the language gives every object (`reservedOfferNames`: every `PlatformHook` and `EntityHook`, `constructor`, `toString` and their kin), **nor a function one of the plug-in's own actions calls** — a platform hook is the app's to call with its consent and its usage records, `verifyKey` receives a candidate key the person just typed, an entity hook writes versions, `constructor` is not the plug-in's function at all, and an action is a **person's button**, with their gesture behind it, which a caller must not press for them (reference said so and nothing had enforced it). It is refused where the manifest is read **and** again at the door, since one of the two alone would be a rule with a hole. Settings (`setting_spec.dart`) are `string`, `text`, `number` (`min`, `max`), `boolean`, `enum` (`values`), `model` (`category`, `platform`) or, `server`, each with a `label` and `help` that are locale keys and a `scope` of `project` (the default) or `machine`; an entity setting has no scope. **A `server`** holds a `ServerAddress`'s normalised text and is **always machine-scoped**, whatever `scope` says — `scope: project` is reported (`badEntry`) and the setting is kept on this computer anyway, so its author learns it — and is refused under `entitySettings` (`unknownSettingType`, the field left out), since an entity's file travels as the project file does. Its `default` **may only be this computer** (bench plan's): an address elsewhere is reported (`badHost`) and dropped, so the setting starts empty and the box asks; one that is no address at all is `wrongType`, as any default is. `accepts` takes what `ServerAddress.parse` reads. Setting keys and action calls are identifiers, action ids and slots segments.

**Keys** (`key_id.dart`). A key's id is `<owner>:<slot>`, both segments: the tag of the plug-in whose manifest declares it in `keys`, or `app` for the application's own. Its store name is `filmopen/<owner>/<slot>` and its preference `providerKeys.<owner>/<slot>` — the status, the date and the last four characters, never the key (§6.7).

**Strings** (`plugin_strings.dart`). A locale file is ARB-shaped and read by the format's own reader, so a repeated key refuses the file (`notLocaleFile`, as §18.1 refuses one anywhere): `@@locale` must be its file's name (`localeMismatch` otherwise), `@key` metadata is skipped, a key holding `:` is refused (`colonInKey`). `PluginStrings.t(key, locale:, args:)` reads an unprefixed key, or one prefixed with the plug-in's own tag, as the plug-in's; `app:<key>` through the application's lookup; any other namespace as nobody's. It falls back from the locale (`pt_BR` read as `pt-BR`) to its language to `en` to the key itself, reporting each missing key once (`plugins.missingString`), and fills `{name}` placeholders, leaving one without a value as written. `textOr` shows a manifest's `name` or `description` as a key where the strings have it and as written where they do not.

**The package** (`plugin_package.dart`). `PluginPackage` — `tag`, `list`, `text(path)`, `bytes(path)` (for the consent hash) — is the one interface the loader reads a plug-in through; `SourcePluginPackage` is a folder inside any `ProjectSource`, and `SourcePluginPackage.tagsIn(source)` the plug-in folders under `plugins/`. `PluginFolder.read(package, catalogueIds:)` reads every manifest at the folder's top (a stock plug-in and a person's fork share a folder), the locale files of the first manifest's `l10n`, and the plug-in's own platform files, refusing one for an id the catalogue defines (`platformConflict`); a folder without a manifest (`noManifest`), a manifest whose tag is not its folder's or whose stem is not its file name (`folderMismatch`), a manifest whose `entry` is not in the folder (`noCode`, the manifest still listed so that its page can say why it cannot run), a folder with no `en` locale file (`noEnglish`), a file that cannot be read as text — bytes that are not UTF-8 — (`unreadable`, with the failure's type, the rest of the folder still read), and a document that does not parse are reported by the path they concern. The code is not read. `PluginManifest.isByStockAuthor` says only that the author is `filmopen`, the stock plug-ins' handle; it grants nothing, since anyone can write under it and the template does.

**The engine** (`filmopen_js`). `runJs(JsCall, doors:, cancel:)` runs one call in an isolate made for it (`Isolate.spawn`), in a QuickJS-NG runtime made and freed for it: **each of the call's files is evaluated in order** — `JsCall.files`, a `JsSource` of a name and its text, the one-file constructor making a list of one — as plain scripts of one scope in the one context, so that what an earlier file declares at its top is there for a later one and **the last file's value is the plug-in** (the format's §14.1); the function of that value is called with `ctx` and the JSON arguments (or `ctx` alone, for an action), its promise awaited, and the answer is `JsValue` or `JsFailure` with a code — `failed` (the script's own message, its author's words for the person), `limit` (`time`, `memory`, `stack`, `result`, `wall`), `cancelled`, `hung`, `noFunction`, `notJson`, `stalled` (a promise nothing can settle), `engine`. A file that fails stops the load where it is, so the failure's place names that file. The C shim (`src/filmopen_js.c`) keeps every `JSValue`, the budget and the cancel flag, so Dart passes only UTF-8 strings and integer handles and no Dart callback runs inside JavaScript; `fjs_load` is called once per file, the prelude running before the first. Before the script, a prelude builds `ctx` on one host function and removes `eval`, `Function` — the global, and the `constructor` of every kind of function — and `Math.random`; the runtime has QuickJS-NG's base objects — §14.2's list and the language's other plain built-ins (`Reflect`, `Symbol`, `BigInt`, the weak collections, `queueMicrotask`, …), none of which reaches outside the runtime — and no `Date`, module loader, timer or I/O (Project Specification §14.2). The prelude captures `JSON`'s functions, `Reflect.apply` and the error constructors before the plug-in's file runs, locks `Error.prepareStackTrace` — whose call sites would otherwise hand a script the functions on the stack, the host's among them — and evaluates to the runner, which the shim holds: nothing of the host is on the global or reachable from the script. The runner reports through a host function, and the shim writes the outcome's JSON — the value by the engine's own serialiser, the message as a JSON string — so a script decides only its own value and its own `failed` message; a thrown error's `code` is kept only as `refused` or `badArgs`, which doors give, and `cancelled`, `limit`, `hung`, `stalled` and `engine` are the shim's and the runner's alone. A request is written to JSON by the engine's own serialiser in C, never by the script's `JSON`, so its name and id are the shim's, and the runner answers only the door names `ctx` uses; its bytes count against the memory limit until its door answers, a request is at most 16 MB and at most 10,000 wait at once. A microtask that throws outside the call's promise is dropped, not the call's outcome; a `log` or `progress` made just before a call ends still reaches its door, and no other request queued then is started; a cancel that comes before the call's isolate has started is delivered when it starts. **A failure says where it is** (bench plan's): the runner hands `done` the error's `stack` where `typeof` says string, the shim cuts it at 2,000 bytes and makes it JSON-safe — a quote, a backslash and every control character becoming a space, so the frames run together and stay readable — and a load-time failure, a syntax error among them, reads the exception's own `stack` the same way; Dart then takes the **first frame naming one of the call's own files** as `JsFailure.file`, `.line` and `.column`, so a `<prelude>` frame never counts and a failure with no such frame — a door's refusal, made where the door is answered — has no place. Only the text crosses over: `Error.prepareStackTrace` stays locked, since call sites would hand a script the functions on the stack, the host's among them. A script can throw an error that reads as a stack overflow, or write its own `stack`, which only mislabels its own failure, as it can mislabel its own message; the capped stack protects the process either way. Every C string is read as UTF-8 with malformed bytes replaced, and a result is measured in bytes before it is copied. `ctx`'s asynchronous members are requests queued in C and answered by the caller's `JsDoor` on the caller's isolate — where plugin channels and providers are — and a `JsDoorRefusal` reaches the script as an error with its `code` and `reason`, while anything else a door throws arrives as `failed` without its text; `sleep` is answered in the call's isolate, when it ends and never sooner — one longer than the call has left is ended by the wall clock, whose cancel wakes it, and the call ends as the `wall` limit; `settings`, `plugin`, `selection` and `l10n.t` read the call's data synchronously, a missing string reported through a door. **Limits**: memory is counted by the runtime's own allocator, so running out is known for certain and ends the call even when the script catches it; the JavaScript stack is capped at every entry by what the current thread really has below it, less 256 KB (a 1 MB limit crashed a Linux isolate thread whose stack was smaller); engine time is counted only while JavaScript runs, never while it waits on a door, and the interrupt handler ends a call past its budget or cancelled — uncatchably; the wall clock and the result's size are the Dart side's. A cancel sets the C flag at once, from any thread, and wakes a call waiting on a door or asleep; a cancelled call that has not ended within 5 s answers `hung` and is left, since an isolate inside C cannot be killed.

**The host** (`filmopen_plugin_host`). `lib/main.dart` installs `createPluginRuntime` into the state's `PluginRuntime` seam (§7.1) — the host where there is `dart:io` and `dart:ffi`, the seam's `NoPluginRuntime` on the web — and attaches it to the container, as the automation host is. Nothing runs at start: the runtime reads manifests and code as text and installs the stock plug-ins' files; JavaScript runs on a gesture. The host reads the app through a `HostEnvironment` (the container's, or a test's in memory).
- **The stock install.** On its first load the runtime runs `installStockPlugins` (`filmopen_plugins/stock_install.dart`) over the library with the bundled `plugins/` assets: a file the library lacks is copied, a stock file whose bundled text changed is replaced, a stock file the bundle dropped is removed unless the person changed it, and nothing `plugins/.stock.json` does not list is touched; a deleted stock folder comes back unless the person disabled that plug-in. The project is re-read when anything changed, since the library's index was read before the files were there. The template is stock and installed **off**.
- **The registry** (`plugin_registry.dart`) reads every plug-in folder of **the development folder**, the open project's folder and the library, in that order (§14.5). The **development folder** is a folder on this computer whose sub-folders are plug-ins — `<tag>/pg_<tag>_…json`, with no `plugins/` inside it — named by the preference `filmopen.plugins.devFolder` or, where that is empty, by the environment variable `FILMOPEN_PLUGIN_DEV_FOLDER`, so that an agent's launched build, whose preferences are new each time, needs no typing; the preference wins where both are set. It is **found first**, before a project's and the library's and under a stock plug-in's tag too, so that a working copy is the one that runs; it is never written by the app, a path that is not there lists nothing, and **it is read one level deep, one plug-in at a time** (`dev_folder.dart`'s `DevelopmentFolder`, through a `DevFolderReader` a test replaces to count what it was asked): its immediate sub-folders alone are looked at, one whose name is a tag and whose own files at its top include a manifest of that tag is a plug-in, read on its own, and any other — `docs`, `research`, `tests` — is never read and nothing below it is listed, the names at its top being all that is asked of it once, while a folder whose name is no tag — `.git`, `node_modules` — is not asked about at all; so the folder may be a repository. **A plug-in folder that cannot be read is a problem of that plug-in**, said with its path on the developer page (`devFolderProblems`) and in the log once (`plugins.devFolderUnreadable`), and every other plug-in of the folder is there as before; one that cannot even be looked into is passed over, since nothing says it is a plug-in, and said in the log once with its path (`plugins.devFolderPassedOver`), as is a development folder that cannot be listed at all, so that a folder that lost its permissions does not vanish without a word. **A plug-in found there is never trusted by origin**: it asks *Allow* like any other in ordinary use, once for each state of its files. The version that runs is the format's resolution of the `pg` entity for the viewer (§6.1); where that decides nothing, the stock author's highest, else the folder's highest. A folder in the open project under a stock plug-in's tag is not read: keys belong to the tag, and a film that arrives with `plugins/default-ai-assist/` must not take over the person's keys or the app's own assistant. A plug-in is **trusted** when **every file of its folder** is one the stock record hashed, unchanged, and the folder holds no file the record lacks (widened): it is on unless the person turned it off, and its `uses` are granted as installed. Any other is off until the person allows it: *Allow* stores `pluginFolderDigest`'s hash (`plugins.consent.<stem>`), **the SHA-256 of every file of the folder **as the source lists it** — the manifest, every code file, `assets/`, `platforms/`, `models/`, `l10n/` — sorted by path, each line the path, its length in bytes and its own SHA-256, one file held at a time; a change to any of them turns the plug-in off and asks again. **What the listing leaves out does not run**: a source reports no name beginning with a dot, nothing under `build/`, `conform/` or `node_modules/` and no `.tmp`, so a code file it does not report is `noCode` — the plug-in listed and not runnable — `ctx.asset` refuses a file it does not report, and `entry` may not name a segment beginning with a dot; reading one would be running what nobody allowed. A folder of more than `mostFolderFiles` (2000) files or `mostFolderBytes` (64 MB), a zip's own limits, is not read at all: unreadable, so not trusted and asking again. A workflow in `assets/` decides what runs on the person's own computer as surely as the code does, and a plug-in's own `platforms/*.json` is inside the hash. Files are hashed by their bytes, so a picture in `assets/` counts; one that cannot be read hashes as a line no readable file can write — never as the empty file somebody may have allowed — and the registry lists it as a problem (`unreadable`) on the plug-in's page; it also breaks trust, since a file outside `files` would otherwise slip past the record's count. The preferences are `plugins.disabled`, `plugins.enabled`, `plugins.grants.<stem>` (key ids), `plugins.consent.<stem>` and `plugins.prefer.text` / `.media` (a tag). A key's platform is its owner's declaration, and only an enabled owner's: a disabled owner's section is gone from Provider keys, so its keys are nobody's to send. The keys a plug-in may send are its own slots and each granted `uses` whose owner is enabled and still declares it. **A plug-in's own `platforms/*.json` names a platform for the app only while that plug-in is on, and never decides where another's key goes**: a key is sent by the catalogue's file, else its owner's own — a folder nobody had allowed, read first, used to decide where every key on a platform the catalogue lacks was sent. A plug-in one of whose calls hung (it did not end within the grace after a cancel; its isolate cannot be killed) is off, without touching the preferences, until the app starts again or the person turns it on or allows it again — their choice, which may leave a second hung isolate beside the first. Consent to other files than the ones allowed before takes back the keys granted then.
- **What the seam answers.** `plugins` (summaries in the app's language: name, description, origin, enabled, consent, grants, hosts, **servers** — each `server` setting's words and the default it starts with, which consent says in one line — types, hooks, machine fields with their values, actions, problems); `keyOwners` (Provider keys' sections: the app's own `app:openai` and `app:xai` first, then each enabled plug-in's slots; the app's slots are listed once, `appKeySlotsOfTheApp` in `filmopen_state`, which the host's `platformOf` answers `app:<slot>` from too); `sectionsFor(type)` (each enabled plug-in's `entitySettings` for an entity type, or its project-scoped settings for the project file); `providers(hook)`; and the changes — `setEnabled`, `allow`, `setGrant`, `setMachineSetting`, `setPreferred`, `installArchive` (a zip's text files written as text and anything else, a picture in `assets/`, as its bytes) — each logged (`plugins.enabled`, `plugins.disabled`, `plugins.granted`, `plugins.settingChanged`, `plugins.preferred`, `plugins.installed`).
- **Calls between plug-ins**. `ctx.call('<tag>:<name>', args)` runs a function another plug-in **offers**, or one of an interface it implements that the definition says plug-ins may call (`platform`'s `run` and `request`, and every plug-in's `status`) — by name and never by a handle. Never `verifyKey`, `transform`, `render` or `complete`, which go through the app so that they are routed, recorded and paid for as the person's, and never a function one of the plug-in's own actions calls: the manifest's reader drops such an offer and **the door refuses it again, reading the contract itself** (`plugInsMayCall(api, manifest, name)`, the one rule both use), so that neither half alone is a rule with a hole. The function runs **as its owner** — its settings, its server, its storage, its keys, its own engine time and memory — and `ctx.caller` is `{ tag, stem }` of the plug-in that asked, **null** where the app or the person started the call; the caller receives the JSON it answers and nothing else. The runtime keeps the front — the development folder, its preference and its problems — and the three seam methods are one-line forwards. **It is built from closures, not from a reference to the runtime**: `plugin_call_runner.dart` imports `dev_run.dart` for `DevLog`, so the bench may not import the runner back, and what it needs — the registry, the views, the contract, the language, the data files, a reload, a binding, a run, a call and the three that hold an answer to a shape — is handed in. For the same reason the door it watches arrives as a closure that answers, not as the means of asking. **The developer page's side** (`dev_run.dart`, `host_runtime.dart`'s four `dev…` methods). `devOpen(stem)` reads the plug-in's files **from disk again** and answers what it exposes, **in the definition's terms**: **`status` first**, then the functions of the interfaces it implements, its actions and the functions it offers, each with **the definition's example** for a function of the contract and the manifest's own for an action or an offer — no shape kept by hand — and `verifyKey` never among them, since its candidate key is typed on Provider keys — with every problem by the file it concerns and where its last run and the developer's log are written. `devRun(stem, function, args, mode:)` reads them again and runs the function **enabled, asking no consent, with every key its `uses` names granted** (bench plan's: the page is for people who write code, and nothing on it is withheld); the sandbox, every door's rules, the limits and the usage records are exactly the app's, or what passes here might fail in the app. **The registry, the preferences and the stored consent are untouched**: outside the page the plug-in asks exactly as before. The run's hook in the usage records is `dev.<function>`. **It calls the function one of two ways** (`PluginDevMode`): *As FilmOpen calls it*, the default, with the request the app would make — `status` with `ctx` alone; an action with `ctx` alone, as its button presses it; a `render` prepared by `prepareRender` (its entry, its inputs described and held to the entry, the seed, the source) and a `complete` or an estimate as the app builds them, an estimate being the function of the interface its `operation` names, and **a request the app could not make refused before the plug-in runs** — a model the catalogue lacks (`noProvider`/`noEntry`), one this plug-in does not serve because the entry names no platform its manifest implements the interface on or its manifest names other models (`noProvider`/`noPlugin`, since the app's choice would never bring it here), a completion's `params` that are no object (`badArgs`/`params`); an entity hook with the entities chosen; an offer, or a function of the contract an action's button also calls, as the contract calls it — and *Exactly what I typed*, the box as it is, for the protocol and a function's edges. **The mode changes what is sent, never the guards**: `status` runs as *Check* runs it either way, so it may not reach `ctx.ai.complete` and spend (step 2's N4). **The request as sent is the run's first log line** (`request`), so the page shows it before the answer comes, and the run carries it (`PluginDevRun.request`, with its `mode`). **An answer of a function of the contract is held to the definition either way**, one of the wrong shape being `badResult` with its path, and **an offer's own `args` and `returns` hold a call to it** — its arguments as a caller would send them, before it runs, as FilmOpen calls it, and its answer either way (step 7). A render as FilmOpen calls it is read by its `state` and, where an entity was named, **saved as a take exactly as the app would**, its batch's item the request as prepared; as typed, nothing is saved, since the app's record would name a request nobody prepared; with no entity named, the outputs are only listed. `last-run.json` holds the `mode` and, as `args`, the request as sent — `null` where it was refused and nothing was sent. `devClose(stem)` forgets `last-run.json`.

**The log of such a run.** The doors closure is wrapped for the page and for it alone: **the request as sent first** (`request`), then every `ctx.log` line and a row per door, in order, with what the door was asked for — the setting or the key **by name**, the path, the answer in summary and the milliseconds — and **what crossed into JavaScript and nothing else**, so no credential and no address is in it. A line's data is cut at 64 KB with a mark and a message at 200 characters. Each line goes to the page as it happens and to **`plugins-dev.jsonl` beside the app's log**, rotated at 5 MB to `plugins-dev.jsonl.1`: a developer's own file to `tail`, which no issue report ever carries and which a person's ordinary use never writes to. After every call `last-run.json` is written under `<app support>/plugins/<tag>/dev/` — the function, the mode, the request as sent, the outcome with a failure's place, and the lines, under a megabyte — results as data, for an agent; it is not a log line, since the app's log holds events and never an answer's text. The log events are `plugins.devCalled` and `plugins.devFolderSet`, each with a stem and a function and never an argument.

**The zip** (`plugin_archive.dart`). `PluginArchive.read(bytes, expectedTag:)` reads a plug-in's zip into memory and refuses it whole — nothing kept — when it does not read as a zip or holds nothing, claims more than 64 MB unpacked or 2,000 files, has an entry that would land outside the folder (absolute, a drive letter, a backslash, an empty, `.` or `..` segment) or a link (by its target or its Unix mode), or has no manifest at the folder's top, manifests of two tags, a folder not named after the tag, or a tag other than the one expected. Each entry is inflated by the `archive` package's pure-Dart inflater into a buffer bounded by what remains of the 64 MB — never through `entry.content`, which on `dart:io` hands the whole entry to zlib and writes it out only once it is complete — so an entry whose directory claims a few bytes and inflates to gigabytes stops at the limit; an encrypted entry, one compressed other than stored or deflated, and one whose bytes do not match its CRC-32 — a download cut or damaged on its way — are unreadable. What an operating system adds as it zips a folder — macOS's `__MACOSX/` and `.DS_Store`, any hidden name — is left out, as a folder source skips hidden entries. The folder's contents may sit at the archive's top or inside one folder named after the tag. `PluginArchive.write` makes one.
