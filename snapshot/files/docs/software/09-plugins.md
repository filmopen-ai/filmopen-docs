# Plug-ins

### 6.11 Plug-ins — `filmopen_plugins`

A manifest key slot's `auth` is `key` by default, or `oauth` for the platform's signed-in route.
The optional sibling `oauth` block on the platform defines its authorization, token and revocation
endpoints, issuer, scopes and required scope, public client id, extra authorization parameters,
output-cap behavior and plan label. An incomplete block makes the platform unusable, with a diagnostic
at the field concerned; it never changes the platform's existing `auth.kind` or its key route.

`ctx.signIn({key})` and `ctx.signOut({key})` are settings-action doors for the plug-in's own
OAuth slots. Sign-in opens a fresh IPv4 loopback callback with PKCE, state, nonce and an
installation UUID, kept in preferences and reused across attempts. The exact redirect address is reused in the code exchange.
The ID payload returned by the token endpoint must match the configured issuer, client
audience, expiry and nonce, and the granted scopes must include the required scope.
An existing client or account cannot change without sign-out. The credential and its
account/expiry key record are committed under the slot's lifecycle lock; a refused store
never produces a signed-in record. Sign-out revokes once and clears both records only
on HTTP 200. The callback and exchange end on Stop or the action's existing wall.
Codes, verifiers and tokens stay in Dart and never enter JavaScript or logs. Sign-in
logs its start, authorize URL, callback, exchange metadata, validation comparisons,
storage and refusal/failure stages with elapsed time. Sign-out logs revocation status
and server text, record removal and completion, or the stage that failed. Endpoint
requests follow no redirects, and a browser closed by the person is not detected.

An OAuth slot’s Provider keys card reads account and expiry from the manifest view’s existing key record, without opening the credential store. Its Sign in and Sign out buttons call the host doors for that declared enabled slot directly, without a plug-in action or inferred name. A cleared record displays Sign in exactly as a slot never signed in. A refused refresh records its reason in refreshFailed/cleared log events and shows its terminal explanation in the dock. That explanation takes precedence over the record removal’s stale status; the session still becomes stale and sends nothing further. No card history is retained.

The `process` capability permits program doors. A plug-in without it is refused before any program action and logs `plugins.capability.refused` and `plugins.process.refused` with the door, arguments, reason and elapsed time. Consent names each program setting and says: “It runs a program on this computer that you choose on its page, as you, with your access.”

A `program` setting is an executable path chosen by the person and kept on this computer. It is refused in an entity's settings or with any scope other than `machine`. Its optional `names` lists executable names without extensions. The plug-in page looks for those names on PATH, including PATHEXT on Windows, and offers *Use this* beside the found path; only accepting it or typing a path stores permission. A manifest default is reported as `badEntry` and dropped. A stored path that no longer names an executable file is shown inline. Discovery logs the names, found path and elapsed time; a missing executable and every stored setting change log the path as it is.

`ctx.process.start({setting, args, cwd?})` starts the executable currently stored by the person, never a default. Each plug-in and program setting has one host-owned process across JavaScript calls. An unset path is `notSet`, a path that is not executable is `notExecutable`, and starting an already running process answers `already: true`. Linux starts an owned process group; Windows runs through the shell so that a `.cmd` shim works. Arguments travel as a list. Without `cwd`, the host creates and uses the stable private plug-in data folder `process/<setting>/`; an explicit directory is used as given.

`send({setting, line, operation})` writes one line and the first send makes its operation the owner. Another operation's send or receive is `busy` until `release({setting})` frees the owner. `receive({setting, operation})` takes the next complete stdout line, or answers `exited: true` with the exit code. It waits without a timeout and ends when the calling control is cancelled; cancellation leaves the process alive. Output is queued whole, stderr is logged separately, and a crash is never restarted automatically. `stop({setting})` closes stdin and sends TERM to the Linux group, then KILL after two seconds if it still lives; Windows ends the tree with `taskkill /T /F`. Disable, a hung call, a failed switch held off for the session, a change to the program setting, and application exit stop the owned processes, including children. Every process operation logs its inputs, path, arguments, working directory and whether it was defaulted, pid, whole input/output/error lines, ownership and release, refusals and reasons, exit code and elapsed time. No provider protocol or file-reading door is part of this transport. When a call ends done, failed or stopped, any process still owned by its own frame id is stopped and its queue discarded with reason `ownerEnded`, including a process in another plug-in started by a nested completion. The existing call slot stays held until that cleanup ends.

Only the operation the host hands to `complete` is automatically cleaned up by turn handover or a frame’s `ownerEnded`. Any other function that sends must `release` in its own `finally`. `stop` releases ownership; `release` on that stopped pair answers `notRunning`. A normal reply still owning its process hands over as `unreleased`, rather than `failed`.

Every text `complete` receives an `operation`: the assistant session's id, including finalization, or the calling frame's id for another call. At an admitted turn's end, an operation still owning a process is handed once to the text plug-in's optional `interrupt({operation})`. Stop, a failed call, a third repeated tool refusal and a stale session take this same path; an operation already released takes none. The interrupt is a root call with a fresh uncancelled control and its own Usage ledger, waiting for the existing per-plug-in slot. It writes the program's protocol interrupt, consumes its terminal line and returns `{usage}`; its ledger records that answer separately from every completed call's ledger. The host then releases the owner. Ordinary Stop keeps the program alive when the interrupt succeeds. An absent or failed interrupt, or one reaching the ordinary call wall, stops its owned processes and discards their queues, with stop reason `interruptFailed`. No repeat-Stop control is added. If handover cleanup throws, that failure is logged and propagated while the existing turn control and policy are still cleared, leaving the backend free for another turn. `assistant.turn.interrupt` records session, plug-in, declaration, `done`, `failed`, `absent` or `wall`, the turn-end reason, returned usage and elapsed time.

`VisualStyle` holds the treatment's five primary leaves as `Observed` text: `camera`, `camera_mount`, `lens`, `depth_of_field_prompt` and `color_grading`. A description may now propose them through the same treatment-leaf gate: text is trimmed, limited to 4,000 characters and refused if it contains a control character other than tab or a line ending. A null or empty text leaves the current value alone; an invalid leaf refuses the whole description. The existing depth-of-field scale, inheritance and prompt composition are unchanged, with `treatmentPromptLeaves` remaining the one ordered list of the five.

**The assistant contract.** An assistant declares its required `catalog` under `assets/` and exposes no assistant functions. The host runs its catalog actions (§6.11a). The host subsequently owns microphone, playback, sockets, interruption and cleanup under the native conversation contract. Opening captures binding only; explicit Start admits a ready funded session. Finish draft stops capture and spoken output, drains already-admitted captions for at most five seconds, closes resources and freezes the visible transcript. End or Close tears down immediately without finalization or writes. Native sessions have no cap of the app's on their length and require explicit restart.

Text start and turn use the frozen, verified text completion route, with transcript and session state owned by the host. The host voice finalizer consumes the visible transcript after cleanup; an incomplete transcript is labeled and requires an explicit choice to use it. Its proposal is bounded to one file object whose `$id` is the target's id, changing at most the target's field — a string, of any length — and removing nothing; an import that changes nothing proposes nothing. The person reviews and applies the proposal in FilmOpen.

The assistant's limits are the model's: the host keeps one in-flight text/finalization request and asks for the chosen model's catalogue `max_output_tokens` through the provider's verified output parameter, none where the catalogue names none; where the action names an `effort` (`low`, `medium` or `high`, the catalog's) and the route's catalogue row maps `reasoning` (OpenRouter's and OpenAI's `reasoning.effort`), each call of the turn and of *Apply* carries `reasoning: {effort}`, the call policy admitting that value and no other, and none otherwise, the model's own default then standing — each call's line logs `effort` and `effortFrom` (`action`, `none`, `unmapped`), and `bytesBy` the size by part — the opening's (system, context, tools, fields) on `assistant.open`, and each model call's (system, context, history, tools), measured as it is sent, on its `assistant.turn.call` and *Apply*'s on its stage —; `assistant.open.select` names the `transport` (`text`, `voice-openai`, `voice-grok`) and where the fields' `guide` went (`tools` or `context`); it counts no turns or model calls, measures no request, answer, partial or note against a bound of its own and keeps no clock on a turn. What ends a turn is the model's answer in words, the person's Stop, a stale binding, the third same refusal of one tool, an output cut off, a provider's refusal (its context limit among them) or a network call's own bound. Nothing is truncated: the activity block goes whole, and *Apply*'s answer is proposed whatever its length; roughly 300 words for a synopsis is prompt guidance. Cancellation closes only owned work, with no automatic paid retry or fallback. Finalization has its own Usage chain through the frozen nested completion operation; provider units, charged failures, estimates, confirmed charges, confirmed zero and unknown remain distinct. Usage is not a field of the finalizer's answer. The schema does not enforce byte, turn, identity-equality or time bounds. Account/funding doors and the host's preparation mode are separate runtime work; FilmOpen-credit conversation remains unavailable until an accepted authenticated metered relay exists.

**The exchange doors.** The contract settles three members of `ctx.project`, which the host answers (`exchange_doors.dart`): `scopes()`, the scopes `export` takes (§6.18's registry, each with its argument); `export(scope, arg?, options?)`, the film as the viewer has it in use, as one scope selects it, in exchange 1 — kept under its `export_id` for the call, at most four, or for the assistant's operation; and `import(document, options?)`, which plans a document against the versions in use and queues it for the person's review, answering the plan (`ImportAnswer`: the state, the proposal's id, and per patch its action, target stem, paths, removals, notes and problem — ids, paths and codes, never a document); `options.base` names a kept export and `dryRun` plans without proposing. The contract lists the codes and kinds the package raises (§6.18) and the rule that makes the lists safe to grow: a problem code a plug-in does not know is a refusal, a note kind it does not know is information. The outcomes of the person's apply never cross the door. Exchange 1 is bound to these doors for as long as they exist. Their refusals are a code and a reason: `scopes` `refused`/`noProject`; `export` `badArgs`/`scope` and `arg`, `refused`/`noProject` and `tooLarge`; `import` `badArgs`/`document` and `base`, `refused`/`noProject`, `otherFilm`, `noViewer`, `inCheck` and `tooLarge`. An answer is bounded at 8 MiB of UTF-8 (`exchangeAnswerMost`) and the reason stays `tooLarge` whatever the size; a request is bounded by the engine's 16 MiB. `filmopen_js` names the three doors in `doorNames` and the prelude.

**The exchange binding and retained exports.** The film and the viewer are the call's binding (§6.11): the three doors read the bound film for the bound viewer and nothing of another. **A door proposes and never writes**: `import` plans with the bound film's guards and holds the proposal through the state's seam, `ImportProposals.add`, with its origin — the plug-in's tag, the function and, under the assistant, the operation — and an id of the door's own (`p-` and sixteen hex digits, never derived from the content); the person's *Apply* is the only write. The answer is measured before the proposal is held, so an answer refused `tooLarge` leaves none behind, and the size goes to the log as `plugins.exchangeTooLarge`, never into the reason. Every running plug-in call may use the ordinary exchange doors; `import` remains refused `inCheck` in a check. Ordinary exports are kept on the chain's top frame (`CallFrame.keptExports`): at most four distinct `export_id`s, the oldest dropped and an export repeated moved to newest, released when the top call ends. Under an assistant operation, exports are kept by `ImportProposals.retainExport` under its `operationId` and go with it (`release`). A document carries a file's notes wherever its projection carries the whole content (`whole`, `everything`). Each dispatch logs `plugins.exchange.start`, then `.done`, `.refused` or `.failed`, with the plug-in, door, operation, arguments, answer or failure, and elapsed milliseconds.

A plug-in is one folder — `plugins/<tag>/` in the shared library, or `<tag>/` in a developer's configured development folder — holding its manifest `pg_<tag>_<author>_v<n>.json`, its code `.js` beside it, `l10n/<locale>.arb`, and optionally `README.md`, `platforms/<id>.json` and `assets/` (Project Specification §14.4). `plugins/README.md` is the reference a plug-in's author and a coding agent work from — where a plug-in lives, the roles and the names, the manifest field by field, **every member of `ctx`** and **every function a plug-in may expose**, each marked *built* or *planned*, then the limits, keys, servers, calls, strings, trust and the developer page. `plugins/REFERENCE.md` holds the shapes — every function with its arguments, its answer, its example, who may call it and whether it is built — and `plugins/filmopen-plugin.d.ts` says the same in types, with what is planned in a namespace of its own so that nothing there reads as callable; both are **generated from the interface definition** (below), and the plug-ins repository's `template/` is the plug-in to copy. **The generated documents are read against the definition by a test** (§12, `reference_test.dart`) and **the host against it too** (`contract_test.dart`): every door `filmopen_js`'s `doorNames` lists is a member of `ctx` and none is missing, what a running call is given is what the definition says `ctx` carries, and the arguments the host builds for a function are valid against that function's own `args`.

A manifest may provide `docs`, a guide path such as `/docs/platforms/comfyui/`. It starts with `/docs/` and has nonempty segments of letters, digits, hyphens or underscores, with an optional trailing slash. A scheme, host, query, fragment, backslash, percent encoding, dot segment or repeated slash is refused: the field is reported and omitted, and the rest of the plug-in remains usable. FilmOpen supplies the documentation origin for the build, `docs.dev.filmopen.ai` in development builds and `docs.filmopen.ai` in release builds; a package cannot select a different host.

**The contract, as data** (`plugin_api.dart`; its checker `JsonShape` is the format package's `json_shape.dart`, beside the records it also holds a model's content to, re-exported by `filmopen_plugins`' barrel). `plugins/filmopen-plugin-api.json` is the one place the interface between the app and a plug-in is written: `$defs` (the shapes that recur), `everyPlugin` (`status`), `interfaces` (each with what a manifest adds when it declares it, and its functions — required or not, who may call it, `args`, `returns`, an `example`, a state and the revision it arrived in), `beyondInterfaces` (actions and offers) and `ctx`. It is **JSON Schema, draft 2020-12, in the keywords it uses and no others** — `type`, `properties`, `required`, `items`, `enum`, `const`, `oneOf`, `additionalProperties`, `minimum`, `maximum`, `description` and `$ref` into `$defs` — so that a standard validator reads it as it is: `JsonShape` knows exactly those and `anyOf`, `minItems` and `maxItems`, which the format's records use (§5), **refuses a keyword it does not know** where a schema is read (`JsonShapeException`, naming the keyword and where it is), and reports a wrong value **by its path** as a code and never a sentence (`outputs[0].mime: missing`), a `oneOf` answering with the problems of the shape that came closest — of the shapes the value's own tags leave, the one with the fewest problems, a tag being a property that two or more of the shapes hold to fixed values in their own properties, such as `state` or `kind`, which rules out a shape whose values the value's is not where another shape takes it; a `oneOf` inside a shape chooses within it — so that the path is one an author can go to. An `integer` is a number with no fraction, as a standard validator reads it. `PluginApi.parse` reads the file whole and refuses it whole: every `$ref` resolving, every function carrying its arguments, its answer, an example, its state, its `since` (never after the file's own `revision`) and who may call it, and **every example valid against its own arguments**. **The app reads it as an asset of its own** — `plugins/filmopen-plugin-api.json`, bundled beside the stock plug-ins — at the host's first load; a build that cannot read it runs no plug-in and says so in the log (`plugins.apiMissing`, `plugins.apiUnreadable`) rather than reading manifests against a contract it does not have, and a test of the root package pins the asset. `ctx.api` is the file's two numbers, `{ api, revision }`, so that a plug-in asks for a door only where the revision says it is there, and `ctx.caller` is `{ tag, stem }` of the plug-in that asked, **null** where the app or the person started the call. **The contract** settles `options` with its per-stack readiness and quote, a job's `pending`, `collect` and `cancel` under `ctx.job`, media sent by a descriptor's `grant` (`ctx.upload`, an `HttpRequest`'s `embed`) and inline outputs kept behind `ctx.stage`'s handles, a call's `Destination`, `Usage` with its `Billing` basis, and four interfaces — `reference-analysis`, `style-analysis`, `voice` and `server-provider`; three members of `ctx` are built already: **`ctx.now`**, the host's clock in milliseconds when the call started, **`ctx.job`**, the render job a call belongs to — its render, its collect, its cancel, and every call they make — and null for any other, and **`ctx.features`**, what the host bridges for a plug-in — nothing: it answers an empty object, a server provider implementing `server-provider`, and no inline output is bridged. `ctx.stage` and an output naming a staged handle are built, as *The film's media coming back* says; `ctx.upload` and a request's `embed` are built, as *The film's media going out* says; an answer's `usage` and its `billing` are recorded as §6.7 says, a failure's too. **The `lifecycle` interface** holds `onEnable`, required of a plug-in that declares it, and `onDisable`, both called by the app alone, with `LifecycleEvent` and `LifecycleResult` and the manifest's `discovery` routes. The app shows four members of `Status.details` (*Turning a plug-in on and off*, below). A function of the definition is never taken as an offer, so an offer of one of the capabilities' names is refused (`reservedOfferNames`), and the server provider's functions have names no platform's offer uses. **`plugins/filmopen-plugin.d.ts` and `plugins/REFERENCE.md` are generated from the definition** by `python3 scripts/gen_plugin_api.py`, never written by hand, and its `--check` runs in `scripts/test_all.sh` and `scripts/test_all.ps1`; `plugins/README.md` stays the guide, written by hand, and **states no shape the reference does not**: every shape it writes outside its examples, a function's arguments among them, is one of the definition's objects — whole unless it says `…`, each field optional exactly where the definition says — and it names neither `hooks` nor `provides`, which `reference_test.dart` holds it to.

**What a manifest declares it implements**. `implements` is the one place a manifest says what the app may call it for — `{ "render": { "platform": "comfyui", "models": ["t2i-z-image-turbo"] } }` — and `hooks` and `provides` are unknown fields, reported as any other (`unknownField`) and not read. Each declared interface is read **against the definition**: one it does not know is reported by name (`unknownInterface`) and left out with the rest working; one declared without what that interface must add — `render` with no `platform` — is reported and left out, since the app could neither route it nor say where it goes; a declared value of the wrong shape is reported by its own path, the definition's `declare` schema deciding. `ImplementedInterface` carries the platform, the catalogue entries it speaks for (an id the catalogue lacks is kept and said on its page) and **the functions the interface holds that this build can call** — a function the definition marks `planned` is listed nowhere, the developer page's list included — copied from the definition as the manifest is read, so that the host asks `implementsFunction('render')` without the definition in hand. What another plug-in may reach (§3.3) is `plugInsMayCall`'s, read from the definition at each call: the functions of those interfaces whose `calledBy` names `plugins`, and every plug-in's `status`. **`minRevision`** is the least revision of the contract the plug-in needs; above this build's, the registry drops its code, the plug-in is **listed with `needsNewerApp` and does not run**, and its page says which revision it asks for — a sentence drawn only where the revision is past this build's, so that a plug-in which cannot run for another reason is never told it needs a newer FilmOpen. The contract is revision 1, and an absent `minRevision` is read as 1. **A plug-in reaches its `render` and `voice` functions only when `minRevision <= api.revision`** (`admitsRevision`), checked at the one guard every road to a call passes — a person's call, a capability, a render job and the developer page each name the interface they resolved, and an offer, which can carry neither, names none — before anything is sent, and a contract not yet read admits none; every plug-in read is logged at info, `plugins.revision.admitted` or, listed `needsNewerApp`, `plugins.revision.refused`, and a call refused at the guard `plugins.revision.refused`, each with the revision needed and had, the decision, its reason and its code (and, at the listing, the read's milliseconds), and the registry's read line carries every plug-in's. The floor below which a package that declares `render` or `voice` is listed with `updateRequired` (*Update required: written for an earlier FilmOpen.*), keeping its code and its other functions, is revision 1, so that no package is listed so today. **`capabilities.upload`** lets a plug-in send the film's media a call of it is handed, through `ctx.upload` and a request's `embed` (*The film's media going out*, below): consent names it — *only the pictures, clips and sounds FilmOpen hands to a call it takes part in, never another file of your film* — and the plug-in's page says the same; a plug-in without it is refused `noCapability`, by either door. **`x`** is anybody's: kept as written, reported never, shown nowhere. An **offer** may carry `args` and `returns`, schemas of the kind the definition writes, which the developer page holds a call to; one this checker cannot read is reported and left out, the offer still readable. **No offer may take the name of a function of the contract** — every interface's and every plug-in's `status` — nor a name the language gives every object, nor a function one of the plug-in's own actions calls: a function of an interface is reached because the manifest implements that interface and the definition says who may call it, never because it was offered.

**The render container.** Every render result, including voice design and speech, and each of its outputs, carries a `metadata` container: an object with an integer `v`, complete at every answer and never a delta, holding no credential, authorisation header or expiring address. Each output adds its provider `id`, its `seed`, `role` and `mime`, and `width` and `height`, integers where present. `render`, `designVoice` and `speak` take `stage` (`prototype`, `draft` or `final`) and, where they continue a take, `from`, the take's complete descriptor, both optional in the definition; a plug-in that rebuilds its arguments keeps both. A failure answers `error` with a `code` and a `message` a person can read. `KeyInfo` adds `usable`, `mode` (`own` or `funded`) and `reason`, so that a plug-in asks the door whether it may call and never refuses on `hasKey`; the host answers them at the `keys` case from the person's own key — `usable` a key stored and allowed, `mode: own`, `reason` absent where usable, else `needsKey` where none is stored and `grantDenied` where one is stored and not allowed — the funded route later. The manifest may declare `sharing`, the operations it could offer to others with their unit; `PluginManifest.sharing` reads and checks it, a wrong shape — `scale` without `character` among them — one `wrongType` at its path; lending (*Lending*, below) acts on its `render` operations. The current shapes are required: `options` answers `stacks` and `params`, and an output is an `https` address, a path on a server the person named or a `ctx.stage` handle, never `data:`. The describers (`fo-openai` and `fo-fal`) implement `reference-analysis` and `style-analysis`.

**Exposed offers, and the text tool-turn shapes.** An offer (`OfferSpec`) may carry `expose`, a public kebab name (`^[a-z0-9][a-z0-9-]{0,47}$`, declared by its author, since an offer's own name is camelCase; a second offer of one plug-in exposing the same name is `badEntry` and reads unexposed, as does a name of the wrong grammar), `description`, a string key resolved as `label` is (at most 4,096 characters; `label` serves without it), `effectful` (default true: the call takes an operation key, not a consent) and the annotations `readOnly` and `destructive`; beside the parsed `args` and `returns` it keeps the raw maps (`argsSchema`, `returnsSchema`), only where they read. `ExposedOffers` (`exposed_offers.dart`) registers, on every change of the host, each enabled plug-in's offers with `expose` and a raw `args` as commands of the state's `CommandRegistry` (§7.3), replacing the plug-in's commands whole, so that one turned off or removed has none: `source` the plug-in's tag, `name` the `expose` value, `exposed: true`, the flags from the offer, the title from `label`; the input is the envelope `{input, session, operation}` with the offer's raw `args` under `input` as it is, closed to anything else (a non-effectful offer's has `input` alone), so that the offer's own fields are never read as controls; an `outputSchema` only where the raw `returns` is an object schema. An offer without a readable `args`, one whose resolved description is too long, and every offer of a plug-in tagged `builtin` or `app` (the app's own sources) are skipped (`plugins.exposeSkipped {tag, name, reason: schema|description|reserved, description}`), and a registration the registry refuses is logged with its tag, name, code and the registry's words (`plugins.exposed.refused`); the plug-in loads and runs as before. The command's handler re-reads at dispatch that the plug-in is on and the offer still exposed (`not-enabled`, `not-exposed`), then runs it through `HostPluginRuntime.runExposed`, which **binds the run first, then waits its turn** — its plug-in's one call at a time, for at most 30 seconds, then one of the app's slots, as every call does — **then passes the registry's effect gate** (`admit` for an effectful offer; `check`, which admits nothing, for the others, so that a caller gone or a deadline passed runs nothing), **then runs with that binding**, nothing awaited between the gate and the start: an authority change before the gate is refused there and nothing runs; one after it cannot reach the binding, and the admitted effect runs to its end under the plug-in's own wall time, the caller's deadline being the gate's. Two calls of one plug-in at once thus run one after the other; a call still waiting at the bound answers `busy` having admitted nothing, so its operation key runs on a later call (`plugins.exposed.wait {ref, ms, gotTurn}`, with the outcome's code on every way out without the turn: `busy`, `disabled` when the plug-in is turned off while it waits, `cancelled` when the call is stopped while it waits, or a refusal before the wait). The run is otherwise an action's: its own frame and usage chain, `ctx.caller` null, a nested `ctx.call` under its frame; it may spend through any door the host has, at any price, recorded by the usage chain as for the person's button, and nothing is added to stop it. Only `input` reaches the function. A done answer is held to the offer's `returns` by its `JsonShape` — a breach answered `bad-answer` and logged with each problem and the answer (`plugins.exposed.badAnswer`) — and answered as `structured` (an object as it is, any other JSON as `{value}`) with the JSON as text; a failure answers its code, and a `refused` one its fixed reason beside it (`{error: "refused", reason}`), which the `done` line logs too. Each registration logs `plugins.exposed.register.start {plugins}` with the stems, one line per offer — `plugins.exposed.accepted {tag, name}`, `plugins.exposeSkipped {tag, name, reason, description}` or `plugins.exposed.refused {tag, name, reason, error}` — and `plugins.exposed.register.done {count, skipped, refused, ms}`, or `plugins.exposed.register.failed {type, error, ms}` on an unexpected throw, the next change registering again. Each call logs `plugins.exposed.call {ref, tag, name, input, enabled, exposed}`, `wait {ref, ms, gotTurn, outcome?}`, `frame {gated, admitted}` and `done {ref, outcome, reason?, answer?, message?, usage: done|unknown|none, ms}`, never the session. **The text tool-turn shapes** are defined beside `Message` and `CompleteResult`, which do not change: `ToolTurnMessage` (an assistant's tool calls, a tool's answer by `tool_call_id`, or a message as `Message` has it), `ToolCall`, `ToolSpec`, `ToolCompleteOptions` (`tools`, `tool_choice`) and `ToolCompleteResult` (text, tool calls or both); nothing passes them yet, and their limits — an id of at most 64 characters — are written for the loop that will hold them; the loop bounds neither the count nor the size of its tools. A `$defs` entry carries no `since`, so each says its revision in its description.

**The catalog assistant and tools in the text interface.** An assistant declares its required catalog in `implements.assistant.catalog`, a path under `assets/` (format 1, §6.11a), and exposes no assistant functions or catalog hooks. The host reads the declared catalog first and `x.assistant` (`version: 1`) only where the manifest declares none. A refused declared path or shape is not retried through `x` (`assistant.catalog.refused {location: manifest.implements.assistant.catalog}`). Each model call logs `assistant.turn.call {session, turn, call, started, route: key|credit|none, requestBytes, messages, replyBytes, hasText, reply, toolCalls, outcome, finish, units, ms}` — `finish` the model's own reason for stopping as its answer gave it (the provider's own word: `stop`, `length`, `tool_calls` on a chat-completions route, the response's status, such as `completed`, on OpenAI's Responses; null where it gave none), so that an answer cut at its length shows (a provider refuses one as `cutOff`, logged `length`) — the session id as it is, the messages sent and the reply whole, and the call's start time, so that it sits beside the HTTP door's `plugins.http.stream.open` or `.whole`; each tool `assistant.tool.call {turn, call, ordinal, id, asked, arguments, argumentsError?, tool, source, name, effectful}` and `assistant.tool.output {outcome, bytes, reason?, output?, ms}` (`outcome` `ok`, `bad-call`, `not-run`, the code the command refused with, declared or not, as the registry's `command.call.done` records it — `error` only where it gave none —, as the voice road's; `output` what the model is sent, whole; absent where the tool did not run) beside the registry's own lines; the turn `assistant.turn.start {sessionId, input, messages}`, its `messages` stage with `requestBytes`, `maxOutput` and `maxOutputFrom` (`catalogue` or `none`), and `assistant.turn` with `turn`, `calls`, `toolCalls`, `requestBytes`, `reply`, `display` and `ms`; a failure, `assistant.turn.failed {stage, type, error, ms}`, the error's message in `error`; why a turn stopped, written where it fires before the cancel, `assistant.turn.cancel {reason}`: `stop` from the person's Stop, `stale` with `staleReason`, the session's lines with `session` and `turns`, `stop` and `stale` with `busy`. Not guarded, by design: no retry, no second model, no tool shown in the dock, no bound on the calls one answer asks for, a model that keeps calling tools that succeed, or is refused in ever different ways (the person's Stop ends it); *Apply* keeps its one call with no tools. A close asks no model (§7.4), and a request of any phase but `start`, `turn` and `finish`, `summary` included, is refused `request`. A film left or the quit during a close logs `assistant.turn.cancel {reason: leaving, running}`, cancelling a turn begun since the close began where `running` says one is (a close's own cancel of the turn under way is `close`); while a tool runs, the backend's `inFlight` is that registry call, which a close lets settle.

**`status`, required by the contract and never a reason to refuse a plug-in**. The seam's `checkStatus(stem)` runs the plug-in's `status` with `ctx` alone and **holds its answer to the definition** before the app reads it: `PluginChecked` with one of the four states (`ready`, `unconfigured`, `unavailable`, `degraded`), the plug-in's own message and the four facts of its `details` the app shows (`PluginStatusDetails`, below); `PluginSaysNothing` where the code has none — *this plug-in does not say whether it is ready, which api 1 asks of it* — after which its other functions still run, since no app can know a function is missing before it has run the code; `PluginCheckFailed` with the call's own outcome, a shape the contract does not hold being `badResult` **with its path**. It starts no render, spends nothing and installs nothing, and runs **only on a person's gesture, or an agent's**, and for this computer's render engines — each enabled plug-in implementing `platform` that renders on a platform of kind `local` itself or that a plug-in rendering on one calls (`localPlatformsOf`, which logs why each platform plug-in is one or not) — once at start, in the background when the plug-ins have loaded, and on each arrival on the GPU page (`refreshLocalStatus`, reason `start` or `refresh`, §9.7a), logged `plugins.status.refresh.start` and `.done` with the state, the plug-in's words and details, a failure's code, reason and path, and the time, never on a timer: the app draws *Check* (`plugin:<tag>.check`, the answer `plugin:<tag>.status`) on every plug-in's page, and a list of plug-ins calls nothing. **A check may not reach `ctx.ai.complete` or a platform's `run`, nor may any plug-in a check calls, and a `status` is a check however it is reached** — an action's `ctx.call` too — the chain's frame carrying it (`CallFrame.inCheck`) and the door answering `refused`/`status` (`run`, and the road through an action too) — since the app presents *Check* as an inspection and that is the one door that always costs money; its own key, its own server and another plug-in's `status` stay open, which is how it answers *is my key there, does my server answer*, and what those cost is recorded as any call's is. *Check* is disabled with its reason while the plug-in is off, and while a check or turning it on or off is under way; what it finds is the runtime's record (*Turning a plug-in on and off*, below), drawn on the page and on the plug-in's card in one wording — `ready` in green, `degraded` in amber, `unconfigured` and `unavailable` in red, always with words and a mark — and **the plug-in's words are left out once the language changes**, half the line being the app's and half the plug-in's, an answer that lands after the change included. The log carries `plugins.checked` with the state, the message and the details as the answer holds them, or a failure's code, reason and message.

**Turning a plug-in on and off** (`plugin_lifecycle.dart`, `host_runtime.dart`, `ctx_doors.dart`). A plug-in that declares the definition's `lifecycle` interface is told when the person turns it on or off, each time and only then: `setEnabled` and *Allow* (`allow`) are the two roads, and the app's start, a reading of the plug-ins again, a stock install, a change of files and a redraw call nothing. **A call of the same value is no operation** — nothing written, nothing read again, no hook — measured against the value last accepted or, with none pending, the switch as the registry has it. An accepted Off-to-On shows *Checking* at once (`PluginReadiness.phase` `enabling`), writes the switch, reads the plug-ins again, and then runs `onEnable` once, told `{ operationId, reason }` — an opaque random token and `toggle`, `consent` or `retry` — **only on what the registry published on**: where the reading did not turn it on (its new files ask *Allow*, or the reading failed), nothing runs and the problem `notPublished` is kept. **A reading another switch or a grant let go is read again first**: that switch starts its own reading only once its write has landed, so nothing may have been published since this On was written. The plug-ins are read again — twice at most — only while no reading begun after the On was written has been published, so that a plug-in that came on is never said not to have, while one a published reading left off (its new files ask *Allow*, it cannot run, its switch was not saved) is said at once; a reading that failed published nothing, and is tried again with them. An accepted On-to-Off is **at once**: the registry's view of the plug-in is off before anything is awaited (`RegisteredPlugin.switchedOff`), so a call asked for is refused `disabled` and one waiting for its slot is refused when it gets it, while one under way runs to its end; a probe or a *Check* of that plug-in under way is stopped; and one bounded clean-up is put in line, run by **the version that was on** — its consented code and grants, captured as Off was accepted — the one call the runner makes without asking whether the plug-in is still on (`stillOn`), which only that clean-up skips. **A plug-in that was never on, as the registry had it** — an On whose reading had not published it yet when the Off came — has nothing to tidy: no clean-up runs, and no problem is made of it. The switch's two preference lists are written one switch after another, in the order the switches were accepted. **A switch is held over every reading until its write lands** (`_unwritten`): the switches being written one at a time, a plug-in whose Off or On has been accepted and not yet written is published off by every reading, one already under way when it was accepted included, whatever the preferences it reads say meanwhile — an Off refuses ordinary calls and runs nothing from the moment it is accepted, and an On is on only once its own reading, begun after its write, has published it, before its `onEnable` runs. **A switch that cannot be written holds only while it is the latest operation**: one accepted while it was written decides, and an *Allow* of a plug-in already on changes nothing. **An Off that cannot be written holds for the session** all the same, as a hung plug-in's does, since its clean-up has run and a reading would otherwise publish it on again with nothing having told it, and it is said on the plug-in's card (`PluginReadiness.switchNotSaved`) beside whatever its clean-up leaves unconfirmed, until its next accepted operation. **An On or an *Allow* that cannot be written** holds the plug-in off for the session too — the preferences keep a value in memory before the disk takes it, so a reading would otherwise publish it on whatever the disk kept — and is said as that, its switch not saved (`PluginSwitchNotSaved.on`), never `notPublished`, since nothing failed to be read. **Per plug-in, everything runs in order** (`PluginLifecycles`): a clean-up always ends before a later `onEnable` begins, neither is dropped for the other, and an `onEnable` that an Off overtook before it began never runs; an `onEnable` waits for the plug-ins to be read again **outside** that line, so that a clean-up an Off puts in line meanwhile never waits behind a reading. Off holds whatever the clean-up answers.

- **Each lifecycle call keeps its mode** (`CallMode`, `CallFrame.mode`), whoever calls it — the app or the developer page — as a `status` is a check whoever calls it. Both lifecycle functions use the ordinary `ctx` API with its authorization, input bounds and `inCheck` spending guard. HTTP uses the ordinary transport, bounded by the operation's remaining time and closed when the operation stops (`PluginHttpDoor.send`'s `abort`). `implements.lifecycle.discovery` is optional metadata, not a separate HTTP gate.
- **Bounded in all** (`enableBound`, 10 s; `disableBound`, 5 s), from the hook's own start in the plug-in's line — behind what was asked of the plug-in before it, each bounded in turn, a probe an Off stopped ending within its grace: the wait for the plug-in's turn behind a call under way and for one of the five slots, the run, and the grace a stopped call has to end (`lifecycleGrace`, 1 s), **held inside the bound rather than added after it** — the call is stopped a second before the bound, its JavaScript wall set to the same, its requests closed with it and each request's own timeout set a quarter of a second past the stop, so that the stop decides. The host waits for the runner's own answer — a call that does not stop answers `hung`, at the bound — until a grace and a quarter of a second past the bound, and takes the call as timed out only where the runner has not answered by then, so that a hang is never said as a timeout. **Whatever comes after the stop is the stop's** — a refusal of the request it closed, an answer the plug-in made of that refusal — so a server that never answers is said one way every time: `activationTimedOut` or `cleanupTimedOut`, a clean-up not confirmed, never a success. One that does not stop when stopped is turned off for the session as any hung call is (`activationHung`). A call under way is never stopped for a clean-up.
- **What a hook answers** is held to the definition's `LifecycleResult` — `succeeded` with the `Status` it may carry, or `failed` with its `Problem` — and then read. A function the code leaves out is the neutral outcome, never *Ready*. A throw, a refusal or a shape the definition does not hold is `activationFailed` (or `cleanupFailed`) with the call's code, its path for `badResult`, and the plug-in's words for a throw; a `failed` answer keeps its problem's code as it is, its words, and the status it carried. **A failure keeps the person's On**, says what went wrong, and offers *Try again* (`retry`), which runs `onEnable` again, told `retry` — or *Check* again, where it was a check that failed; a plug-in that hung or did not come on is off, and its switch, or *Allow*, is the way back.
- **What is known** (`PluginReadiness`, the seam's `readiness(stem)`): the phase, whether the plug-in declares the interface, its last fact — the state, its words and the four facts of `details` the app shows (`PluginStatusDetails`: the service's version, the graphics card, its memory and the computer's, each copied by its type, one absent unknown and never zero) — and its last problem. **A plug-in's words reach a screen cleaned** (`pluginWords`), a status's message, a failed answer's and a throw's alike: at most 300 characters — code points, so that a cut never parts a surrogate pair — cut with an ellipsis, with control characters and the marks that embed, override or isolate a direction made spaces, runs of space made one, and half a pair standing alone, which no text can draw, made U+FFFD — only as much of the text read as the characters kept need; a detail's text over 200 characters is left out, as unknown. It lives in memory and **is unknown at every start**. **A fact said under another identity no longer holds** — how many times the plug-in's configuration changed in this session (a setting saved, a grant, its code read anew: `PluginLifecycles.reconfigured`, which drops what was known at the change itself), its files (its consent hash), its grants, its settings on this computer, and the records of its keys that are saved, so that a change undone is a change still and a key saved again, checked again or removed and saved is another — and is dropped for good, never asked again, as is a failure of turning it on or of a check (`activationFailed`, `checkFailed`, a check that ran out of time among them), which was what the configuration before came to; another language leaves out the plug-in's words and keeps the state; an answer of an operation a later one overtook, or of one whose identity or language changed while it ran, is never kept; and a timeout or a hang of turning it on, a clean-up not confirmed and a reading that did not publish it (`notPublished`) stay until the next operation that succeeds. *Check* publishes into the same record (phase `checking`), so the card says what the page found; **a check that finds no `status` keeps what turning the plug-in on found** under the same identity, since a provider's guidance is not lost to a check its code cannot answer.
- **The host fixtures** (`packages/filmopen_plugin_host/test/fixtures/lifecycle/`) are the contract's examples, not shipping plug-ins: `fixture-comfy` declares `/system_stats` on its `server` setting and answers what a ComfyUI measured there — its graphics card (trimmed of the service's device index and allocator), that card's memory, the computer's and the version — or where to look when nothing, or something else, answers; `fixture-salad` asks only whether its key is saved — in its `onEnable` and in its `status` alike, so that a *Check* says it again in the reader's language — and sends the person to Provider keys, with no request at all. Both have `onDisable`, both say `minRevision` 3.
- **The log** says `plugins.lifecycle` with the stem, function, operation token, reason, outcome, code or state and failure message, and `plugins.lifecycleRetry`. The plug-in's words and addresses are logged as given; credentials never enter it.

**The manifest** (`plugin_manifest.dart`). `PluginManifest.parse(json, api:, knownPlatforms:)` never throws. It answers a `PluginManifestParse`: the manifest, or null when the plug-in cannot run on this host, and every `PluginIssue` found — a code (`PluginProblem`), the dotted field it concerns and the values a sentence needs. Refused (no manifest): a file that is not `pg`, a tag that is not a segment or is `app` (the owner of the app's own keys), an author that is not a handle, a missing or mistyped `v`, `name` or `api`, an `api` other than the definition's (`apiUnsupported`, carrying the manifest's version and the host's), and an `entry` that does not read (`badCodeFile`, carrying the path it concerns). **`entry` is a file name or an ordered list of them** (the format's §14.1): each a `.js` file of the plug-in's own folder named by a relative path with `/`, no `..`, no absolute path, no drive letter and **no segment beginning with a dot**, none twice, at most `PluginManifest.mostCodeFiles` (32) of them and `mostCodeBytes` (2 MB) in all — the last checked where the code is read, since a manifest knows no sizes. Absent, it is `<stem>.js`; `manifest.entry` is the first, for what reads one. Reported and left out, the rest read: a field the manifest does not know (the common header's fields and `plugins` are known), at its top or inside a key slot, a setting or an action — a mistyped `defualt` among them, a key slot's or a setting's `label` or `help` that is not text, a number's `min` above its `max` (both bounds left out), a hook (`unknownHook`, entity or platform), a setting type (`unknownSettingType`), a setting, action or key slot that cannot be used, a malformed key id in `uses`, an entity type the format does not know, `entitySettings` for a type `applies` does not name, a host in `capabilities.network` that is not a host name, a default of the wrong type (the setting kept without it). A key slot naming a platform no platform file defines is reported and kept. **`kind`** is `platform`, `model` or `tool` — a word for lists, which decides nothing, as a folder's kind decides nothing; the three are said in the reader's language on the plug-in's page, and another token is kept and shown as written. **The `models` of an interface it implements** (`implements.render.models`, `implements.text.models`) are the catalogue entry ids the plug-in speaks for (§14.7), since an entry's id does not always fit a tag: one that is not an entry id is reported and left out, and one the catalogue does not define is reported **on the plug-in's page and kept**, since a catalogue grows and a plug-in that names tomorrow's entry is not broken today. **`offers` and `calls`** are read as the architecture document's §4.2 has them: an offer is a plain name on the plug-in's object with a `label` — a locale key of the **offering** plug-in's strings, since it is what the *caller's* consent shows — and optionally `help` and an `example` of its arguments; one without a label is reported and left out, because consent would then say nothing about it. `calls` is `<tag>:<name>`, a list apart from `uses`, since a person reads *the keys it may use* and *the plug-ins it may use* as two things; a plug-in's **own** tag is allowed, which is how the template shows the door with nothing else installed. **A hook may never be offered**, nor a name the language gives every object (`reservedOfferNames`: every `PlatformHook` and `EntityHook`, `constructor`, `toString` and their kin), **nor a function one of the plug-in's own actions calls** — a platform hook is the app's to call with its consent and its usage records, `verifyKey` receives a candidate key the person just typed, an entity hook writes versions, `constructor` is not the plug-in's function at all, and an action is a **person's button**, with their gesture behind it, which a caller must not press for them (reference said so and nothing had enforced it). It is refused where the manifest is read **and** again at the door, since one of the two alone would be a rule with a hole. Settings (`setting_spec.dart`) are `string`, `text`, `number` (`min`, `max`), `boolean`, `enum` (`values`), `model` (`category`, `platform`) or, `server`, each with a `label` and `help` that are locale keys and a `scope` of `project` (the default) or `machine`; an entity setting has no scope. **A `server`** holds a `ServerAddress`'s normalised text and is **always machine-scoped**, whatever `scope` says — `scope: project` is reported (`badEntry`) and the setting is kept on this computer anyway, so its author learns it — and is refused under `entitySettings` (`unknownSettingType`, the field left out), since an entity's file travels as the project file does. Its `default` **may only be this computer**: an address elsewhere is reported (`badHost`) and dropped, so the setting starts empty and the box asks; one that is no address at all is `wrongType`, as any default is. `accepts` takes what `ServerAddress.parse` reads. Setting keys and action calls are identifiers, action ids and slots segments.

**Keys** (`key_id.dart`). A key's id is `<owner>:<slot>`, both segments: the tag of the plug-in whose manifest declares it in `keys`. The tag `app` is reserved for the application, which owns no key (§6.7): a request for `app:<slot>` names nobody's key. Its store name is `filmopen/<owner>/<slot>` and its preference `providerKeys.<owner>/<slot>` — the status, the date and the last four characters, never the key (§6.7).

**Strings** (`plugin_strings.dart`). A locale file is ARB-shaped and read by the format's own reader, so a repeated key refuses the file (`notLocaleFile`, as §18.1 refuses one anywhere): `@@locale` must be its file's name (`localeMismatch` otherwise), `@key` metadata is skipped, a key holding `:` is refused (`colonInKey`). `PluginStrings.t(key, locale:, args:)` reads an unprefixed key, or one prefixed with the plug-in's own tag, as the plug-in's; `app:<key>` through the application's lookup; any other namespace as nobody's. It falls back from the locale (`pt_BR` read as `pt-BR`) to its language to `en` to the key itself, reporting each missing key (`plugins.missingString`: once a session for each plug-in and key, the key as it is, since a manifest's label is looked up by its own text, which may be any sentence), and fills `{name}` placeholders, leaving one without a value as written. `textOr` shows a manifest's `name` or `description` as a key where the strings have it and as written where they do not.

**The package** (`plugin_package.dart`). `PluginPackage` — `tag`, `list`, `text(path)`, `bytes(path)` (for the consent hash) — is the one interface the loader reads a plug-in through; `SourcePluginPackage` is a folder inside any `ProjectSource`, and `SourcePluginPackage.allIn(source)` every plug-in folder under `plugins/`, sorted by tag, from one listing of the source. `PluginFolder.read(package, catalogueIds:)` reads every manifest at the folder's top (a stock plug-in and a person's fork share a folder), the locale files of the first manifest's `l10n`, and the plug-in's own platform files, refusing one for an id the catalogue defines (`platformConflict`); a folder without a manifest (`noManifest`), a manifest whose tag is not its folder's or whose stem is not its file name (`folderMismatch`), a manifest whose `entry` is not in the folder (`noCode`, the manifest still listed so that its page can say why it cannot run), a folder with no `en` locale file (`noEnglish`), a file that cannot be read as text — bytes that are not UTF-8 — (`unreadable`, with the failure's type, the rest of the folder still read), and a document that does not parse are reported by the path they concern. The code is not read. `PluginManifest.isByStockAuthor` says only that the author is `filmopen`, the stock plug-ins' handle; it grants nothing, since anyone can write under it and the template does.

**The engine** (`filmopen_js`). `runJs(JsCall, doors:, cancel:, note:, onDoorFailed:)` runs one call in an isolate made for it (`Isolate.spawn`), in a QuickJS-NG runtime made for it and freed after it — unless its isolate dies on an uncaught error, which leaves the runtime unfreed —: **each of the call's files is evaluated in order** — `JsCall.files`, a `JsSource` of a name and its text — as plain scripts of one scope in the one context, so that what an earlier file declares at its top is there for a later one and **the last file's value is the plug-in** (the format's §14.1); the function of that value is called with `ctx` and the JSON arguments (or `ctx` alone, for an action), its promise awaited, and the answer is `JsValue` or `JsFailure` with a code — `failed` (the script's own message, its author's words for the person; or, where the call's isolate dies on an uncaught error — its native library not loading, say —, `isolate: <error>; function <name>`, which the host's `plugins.failed` line carries), `limit` (`time`, `memory`, `stack`, `result`, `wall`), `cancelled`, `hung`, `noFunction`, `notJson`, `stalled` (a promise nothing can settle), `engine`; a function the plug-in does not have is `noFunction`: one the definition lets it leave out (`required: false` in every interface it implements that has it) — a plug-in's `options`, which it answers by having none — **logged once a run as `plugins.absent`**, never as a failed call, and one it must have — `render`, `status` — a failed call as before. **An action's answer of `state: 'failed'` is its failure** (`runAction`): a `PluginCallFailed` whose message is the plug-in's own — its `message` key in the person's language where its locale files hold it, else its problem's words — and whose reason is the problem's code as it is, logged as `plugins.actionFailed` with that code, else `failed`, the problem and the words; a message without that state is an answer, never a failure. A file that fails stops the load where it is, so the failure's place names that file. The C shim (`src/filmopen_js.c`) keeps every `JSValue`, the budget and the cancel flag, so Dart passes only UTF-8 strings and integer handles and no Dart callback runs inside JavaScript; `fjs_load` is called once per file, the prelude running before the first. Before the script, a prelude builds `ctx` on one host function and removes `eval`, `Function` — the global, and the `constructor` of every kind of function — and `Math.random`; the runtime has QuickJS-NG's base objects — §14.2's list and the language's other plain built-ins (`Reflect`, `Symbol`, `BigInt`, the weak collections, `queueMicrotask`, …), none of which reaches outside the runtime — and no `Date`, module loader, timer or I/O (Project Specification §14.2). The prelude captures `JSON`'s functions, `Reflect.apply` and the error constructors before the plug-in's file runs, locks `Error.prepareStackTrace` — whose call sites would otherwise hand a script the functions on the stack, the host's among them — and evaluates to the runner, which the shim holds: nothing of the host is on the global or reachable from the script. The runner reports through a host function, and the shim writes the outcome's JSON — the value by the engine's own serialiser, the message as a JSON string — so a script decides only its own value and its own `failed` message; a thrown error's `code` is kept only as `refused` or `badArgs`, which doors give, or `cutOff`, which a text provider gives for an answer cut off at its output length (kept from any operation's script, as the other two are), and `cancelled`, `limit`, `hung`, `stalled` and `engine` are the shim's and the runner's alone. A request is written to JSON by the engine's own serialiser in C, never by the script's `JSON`, so its name and id are the shim's, and the runner answers only the door names `ctx` uses; its bytes count against the memory limit until its door answers, a request is at most 16 MB and at most 10,000 wait at once. A microtask that throws outside the call's promise is dropped, not the call's outcome; a `log` or `progress` made just before a call ends still reaches its door, and no other request queued then is started; a cancel that comes before the call's isolate has started is delivered when it starts. **A failure says where it is**: the runner hands `done` the error's `stack` where `typeof` says string, the shim cuts it at 2,000 bytes and makes it JSON-safe — a quote, a backslash and every control character becoming a space, so the frames run together and stay readable — and a load-time failure, a syntax error among them, reads the exception's own `stack` the same way; Dart then takes the **first frame naming one of the call's own files** as `JsFailure.file`, `.line` and `.column`, so a `<prelude>` frame never counts and a failure with no such frame — a door's refusal, made where the door is answered — has no place. Only the text crosses over: `Error.prepareStackTrace` stays locked, since call sites would hand a script the functions on the stack, the host's among them. A script can throw an error that reads as a stack overflow, or write its own `stack`, which only mislabels its own failure, as it can mislabel its own message; the capped stack protects the process either way. Every C string is read as UTF-8 with malformed bytes replaced, and a result is measured in bytes before it is copied. `ctx`'s asynchronous members are requests queued in C and answered by the caller's `JsDoor` on the caller's isolate — where plugin channels and providers are — and a `JsDoorRefusal` reaches the script as an error with its `code` and `reason` — and, for `ctx.http`, its `stage`: `admission` where the host refused it before anything left the machine (`no-key`, `no-grant`, `no-platform`, `insecure`, `host`, `store`, `badArgs`, a usage, credit or assistant-policy refusal, and a media request's refusals before its request — its grants, its bytes, its key's road, its upload to the media store — logged `plugins.media.refused`), `transport` where it refused it once it was being sent (`timeout`, `connection`, `redirect`, `tooLarge`, a portal's refusal, `cancelled`); an answered status, a 401 or a 403 among them, is an answer, not a refusal. A plug-in passes an `admission` refusal on as the host gave it, never as an outcome nobody knows; `plugins.refused` logs its code, reason and stage. Where it ends the call, the call's failure keeps the stage (`PluginCallFailed.stage`), and `ctx.ai.complete` hands it on to the plug-in that asked; a direct describer (`fo-fal`'s `describe`, `fo-openai`'s `responses` called directly) answers it as its failure's code, so a reference analysis says the key is missing; and the assistant's turn reads it as not sent: `notSentNoKey` (*Not sent: <provider> has no key on this computer*, with *Open Settings* to its key card) for `no-key`, else `notSent`, logged `assistant.notSent {code, reason, stage, message}` —, while anything else a door throws, or an answer that cannot be encoded, arrives as `failed` with the message `door: <stage>: <error>; door <name>, args <arguments>` (`call` or `encode`) — uncaught, it is the call's failure, whose message the host's `plugins.failed` line carries, and at either stage, caught or not, `onDoorFailed` tells the host before the rejection is built, whose `plugins.door.failed` warning carries the plug-in, the function, the door, the stage, the error's type and message, the door's arguments and the milliseconds since the call began, since the engine has no log of its own; a call whose isolate cannot start is `engine`, its message `engine: spawn: <error>` with the function and the files; `sleep` is answered in the call's isolate, when it ends and never sooner — where the call has a wall, one longer than it has left is ended by that clock, whose cancel wakes it, and the call ends as the `wall` limit; `settings`, `plugin`, `selection` and `l10n.t` read the call's data synchronously, a missing string reported through a door. **Limits**: memory is counted by the runtime's own allocator, so running out is known for certain and ends the call even when the script catches it; the JavaScript stack is capped at every entry by what the current thread really has below it, less 256 KB (a 1 MB limit crashed a Linux isolate thread whose stack was smaller); engine time is counted only while JavaScript runs, never while it waits on a door, and the interrupt handler ends a call past its budget or cancelled — uncatchably; the wall clock and the result's size are the Dart side's. A cancel sets the C flag at once, from any thread, and wakes a call waiting on a door or asleep; a cancelled call that has not ended within 5 s answers `hung` and is left, since an isolate inside C cannot be killed. The host may grant one call a longer wall, up to `JsLimits.longestWall` (thirty minutes); the default remains ten minutes except for root and nested `complete`, which have no wall-clock cap. A null `JsLimits.wallTime` creates no wall timer; the runner's `noWall` takes precedence over a requested wall or a grant. `interrupt` and every other function keep their ordinary wall. Cumulative JavaScript time (thirty seconds), memory, stack, result size and cancellation grace remain unchanged, and Stop still cancels a completion. Each complete logs `plugins.call.wall` once with its plug-in, hook, null `wall`, `reason: complete`, `ms: 0` and base, requested and granted walls.

**The host** (`filmopen_plugin_host`). `lib/main.dart` installs `createPluginRuntime` into the state's `PluginRuntime` seam (§7.1) — the host where there is `dart:io` and `dart:ffi`, the seam's `NoPluginRuntime` on the web — and attaches it to the container, as the automation host is. Nothing runs at start: the runtime reads manifests and code as text and installs the stock plug-ins' files; JavaScript runs on a gesture. The host reads the app through a `HostEnvironment` (the container's, or a test's in memory).
- **The stock install.** On its first load the runtime runs `installStockPlugins` (`filmopen_plugins/stock_install.dart`) over the library with the bundled `plugins/stock.json` (`JsonAssetSource`), the plug-ins repository's packages staged at a ref (§3): a file the library lacks is copied, a stock file whose bundled content changed is replaced, a stock file the bundle dropped is removed unless the person changed it, and nothing `plugins/.stock.json` does not list is touched; a deleted stock folder comes back unless the person disabled that plug-in. The project is re-read when anything changed, since the library's index was read before the files were there. The stock set is every package of the plug-ins repository at the staged ref, installed **on** and trusted by their origin, so that their key cards stand on their pages before a key exists, except the template, installed **off** (`stockPluginsOffByDefault`). **A plug-in may ship files that are not text**: a file of a plug-in is text when its bytes are valid UTF-8 (`isPluginText`, the one rule, which `scripts/stage_plugins.py` holds as `is_plugin_text`, both checked against `scripts/tests/plugin_text/`); the staging carries any other file, such as a picture, as base64 in `stock.json`'s `binary` map (present only when a package has one), and the install writes it as its bytes and records its hash over them, so that an installed stock plug-in with pictures verifies as stock as one of text alone does; `ctx.asset` still reads text. The log says the start once with the ref and the commit (`plugins.stock.start`), each decision with the plug-in, the path, the outcome and its reason (`plugins.stock.decision`: `installed`/`new`, `updated`/`bundleChanged`, `removed`/`bundleDropped`, `left`/`personal` or `modified`, and per plug-in `kept`/`unchanged` with a count, `left`/`disabledGone` and `left`/`bundleUnreadable` with a count), each failure with its stage and the error's type (`plugins.stock.failed`; a staged binary is decoded only when it is read, so one that does not decode fails its own file at stage `read`; **every file of a plug-in is read before any is written**, so a plug-in one of whose files does not read is left as the library holds it, none of its files written or removed and its record kept, and the other plug-ins install — a plug-in installed without a file would match its shortened record and run trusted; a bundle that cannot be read as a whole ends the trail in place of the start, at stage `bundle`, with the error's type and message, `outcome: notStarted` and the time, before the reload fails, `plugins.loadFailed` carrying the message too), and the totals with the pictures' count and bytes and the time (`plugins.stock`).
- **The registry** (`plugin_registry.dart`) reads plug-ins from **the development folder**, then the shared library (§14.5). It never scans a project for executable code: `plugins/` files in a project are *Other files*, and a `pg_` document in `data/` is an entity that runs nothing. The **development folder** is a folder on this computer whose sub-folders are plug-ins — `<tag>/pg_<tag>_…json`, with no `plugins/` inside it — named by the preference `filmopen.plugins.devFolder` or, where that is empty, by the environment variable `FILMOPEN_PLUGIN_DEV_FOLDER`, so that an agent's launched build, whose preferences are new each time, needs no typing; the preference wins where both are set. It is **found first**, before the library's and under a stock plug-in's tag too, so that a working copy is the one that runs; it is never written by the app, a path that is not there lists nothing, and **it is read one level deep, one plug-in at a time** (`dev_folder.dart`'s `DevelopmentFolder`, through a `DevFolderReader` a test replaces to count what it was asked): its immediate sub-folders alone are looked at, one whose name is a tag and whose own files at its top include a manifest of that tag is a plug-in, read on its own, and any other — `docs`, `research`, `tests` — is never read and nothing below it is listed, the names at its top being all that is asked of it once, while a folder whose name is no tag — `.git`, `node_modules` — is not asked about at all; so the folder may be a repository. **A plug-in folder that cannot be read is a problem of that plug-in**, said with its path on the developer page (`devFolderProblems`) and in the log once (`plugins.devFolderUnreadable`), and every other plug-in of the folder is there as before; one that cannot even be looked into is passed over, since nothing says it is a plug-in, and said in the log once with its path (`plugins.devFolderPassedOver`), as is a development folder that cannot be listed at all, so that a folder that lost its permissions does not vanish without a word. **A plug-in found there is never trusted by origin**: it asks *Allow* like any other in ordinary use, once for each state of its files. **One installed version of each plug-in runs, whatever the film**: the stock author's highest, else the folder's highest (`plugins.registry.chosen`, at debug: the tag, the version and `stock` or `highest`). The film is no input to the reading: a pick or an official pointer on a `pg` stays a legal file, read as a document and choosing nothing; another version runs once the person removes the package and installs it. The runtime still installs stock plug-ins from the app's bundle into the library; registry discovery needs no bundle tag list or project-tag guard. A plug-in is **trusted** when **every file of its folder** is one the stock record hashed, unchanged, and the folder holds no file the record lacks (widened): it is on unless the person turned it off, and its `uses` are granted as installed. Any other is off until the person allows it: *Allow* stores `pluginFolderDigest`'s hash (`plugins.consent.<stem>`), **the SHA-256 of every file of the folder **as the source lists it** — the manifest, every code file, `assets/`, `platforms/`, `models/`, `l10n/` — sorted by path, each line the path, its length in bytes and its own SHA-256, one file held at a time; a change to any of them turns the plug-in off and asks again. **What the listing leaves out does not run**: a source reports no name beginning with a dot, nothing under `build/` or `node_modules/` and no `.tmp`, so a code file it does not report is `noCode` — the plug-in listed and not runnable — `ctx.asset` refuses a file it does not report, and `entry` may not name a segment beginning with a dot; reading one would be running what nobody allowed. A folder of more than `mostFolderFiles` (2000) files or `mostFolderBytes` (64 MB), a zip's own limits, is not read at all: unreadable, so not trusted and asking again. A workflow in `assets/` decides what runs on the person's own computer as surely as the code does, and a plug-in's own `platforms/*.json` is inside the hash. Files are hashed by their bytes, so a picture in `assets/` counts; one that cannot be read hashes as a line no readable file can write — never as the empty file somebody may have allowed — and the registry lists it as a problem (`unreadable`) on the plug-in's page; it also breaks trust, since a file outside `files` would otherwise slip past the record's count. The preferences are `plugins.disabled`, `plugins.enabled`, `plugins.grants.<stem>` (key ids), `plugins.consent.<stem>` and `plugins.prefer.text` / `.media` (a tag). A key's platform is its owner's declaration, and only an enabled owner's: a disabled owner's key cards are gone from its page, so its keys are nobody's to send. The keys a plug-in may send are its own slots and each granted `uses` whose owner is enabled and still declares it. **A plug-in's own `platforms/*.json` names a platform for the app only while that plug-in is on, and never decides where another's key goes**: a key is sent by the catalogue's file, else its owner's own — a folder nobody had allowed, read first, used to decide where every key on a platform the catalogue lacks was sent. A plug-in one of whose calls hung (it did not end within the grace after a cancel; its isolate cannot be killed) is off, without touching the preferences, until the app starts again or the person turns it on or allows it again — their choice, which may leave a second hung isolate beside the first. Consent to other files than the ones allowed before takes back the keys granted then.
- **What the seam answers.** `plugins` (summaries in the app's language: name, description, origin, enabled, consent, grants, hosts, **servers** — each `server` setting's words and the default it starts with, which consent says in one line — types, hooks, machine fields with their values, actions, problems); `keyOwners` (the key cards' owners: each enabled plug-in's slots; the app owns none, §6.7); `sectionsFor(type)` (each enabled plug-in's `entitySettings` for an entity type, or its project-scoped settings for the project file); `providers(hook)`; and the changes — `setEnabled`, `allow`, `setGrant`, `setMachineSetting`, `setPreferred`, `installArchive` (a zip's text files, by the same rule, written as text and anything else, a picture in `assets/`, as its bytes) — each logged (`plugins.enabled`, `plugins.disabled`, `plugins.granted`, `plugins.settingChanged`, `plugins.preferred`, `plugins.installed`). An install from a file says its start with the file's size (`plugins.install.start`), the plug-in and each file's size it read (`plugins.install.read`) and each file it wrote, with its target (`plugins.install.wrote`), and its end with the stem and its time (`plugins.install.done`); a refusal is `plugins.install.refused` with the step, the code, the field, the problem's `args` (a reader's error text), the reason — the problem's sentence, `no-library`, `library-read-only` or `tag-present`, with the tags present — and the time; a failure is `plugins.installFailed` with the step, the target being written, the error's type and message and the time, and the person is answered that the install failed — `writeFailed` for a failed write, `failed` for any other step. Where every file was written and reading the plug-ins again failed, `plugins.loadFailed` says why, `plugins.installFailed` follows at the `reload` step with the reason `registry-reread-failed` and the files written, no `plugins.install.done` is logged, and the answer is `reloadFailed`. A machine setting accepted during a reload survives that publication: its exact tag/key value or removal overlays each fresh loaded-tag map, latest accepted edit per key winning and unrelated disk fields retained, until a winning reload begun after the successful write publishes; a known failed write forgets its own edit.
- **Calls between plug-ins**. `ctx.call('<tag>:<name>', args)` runs a function another plug-in **offers**, or one of an interface it implements that the definition says plug-ins may call (`platform`'s `run` and `request`, and every plug-in's `status`) — by name and never by a handle. Never `verifyKey`, `transform`, `render` or `complete`, which go through the app so that they are routed, recorded and paid for as the person's, and never a function one of the plug-in's own actions calls: the manifest's reader drops such an offer and **the door refuses it again, reading the contract itself** (`plugInsMayCall(api, manifest, name)`, the one rule both use), so that neither half alone is a rule with a hole. The function runs **as its owner** — its settings, its server, its storage, its keys, its own engine time and memory — and `ctx.caller` is `{ tag, stem }` of the plug-in that asked, **null** where the app or the person started the call; the caller receives the JSON it answers and nothing else. Refused with their reasons: `no-grant` (not in the caller's `calls`), and **which cause it was** (the code stays `refused`): `notInstalled` (no plug-in of that tag), `notEnabled` (off — the cause a person can act on), `cannotRun` (on, and unable to run: a code file missing, a newer FilmOpen needed — never told to turn on what is on) and `notOffered` (it answers no such function: not an offer, not a function of the contract plug-ins may call, an action's own, or a name every object has — so an action, a hook that is not offered and `verifyKey` can never be called), each with the app's sentence as the refusal's message, `cycle`, `depth`, `keyCheck` and `callerEnded`; and `serverSession`, in the app's words, for a server provider's `deploy` and `wake` — refused on every road to a call, an action and a hook as well, since only a server's own screen — *Start server* on the GPU page's *Servers* tab — may start one (§9.4a). **A declared call is allowed by *Allow* itself: there is no tick and no store of grants** — what takes a call back is what takes the plug-in back, its switch or files that changed — and consent names every call **grouped by the plug-in called and said in that plug-in's own words**, saying so where it is not installed. `ctx.ai.complete` follows the same frames and is no longer refused merely for being nested; what refuses a provider whose `complete` falls back on `ai.complete` is now the cycle rule, which still allows the assistant's *Ask* (`ask` → `ai.complete` → its own `complete`). **A nested call that did not do its work is logged** `plugin.call.refused` — the caller's tag, the callee's and the function as asked (the name as given where it is not `<tag>:<name>`), the arguments, `answered` (`refused` where a gate of the call refused it — no grant, not installed, not on, cannot run, not offered, a cycle, the depth, the caller ended, a key check — or its callee threw; `failed` where it answered `state: failed`), its code and reason as they are, the refusal's or the answer's message and the milliseconds; the answer itself goes back unchanged.
- **A frame per call** (`CallFrame`, `plugin_call_runner.dart`). A frame knows its parent, so a chain is a list: `depth` is 1 for the call a person started and at most `mostFrames` (4) — the expected case is three, the app calling a model plug-in's `render`, which calls the platform plug-in's `submit`, which may call a base plug-in; `onChain` refuses **that function of that plug-in** where it is already on the chain — another function of a plug-in already on it runs, since `A:f → B:g → A:h` is not a loop. **The turns are per frame and never per chain**: one `Turns` for a chain would deadlock the moment a nested call made a call of its own, the parent holding the turn its grandchild waits for. A frame's model completions take up to `mostCompletions` (4) slots at once, the fifth waiting in order; its other calls keep `turns`. A frame's end cancels its children, which cancel theirs, so no call outlives its caller; **one usage ledger serves the chain**, the top call's, so a key any frame sends is recorded against the plug-in the person ran, and the hook a call records is `<tag>:<function>`. Only the top call takes one of the five slots and the one-call-per-plug-in turn.
- **A call** (`_run`) runs a plug-in's function through `runJs` (the engine, above) — one call at a time per plug-in and at most five in the app — a call stopped before or while it waits for one of the five leaves the queue at once and never starts, and a run cancelled before its isolate began spawns none — a call made through `ctx.ai.complete` — whose answer's usage is recorded against the key it spent, an action's own answer being a message — running inside its caller's slot, so a plug-in asking the text model it itself provides never waits for itself, and bounded by its caller instead: a call's model completions run up to four at once, the fifth waiting its turn, its calls through `ctx.call` one at a time, and a caller's end — an answer, a limit, a cancel — cancels the calls it made, which cancel theirs, and closes its usage ledger, so no request on a key starts after it. — with `ctx` built from its settings (each default, then the project file's `plugins.<tag>` for the project-scoped, then this machine's for the machine-scoped), its strings resolved for the app's language (its own keys, and every `app:<key>` its code names, from `filmopen_l10n`'s generated `appStringsByKey`) and the selection. The outcome's code is logged (`plugins.limit`, `plugins.failed` with the message, `plugins.cancelled`, `plugins.hung` — which also turns the plug-in off); the plug-in's own message goes to the page and to the log.
- **What a call spent** (`usage_chain.dart`, §6.7). The estimate in `started` is not the ceiling's bound. A call's ledger writes `started` before its first request on each key, with the catalogue's price for the call as asked (the format's `usageEstimate`): a render's quote for the whole call where it was handed one — never a quote `per` an hour, which prices a server's lease; else, by what the entry makes, a text call's tokens, a picture's images, megapixels or requests, a clip's seconds, a piece of music's minutes, a voice line's characters — on the row of the variant the call names — a render's chosen stack first —, else the platform's first, at the least of the prices whose `match` the call's settings all equal (the format's `pricePer`), else the least of those without one whose `when` names its resolution, else — only where no price names a `match` — the least of all; a picture none of whose prices applies — no `match` it meets, no `when` naming its resolution — where some price names a `match` has no estimate, never the least of them — so that the estimate is the least the call can cost, and none where nothing prices it or the request cannot be read: `started` then carries no estimate, a cost nobody can foresee, never one of nothing (§6.7). **Each call frame carries its own pricing** — the model and the request it was given, a nested `complete`'s own and an offered function's its caller's — so that calls that overlap never price by each other's. A nested answer uses the pricing of the call that asked it, so models on one key each cost their own rate, summed on the key's one chain, whose record names the model of the request that opened it. Each chain captures the answer as it came, before anything holds it to a shape: `usage.billing`'s cost with its basis, a `provider` cost of more than twelve fractional digits being none; the top-level `cost`; units that the catalogue prices one way — a price's `match` choosing among them, as `pricePer` does — or tokens (`usagePrice`, basis `price`); else a cost nobody knows with the units, or the requests the chain sent — never a cost of nothing the answer did not say. The call's own answer speaks where the call spent on one chain; a nested call's answer — a platform's `run`, a text provider's `complete` — for the one chain the plug-in's own requests used, a receipt answered twice counting once. **A receipt counts for its own key**: a `requestId`, the usage's or the billing's, that no response on that key held, or that is a word of the call's prompt, makes the cost unknown and is not written. A response holds what its head's headers and its body say — a streamed answer's head and each read's events alike, so that the id a plug-in cites from a stream is seen as a whole answer's is, a stream's event strings counting as a text answer's words do; each response's new receipts are logged as they came (`usage.receipts` {plugin, platform, added, kept}), and an unseen one names the ids cited and unseen and why (`usage.receiptUnseen`). **A request the service accepted is never free**: the HTTP door tells the ledger what became of each request on a key the moment it is known — its status as soon as the status line arrives, before a body it may yet refuse; that it never left, where its host's name did not resolve, its connection was refused or its TLS handshake failed; or that it was lost, sent and never answered. Where nothing says what a chain cost, a call that succeeded ends it with a cost nobody knows and the requests accepted, or sent; on a call that did not, the chain ends once no request on it waits for its answer — with a cost nobody knows where the service accepted one, whatever the call did after (a plug-in that threw, an answer the definition refused, a stop), with no cost where it accepted none, and not at all where a request was lost, so that it stays open with its estimate pending (§6.7). A call stopped while its request is out has its chain ended when the answer comes. An ordinary call's total built from nested answers is unknown when some spend was said but fewer answers said spend than requests were sent: a refused answer or a 2xx answer without spend cannot leave a previous known part standing as the whole total. The call's own answer or a funded receipt remains authoritative, including an aggregate cost covering several HTTP requests. Lost or waiting requests take their open or unknown path before the partial check. At an ordinary close, `usage.ended` logs the latest record, its provider request id (`request`) and its operations' ids on credit (`operationIds`), the known subtotal and currency, the sent, spend-bearing-answer, accepted, lost and waiting counts, the operations by frame, the decision reason and elapsed milliseconds. The subtotal stays in the log alone; an unknown record carries no cost. Two first requests on one key open one chain. Cached input tokens are counted within the input tokens, and priced at the catalogue's cached price where the row names one. A usage's `cacheWriteTokens` (`cache_write_tokens`) are counted within them too, and priced at the row's *cache writes* price where it names one; `usage.unitsPriced` logs the price's source, the units, the band chosen and why, and `usage.priced` a cost the plug-in's billing gave. A paid call that then failed, or whose answer the definition refused, keeps what it said it spent on its `failed` record. **A pending answer spent nothing yet**: a cost a job's answer says while it says `pending` — its `usage`, the top-level `cost`, or its nested calls' — is no cost and writes no record, so polls saying one are never summed and the job's usage ends on its terminal answer; a `failed` answer that confirms no provider end keeps its reported cost at once, and a receipt cited by two answers still counts once.
- **The doors.** The callable `http` has an awaited `read` member; `partial` and `note` are awaited text-delivery doors. `http` is `PluginHttpDoor` (`http_door.dart`): with a key, **the key's own platform file** — the catalogue's, else its owner's own, never another plug-in's that names the same id — gives the base URL for `path`, or a `url` must be `https` on its `hosts` — **and, on a host the file names `paths` for, on one of those paths** (Project Specification §14.9: `PlatformFile.refuseCredentials`). A plug-in allowed to use a key holds the key's whole authority on every path it may reach, and a platform's hosts can serve more than models — fal's `api.fal.ai/v1/keys` makes keys — so the path is matched **by whole segments** (`/api/v1/key` is not `/api/v1/keys`), and judged **as the plug-in wrote it**: the `url`'s own text from the end of its authority, a backslash ending that too, or the base's path with `path` joined, before `Uri.parse` resolved `..` and `%2e%2e` away. A `.` or `..` segment however escaped or whatever `;` parameter follows it, an escaped slash or backslash, any backslash, an empty segment (a trailing `/` included), a control character, and a `%` that is not a printable ASCII escape or that escapes `%` itself (`%252e%252e` is `..` to a server that decodes twice) are refused `bad-path` **before anything is matched**, and a plain path outside the prefixes `path`; both are refused before the credential is read, and nothing is sent. **FilmOpen credit** (§6.6): **the person's own key first** — a key stored is used as it always is; where none is, a request to **its platform's own origin** (the origin of the platform file's `base_url`: `https://queue.fal.run`, `https://api.openai.com`, `https://api.elevenlabs.io`) on a platform the funding resolver answers credit for goes to the website's pass-through, `https://<kFilmOpenDomain>/v1/portal/pass/<platform><path>` — the target's path and query as `_target` resolved them, a `path` joined to the base or a whole `url`, so that fal's queue URLs, OpenAI's `/v1/images/generations` and ElevenLabs' query all keep theirs — with its method and body untouched, of its headers `content-type` and `accept` alone, and the bearer and the operation's portal credential (`ProviderFunding.portalHeaders`) and `X-FilmOpen-Operation`. A non-job frame holds its own operation and reuses it during its life; a render job's frames share the chain's operation across submit, status, result and cancel, saved in the receipt across a restart. The platform's own credential header is never added. Its usage chain is opened with no key, on the route `filmopen.ai`, holding the operation (§6.7), and a frame that holds one stays on credit. Entering a key between non-job frames can produce a mixed-funded chain whose recorded route is its first request's. Two completions inside one job still share an operation; a non-job submit and poll split across two calls do not share one. A body over 16 MiB (`maxBodyBytes`) is refused `body-too-large` before the chain opens, nothing sent; an operation with no credential is refused `not-funded`. Then **the ordinary transport**: the plug-in's timeout, no redirect followed, the answer's size bound and its shaping as on a key; the provider's answer comes back as it would on a key, a refusal of the website's — `409 insufficient-funds` among them — as its status, which the plug-in's own error handling reads. The website marks its own refusals with `X-FilmOpen-Refusal: <code>`, and that header alone tells them from the provider's answer, whatever a body says. A `401` whose refusal header is the portal credential's lets the credential go (`portalRefused`) and is refused with its code, once, never resent. `X-FilmOpen-Operation-State` and the echoed `X-FilmOpen-Operation` are logged as they came and never acted on. Each request logs `plugin.http.credit` before the send — the plug-in, the platform, the operation, the method, the path after the base without its query, the bytes — then `plugin.http.credit.answered` with the status, the state, the echo and, on the website's refusal, the header's code as it came, `plugin.http.credit.refused` with the stage (`local`; `portal`, with the code; `provider`, the status alone, for any answer of 400 or more without the header), or `plugin.http.credit.failed` with the stage, the failure's type and its message, each with the sending frame and milliseconds; never the bearer or the portal token. For ordinary model completions, the whole request body on `plugins.http.start` carries that child frame; `usage.operationOpened` joins it to its operation and parent, and the credit lines carry the same child frame and operation. The AI completion's start, done and failed lines carry the caller frame, joined by that parent. The operation-opened line also gives the function, model and scope decision's reason. `api.fal.ai` and every other host stay `no-key` without a key, and so does a key check, which reads the person's own key alone. `ctx.keys()` says a key not stored but granted is usable on credit where its platform is — `usable: true`, `mode: 'funded'`. A job's collect and cancel read the route's key stored when they run, as every other call does. A job on credit ends with the website's receipt: the operation is read in the job's ending call, through `ProviderFunding.receipt` with the kind `http`, before its one terminal record is written — once, and once more after the cost collector's bound (`PluginUsageLedger.receiptWait`, 30 s) where the result was eligible for a charge — and its `chargedCents` is the record's cost (`charged`, with its operation and receipt id); without one the cost is unknown, never zero. A cancel the provider confirmed (`cancelled`) first ends each of the job's operations on credit once (`ProviderFunding.end`, logged `usage.end` with the operation, the reason `cancelled` and the milliseconds, `usage.endFailed` with the error's type and message), so that the website cancels and settles it and the receipt read after it is the terminal one; no other call or state ends one, since its result is still wanted and its `GET` settles it. A `path` cannot leave the base's host: one that starts `//` or holds `://` is `badArgs`/`path`, so fal's `path` reaches `queue.fal.run`, which the file names no paths for and which takes any. **Exact-job storage convention.** The key `job:<exact ctx.job.id>` is the disposable dispatch and recovery receipt of that job, in the store of the route's plug-in or of the platform's plug-in it calls. Per-job history and any record that must survive settlement belong under another key. Settings, caches and keys outside this reserved exact-job namespace are never removed by the host.

Recovery of a render job across a restart belongs to `BackendRenderManager`, which registers the job before submission and restoration and settles its terminal Usage. A direct `PluginRenderBackend` caller without that manager has no supported cross-restart recovery. An answer whose stable id the usage log already holds — a cancellation repeated from the original pending receipt — is not appended again, whatever it says. Registering a job without a manager that settles it leaves its terminal Usage unsettled and is not a supported mode. The executing owner's `job:<exact ctx.job.id>` is its disposable receipt and cancellation fence; long-lived history and billing never belong under that key.

**Receipt retirement.** Managed provider-end confirmation requires an understood affirmative answer: success, confirmed cancellation or a verified terminal failure. Unknown, unreachable, receipt-unavailable, job-mismatch, host failures and unverified failure codes retain uncertainty. The same confirmation rule governs backend failure and provider-driven managed ledger closure; every call’s reported Usage is captured independently of that authority. The manager’s journaled local terminal settlement or Dismiss may close the ledger without provider-end confirmation. Local Dismiss never proves provider completion or grants the removal of a receipt. A settlement the host prepares after an end confirmed in this session says so (`providerEnd`), and the manager journals it with the complete prospective terminal or output-ready state before applying it. Settlement replays Usage once, then removes `job:<id>` from the store of the route's plug-in and of its platform's plug-in, in each plug-in's storage turn, logging `plugins.storage.remove.start` and `plugins.storage.remove.done` (`removed`, with the value, or `absent`), then `plugins.receipt.removed` (the plug-ins, the job, the reason `providerEnd` and the milliseconds), or `plugins.receipt.refused` with the plug-in and the store's reason; a settlement without that word keeps the receipt and logs `plugins.receipt.kept`. Uncertain settlements, and those an earlier build journaled without that word, keep their receipts. Initial uncertainty without an acknowledged pending receipt cannot be collected through the current contract; it finishes locally while retaining its plug-in fence and receives no retirement authority. **A synchronous answer's provenance.** A render answered at once — its outputs inline, no receipt — that fails after its service answered a request on the person's key, whether the provider's own error in the body or an output the host refuses, is a failed answer: the call keeps `reachedService`, so the render says it may have cost, keeps the handles it had staged until the backend lets go of every one no output keeps, and keeps its Usage chain — closed as a charged failure, or held for the managed job's end where the provider confirmed none. It has no receipt, so nothing collects it and nothing sends it again. A failure **thrown** by the host once the plug-in has answered — its answer being held, its Usage being kept — is a failed answer still (`failed`, logged as `plugins.renderAfterAnswer` with the plug-in, the job, the error's type and its message): the call keeps `reachedService` and its staged handles for the backend as above. A failure thrown before any answer is not a failed answer: nothing was produced, and every handle the call had staged, the first frame's copy included, is released before the exception leaves the call.

An installed agent keeps its render journal in a private folder and never sweeps the staged folder shared with the ordinary application. The installed automation host selects the private journal before its container is attached; operational availability is not the startup identity test.

For the same reason the door it watches arrives as a closure that answers, not as the means of asking. **The developer page's side** (`dev_run.dart`, `host_runtime.dart`'s four `dev…` methods). `devOpen(stem)` reads the plug-in's files **from disk again** and answers what it exposes, **in the definition's terms**: **`status` first**, then the functions of the interfaces it implements, its actions and the functions it offers, each with **the definition's example** for a function of the contract and the manifest's own for an action or an offer — no shape kept by hand — and `verifyKey` never among them, since its candidate key is typed on the plug-in's page — with every problem by the file it concerns and where its last run and the developer's log are written. `devRun(stem, function, args, mode:)` reads them again and runs the function **enabled, asking no consent, with every key its `uses` names granted** (the page is for people who write code, and nothing on it is withheld); the sandbox, every door's rules, the limits and the usage records are exactly the app's, or what passes here might fail in the app. **The registry, the preferences and the stored consent are untouched**: outside the page the plug-in asks exactly as before. The run's hook in the usage records is `dev.<function>`. **It calls the function one of two ways, or runs a script in the console** (`PluginDevMode`): *As FilmOpen calls it*, the default, with the request the app would make — `status` with `ctx` alone; an action with `ctx` alone, as its button presses it; a `render` prepared by `prepareRender` (its entry, its inputs described and held to the entry, the seed, the source) and a `complete` or an estimate as the app builds them, an estimate being the function of the interface its `operation` names, and **a request the app could not make refused before the plug-in runs** — a model the catalogue lacks (`noProvider`/`noEntry`), one this plug-in does not serve because the entry names no platform its manifest implements the interface on or its manifest names other models (`noProvider`/`noPlugin`, since the app's choice would never bring it here), a completion's `params` that are no object (`badArgs`/`params`); an entity hook with the entities chosen; an offer, or a function of the contract an action's button also calls, as the contract calls it — and *Exactly what I typed*, the box as it is, for the protocol and a function's edges. **The console** (`console`) calls no function of the plug-in's: `devRun` names the call `$console` and runs the plug-in with one more file after its own (`DevRun.withConsole`), `console.js`, whose value is a plug-in of that one function, its body the box on the file's first line, called with `ctx` alone and the page's entity as `ctx.selection`, its answer held to nothing; `plugins.devConsole` logs the script, the entity and the files as it starts, and `plugins.devCalled` the script and the value whole as it ends. **The mode changes what is sent, never the guards**: `status` runs as *Check* runs it either way, so it may not reach `ctx.ai.complete` and spend. **The request as sent is the run's first log line** (`request`) — after a writer's `context` line, which its preparation writes first — so the page shows it before the answer comes, and the run carries it (`PluginDevRun.request`, with its `mode`). **An answer of a function of the contract is held to the definition in both function-calling modes**, one of the wrong shape being `badResult` with its path, and **an offer's own `args` and `returns` hold a call to it** — its arguments as a caller would send them, before it runs, as FilmOpen calls it, and its answer either way. A render as FilmOpen calls it is read by its `state` and, where an entity was named, **saved as a take exactly as the app would**, its batch's item the request as prepared; as typed, nothing is saved, since the app's record would name a request nobody prepared; with no entity named, the outputs are only listed. `last-run.json` holds the `mode` and, as `args`, the request as sent — `null` where it was refused and nothing was sent. `devClose(stem)` forgets `last-run.json`.

**The log of such a run.** The doors closure is wrapped for the page and for it alone: **the request as sent first** (`request`), then every `ctx.log` line and a row per door, in order, with what the door was asked for — the setting or the key **by name**, the address or a `server` request's route whole, as the plug-in gave it, the answer in summary and the milliseconds — and **what crossed into JavaScript and nothing else**, everything in it as it is — the arguments, a line's words and data, an answer — and no key of the request, since the door adds it after the request is logged; an answer that echoes it crossed as it came. A line's data and its message are kept whole. Each line goes to the page as it happens and to **`plugins-dev.jsonl` beside the app's log** — there **whole**, its message and its data as they are, the call's outcome — the answer and an action's words as shown, or the failure's code, reason, path and message, and whether a request was sent — its last line, written before `last-run.json`, and a call refused before anything went its only line; no request's key reaches it, since a request is logged as the plug-in built it, before the door adds the key; a line the file cannot take is said in the app's log (`plugins.devLogFailed {stage, path, type, error}`) — rotated at 5 MB to `plugins-dev.jsonl.1`: a developer's own file to `tail`, which no issue report ever carries and which a person's ordinary use never writes to. After every call `last-run.json` is written under `<app support>/plugins/<tag>/dev/` — the function, the mode, the request as sent, the outcome with a failure's place, and the lines, under a megabyte — results as data, for an agent; one that would pass a megabyte drops its lines, then its request and answer, and points at the developer log, which holds them, and a file that cannot be written is said in the app's log (`plugins.devLastRunFailed`). The log events are `plugins.devCalled`, with the stem, the function, the mode, the outcome (`done` or `failed`), whether a request was sent and, for a failure, its code, reason, path and message, and `plugins.devFolderSet`.

**The zip** (`plugin_archive.dart`). `PluginArchive.read(bytes, expectedTag:)` reads a plug-in's zip into memory and refuses it whole — nothing kept — when it does not read as a zip or holds nothing, claims more than 64 MB unpacked or 2,000 files, has an entry that would land outside the folder (absolute, a drive letter, a backslash, an empty, `.` or `..` segment) or a link (by its target or its Unix mode), or has no manifest at the folder's top, manifests of two tags, a folder not named after the tag, or a tag other than the one expected. Each entry is inflated by the `archive` package's pure-Dart inflater into a buffer bounded by what remains of the 64 MB — never through `entry.content`, which on `dart:io` hands the whole entry to zlib and writes it out only once it is complete — so an entry whose directory claims a few bytes and inflates to gigabytes stops at the limit; an encrypted entry, one compressed other than stored or deflated, and one whose bytes do not match its CRC-32 — a download cut or damaged on its way — are unreadable. What an operating system adds as it zips a folder — macOS's `__MACOSX/` and `.DS_Store`, any hidden name — is left out, as a folder source skips hidden entries. The folder's contents may sit at the archive's top or inside one folder named after the tag.

**Lending** (`lending_supplier.dart`; the state's `Lending` seam, the account's `AccountLending`, §6.6). What this computer shares is a list of **offers, one per fixed configuration**, kept beside the enabled list (`PluginPreferences.sharedOffers`, one JSON list of `SharedOffer`: `id` — a UUID made once and kept —, `tag`, `function`, `model`, `server` — null for this computer, else `{provider, offer}`: the server provider's tag and the GPU offer its servers are started from, never one session —, `stack`, `params` — the options the person fixed on the stack —, `name`, `usd` — the price of one unit in whole cents, `0` free —, `enabled`), read and written whole through `PluginSettingsControl.sharedOffers` / `setSharedOffers` (one writer at a time, an entry not of the shape or a repeated id refused at the write before anything is written, an entry not of the shape left out at the read, the listeners told). The person writes the list from *Share my plugins*' offer tree (§9.7a), its one writer: a new offer a fresh UUID, an edit keeping its id, *Enable* changing that field alone, and no *Remove* — a disabled offer stays listed and the loop withdraws it; a sharing plug-in's own page says so in one line and has no switch. `LendingSupplier` starts once the render journal is read and runs while the person is signed in on a registered device. At start it stops every remote render the last session left. Each turn (every 15 s, and on a plug-in change) it reads the list and the server sessions and builds each offer (`lendingOffers`): its declaration from the installed plug-in and the catalogue entry alone, so an unchanged entry is the same bytes at every turn — `pluginId`, `pluginVersion`, `configuration` (`function`, `model`, `unit` and `scale` from the manifest's `sharing` operation, `stack`, `params`, `name`), `inputs` `{values: <the entry's capabilities.inputs>}`, `outputs` `{kind}`, `rates` `[{unit, usd}]` — and whether it is **publishable**: the entry enabled, its plug-in enabled and runnable, and its server null or a session of that provider and offer that is `running` **and holds the offer's stack** (the session's stack the offer's, or none named — a server from before stacks; `holdsStack`), so that a running Fast server neither publishes nor runs a Quality offer, which is held `server-not-running` with nothing deployed or chosen in its place; the decision is logged `lending.offer.server` {offer, server, stack, running: [{name, stack?}], session?, outcome: `serves` | `no-server-running` | `no-server-holds-stack`} once each time it changes (`lendingMatch`). An entry whose plug-in is not installed, or whose manifest no longer shares a `render` of that model, is no offer. The loop keeps, in memory and never in the list, what the website holds of each offer — the declaration, the version it answered and the publication last sent — and writes one thing at a time: a **declaration** where the offer is new to the session or its declaration changed (the website hashes it: an equal declaration answers the same version, a changed price or option another), then the **publication** — published where publishable, withdrawn otherwise — where the desired state is not the one last sent for that version, so the first turn of a session sends every offer's state once and later turns only a change; an offer that left the list, or lost its plug-in, is withdrawn where it was published and forgotten; a write the website refuses is logged (`lending.offerRefused`) and leaves the other offers their turn. While any offer is published the device is `available` and the inbox is read every turn, which keeps its presence; with none it is `unavailable`, the job in hand stopped and failed. **A lending notice wakes it**: `pokeLendingSupplier()`, the factory library's one door to the running loop, runs a turn at once — the turn already running where there is one — and answers whether a loop runs, logged `plugins.lending.poke {running}`; the relay calls it when the website says a job was made for this device's offer (§6.6c), and the turns on their own clock stay. It takes one job at a time. A job's input — opaque JSON, handed over as the buyer sent it — must be the object `{prompt, seed?}` and nothing else (an array, a scalar, another key or a seed out of bounds is refused, `lending.input` naming why in one word) — the options are the offer's, never the buyer's —, its frozen declaration this plug-in at the installed version and of the offer's model, and the offer must have a route now (`lendingRoute`: for this computer the plug-in's candidate with no destination, for a server the candidate of the first running session holding the job's frozen stack, that stack set; logged `lending.route` {job, offer, server?, stack?, destination?, outcome: `routed` | `no-route`, ms} and, for a server, `lending.route.server` with the running servers' stacks, the one chosen and whether the plug-in has a candidate on it), or it is refused before acceptance (`bad-input`, `not-this-offer`); a requested job of an offer not published this turn is refused `not-this-offer` as well; `busy` at acceptance leaves it. An accepted job is rendered through the application's render road as a remote request **on its frozen declaration** — the stack and the options frozen with it, never the list's current entry — on the offer's current server (the server is private and not in the declaration); at `outputReady` each output's bytes are read, uploaded through the media client (`MediaClient`, §6.6) and hashed, and the job is completed with one `complete` whose opaque `result` is `{model, seed?, stack?, width?, height?, outputs: [{url, contentType, bytes, sha256}]}` — the model and what the render reports, then each output's download URL, length and SHA-256 in order —, the rail's balance read again once the website took it (`ProviderFunding.balanceMoved('lending')`, logged `lending.balanceMoved` with the job, the role and the milliseconds), then the render acknowledged; an upload the media store refuses, or a result over the 64 KiB bound, fails the job `render-failed`, its code in the log. A job stopped while its outputs upload — the offer off, its server stopped, quit — is failed rather than completed; signed out, nothing more is sent. A render that ends otherwise fails the job `render-failed`, its own code in the log alone. An accepted job that is not the one in hand — a restart's, or one a sign-out or an unanswered failure left — is failed `supplier-restarted` on the next turn and never run again. A refusal by which the website closed the job ends its handling with no retry; any other refusal after acceptance fails it once. Disabling the offer, turning its plug-in off, stopping its server and removing it stop the render in flight, fail the accepted job and withdraw the offer; quit stops and fails likewise and leaves the offers as the website holds them (a stale presence makes them unavailable there; the next session sends their state again); a sign-out sends nothing — the render is stopped, and the website's presence and deadline close the rest. Each step of a job logs its `lending.*` line with the job's id and the milliseconds since that handling began — `lending.input` (with the reason of a refusal), `lending.refusedJob`, `lending.accepted`, `lending.render.started`, `lending.render.ended`, `lending.result.uploaded` (the media key, never the URL, with the type, the bytes and the digest), `lending.result.sent`, `lending.completed`, `lending.refused` and `lending.failed` with their stage and an unexpected failure's message, before acceptance as after. An offer that is not publishable says why in `lending.offer.held` (`offer`, `reason`: `offer-disabled`, `plugin-disabled`, `plugin-not-runnable` or `server-not-running`, the first that holds), as does an entry of the list that is not an offer at all (`plugin`, `reason`: `plugin-not-installed`, or `not-shared` where its manifest shares no `render` of the model), once each time its reason changes, never every turn, and before the declaration, so a refused one still says it; `lending.withdrawn` carries the reason too (`not-an-offer` for one that left this turn's offers). **What the website acknowledged** is `Lending.published`, the ids of the offers whose publication the website accepted and that are publishable: the loop sets it each turn, before a turn with none published returns, only when it changed, and empties it at sign-out and once a stop's turn has ended; the offer tree and *Stop* read it, and nothing else writes it. `lendingRoute` and `runningSession` live in `filmopen_render`, so that the editor asks the options of the route a job would run on.

**The audience** of what this computer shares is the account's, not this computer's: who may use the published offers — the person's own devices always, the persons and groups of the free list, the public where chosen — is `GET` / `PUT /v1/lending/settings` (`Lending.audience` / `setAudience`, §6.6), written from the GPU page's *Share my plugins* (§9.7a); the loop reads nothing of it, since the website admits a job by the setting it holds. The free list carries ids, and the website says no name for them yet, so this computer keeps **the names it resolved** (`PluginPreferences.freeWithNames`, one JSON object of id → username, read and written whole through `PluginSettingsControl.freeWithNames` / `setFreeWithNames`, one writer at a time, a value not of that shape read as nothing, the write logged by its count alone and no listener told); the page trims it to the account's list at each answer. A group the account holds is named from the *Groups* card's read instead, which needs no store. It goes when the website answers the names itself.

**Rendering on a lent plug-in** (`lent_render.dart`; the requester's three operations of `Lending`, §6.6). Another computer's offer is one more route of the render dialog where this computer has the same plug-in **installed and enabled, at any version** (`pluginId` its tag; the supplier refuses a version it no longer runs, so an update on one computer loses the other nothing) and its manifest's `sharing` names a `render` of the dialog's model: only then are the offers read, bounded at 3 s, a refusal or a late read leaving the local routes as they are. Each decision is a line, ids, tags, codes and counts alone: `lending.routes.start` (`model`, `sharing`: how many plug-ins share it); `lending.routes.none` where none does (`reason: no-sharing-plugin`, `installed`: each plug-in's `<tag>:<enabled>`, `ms`); `lending.offers.read` (`count`, `ms`) or `lending.noOffers`; for every offer not taken `lending.offer.skipped` (`offer`, `own`, `reason`: the first that holds of `unpublished`, `unavailable`, `function`, `model`, `plugin-not-installed` — no installed, enabled plug-in sharing the model has its tag — and `unpriced`); and `lending.routes.done` (`routes`, `ms`). Each published, available offer of the model becomes a candidate after this computer's own routes: the installed plug-in's route, a destination of kind `lent` whose id is the offer's and whose `server` holds its version, the price and the quantities it was priced at and whether it is the same account's (`own`), billing unless the offer is free, queued per offer. The price is the design's: one of the configuration's unit and none of any other rate's unit, every rate times its quantity summed exactly and ceiled once to the cent, zero where the offer is free. `options` answers a lent route itself — that price, no stacks, no parameters — and the dialog names the route *Your other computer* or *Shared on {domain}*, then ` · ` and the offer's name (its `configuration.name`, the candidate's label; nothing where it has none), the count the backend adds to two alike carrying its own separator. A render on it prepares **one job whose id is the render's own**, journaled before the call, so a restart reads the same job and no second id is ever made: the offer, its version, the quantities, the input `{prompt, seed?}` — the options are the offer's, frozen in its declaration, so the request's never travel — and the price the dialog showed; a preparation left unconfirmed or unanswered is read, never sent again, and any other refusal fails the render with its code (`terms-conflict`: the price changed; `insufficient-funds`: not enough credit). Collecting reads the job every 3 s: a published result's outputs are fetched whatever the money's state, each from its URL — refused unfetched unless it is `https://<kFilmOpenDomain>/v1/media/…`, since another person's app wrote it —, through a client made for the collect and closed at its end, with no redirect followed, no credential and a 30 s bound, the body held under 32 MiB whatever its length header says; each output's length and SHA-256 are held to the result's entry and its type to the model's kind (`mediaNotWhatItSays` otherwise), and it is staged as a take of the installed plug-in's run (`run` its tag and stem, `item` what was asked, the result's `seed`), which the insertion takes in unchanged; once the handling of a published result is settled — staged, or a confirmed failure; never a fetch to be read again or an unconfirmed failure that *Retry* collects again — the rail's balance is read again (`balanceMoved('lending')`, logged `lending.balanceMoved` with the job, the role, the state, the outcome and the milliseconds, and a handling not yet settled `lending.balanceDeferred` with its outcome and the reason `collected-again`); a closed job fails with its code, a result gone `expired` — as is an output the media store answers 403 or 404, its token or its object gone —, a job never prepared `not-found`; an output nothing answered, or not in time, and an unreachable job are read again at the next collect; any other refusal of the job proves nothing and is an unconfirmed failure, which the person may collect again, as is an output answered with a status other than 200, 403, 404 or a redirect (`mediaUnavailable`; a redirect is refused `mediaNotWhatItSays`, never followed) or that could not be staged (`staging`). Each read logs `lending.collect`, with a closed job's `closeReason` and `failCode`, and each output `lending.result.fetch` (its address whole, its type, size and digest), `lending.result.read` and, where refused or failed, `lending.result.refused` with its reason and the value refused or `lending.result.failed` with its stage, outcome and the error's message, whole. Cancel sends `cancel`: closed or never made, it stopped; published already, it finished and is collected. The take names the job (`render_id`), not the offer or its version.

**Streamed HTTP answers.** A request with `stream: true` receives a successful `text/event-stream` head as `{status, headers, stream: true}` before the body completes. Other content types and non-2xx answers retain whole-body handling. The call's frame owns one stream and closes its connection at EOF, failure, cancellation or frame end. `ctx.http.read()` waits for a complete event or EOF and answers `{events: [{event, data}], done}` with all events already framed. A missing stream, concurrent read or second streamed request is `badArgs` with reason `stream`. Framing decodes UTF-8 incrementally, tolerates malformed bytes, recognizes CR, LF and CRLF, joins data lines with newlines, defaults the name to `message`, and drops comments, ids, retries and unfinished events. Each event's data is handed over as it came. Raw bytes count against the response bound over the entire stream; `timeoutMs` bounds each chunk's wait. A broken body is `refused` with reason `connection`; timeout and oversize are `refused` with reasons `timeout` and `tooLarge`, and abortion is `cancelled`. A streamed head's headers and each read's events are told to the usage ledger as a whole answer's are (*What a call spent*).

**Partial text delivery.** The host passes `stream` only to a text provider's `complete`; `ctx.ai.complete` passes none. `ctx.partial(text)` is awaited and accepts a non-empty string only inside a live `complete` whose own pricing request says `stream: true`. It appends in order to `PluginCallControl.partial` and never clears it; the control's owner, an assistant's turn, keeps it for the whole turn as its display (§6.11a, *The reply that streams*). The frame counts cumulative UTF-8 bytes for its log, with no bound. Wrong text is `badArgs` with reason `text` and the wrong phase is `refused/phase`. Under an assistant binding the turn's check runs first, so Stop or a changed target refuses `cancelled` or `stale`. An accepted delivery writes no line; the stream writes one when its frame ends, `plugins.partials.done` with the count, the bytes and the elapsed time, in the app's log and as one `partial` row on a developer page and in `plugins-dev.jsonl`. A refusal logs `plugins.partial.refused` with its code, its reason and the text it was given.

**Passing notes.** `ctx.note(text)` is the running streamed call's one current note — a passing word of what the model is doing, such as its reasoning's latest sentence. It is admitted as `partial` is — a non-empty string inside a live streamed `complete`, `badArgs/text`, `refused/phase`, under an assistant binding the turn's check first — whatever its size. It replaces `PluginCallControl.note`, a tool note's alias named by its command (`c5_create-entity · 3` reads `create-entity · 3`, from the turn's own table; any other note as it came), accumulates nothing and never enters the call's text, a message, the conversation or what the model is told. It is cleared when the call's first words arrive (`ctx.partial`, cause `words`), when the call ends (`end`, or `failed` where it failed) and on Stop (`stop`), the session's disposal stopping its turn. The host numbers the turn's model calls on the control (`PluginCallControl.call`); `AssistantSession.note` and `AssistantSession.call` are the seam the dock reads, empty and 0 while idle. Every delivery, refusal and clear is one `plugins.note` line — `plugin`, the `frame` where a delivery has one (a clear has none), `session`, `call` where a control numbers it, the `text` as received and, on a delivery, as `shown`, `outcome` (`shown`, `unseen` without a control, `refused` with its `code` and `reason`, a failed delivery with its error, `cleared` with its `cause`) and `ms`. Not guarded: a note's frequency — no quota and no timer. The stock OpenRouter adapter sends the reasoning's visible summary or text, one whole sentence at a time, a sentence that ends as the reasoning pauses (an event without reasoning, or the stream's end) included; encrypted reasoning shows nothing and stays in its event log. While a tool call's arguments stream, it sends the call's tool and its number in the answer (`create-entity · 3`) once, as the tool's name arrives — data, not a sentence, so nothing to translate; the OpenAI adapter asks a streamed call for its reasoning summary (except at effort `none`, which has none) and sends it the same way, and the xAI adapter sends Grok's streamed `reasoning_content` the same way.

**Streamed assistant requests.** Streaming uses the ordinary HTTP transport's stream flag and frame-bound reader. The assistant policy holds the model, route, output bound, request size and one POST per admitted call; the provider owns its wire-body grammar.

The stream logs `plugins.http.stream.open` or `.whole`, each batch's `.read` and `.read.done` — the latter with the batch's events as they came, under `answer` —, `.first` at the first event, and `.done` or `.failed` with read/event/byte counts, first-event time, elapsed time and, on failure, the reason, pending-read state, time since the last read completed and, under `unread`, the events framed since the last read, which the plug-in is never handed, as they came. Where the response ended first and a Stop or the call's end comes before the plug-in's last read, `.unread` carries the counts, the reason and, under `unread`, the events not yet read, once; a read already waiting takes them itself. `.refused` identifies stream misuse. An `error` or `response.failed` event, or a JSON object with an `error` member, emits `.error` with the extracted code, the whole message and the event's data as it came; the event still reaches the plug-in. `.whole` carries the content type as it came.

The dock's readiness row follows the selected action's current route. Before a selection it uses the first runnable action with a known funding route, else the first action needing a key. FilmOpen credit is ordinary information; another offered action's missing key does not replace that notice.

**The LLM decision.** One machine setting, *Use the LLM:* in Settings → General, overrides every plug-in's preferences. With no override, `decideLlm` takes the first reachable preferred id, else the first reachable text catalogue entry in load order. With an override it considers that model alone. Reachability uses metadata only: every enabled provider serving that entry is considered, including generic providers; a configured local server, a stored-key status or a true cached credit answer makes its route reachable. No credential is read and no provider is probed. Among the chosen model's reachable providers, the person's text-provider preference wins, else a stock provider, else the first by tag; a tie never advances to another model. The same rule holds for catalogue fallback. Other callers of `chooseProvider` keep their interface's ranking. Each decision logs a `plugins.llm.decided` line: its inputs, provider preference, ordered `tried` with each route's provider, platform, server, key status, funding and reason, chosen route, `why`, ranking, tie and elapsed milliseconds. Inventory decisions write no call-decision lines; `assistant.model` and `assistant.models` retain their reasons and trials on change. Each action's decision is made once, on the first offers after the service's `changes` — the host's plug-ins, keys, credit, settings or the person's model, or a catalog — and reused by every rebuild of the dock until the next (`assistant.decisions.cleared {decisions, reason: host|catalog}`).

An ordinary call chain without a supplied model captures its default on its root frame at its first completion without preferences; later such completions share it, including a refusal. A step supplies that default before the call. A nonempty `options.llms` list of strings decides that completion alone, after an assistant's frozen route, and never replaces the root's default; an empty list counts as absent, and a present value of any other shape is refused as `badArgs` with reason `llms`. Returned maps carry the actual route's `model` and `provider`, replacing those fields from the provider; other values are unchanged. The completion start logs the requested `llms` and route (`assistant`, `call` or `frame`), its end the answer as returned, and its failure the requested `llms`. An ordinary call with no supplied decision waits for its first completion to decide. A prompt writer receives the up-front reachable model as `buildPrompt.args.llm: {id, entry}`, alongside the separate media model and its `entry`; absent where no LLM is reachable. `ctx.ai.complete` uses the decision selected for that completion for its messages and logs the decided model, reason, trials, messages, answer, outcome and elapsed time. It never retries a failed call through another provider. Media defaults belong to the image, video and voice render picker.

### 6.11a The field-assistant adapter

The host's assistant service (`assistant_host.dart`) is the catalog road's (above), installed by the composition wherever the plug-in host runs (`installAssistantService`, §4); on the web the service is unavailable. It lists the packages that declare a catalog, offers their actions where the person is, and opens an action's chat on the person's gesture (`openAction`): the package and the action admitted, the film captured, a field action's draft admitted for reading, the model resolved and frozen, then the context object bounded whole; each refusal is logged as `assistant.open` with its code and stage. The host permits one in-flight turn and asks for the model's own output maximum (above); a dialog has as many turns, and a request as many bytes, as the model takes. Each model call is one `complete` from Dart to the frozen provider under the assistant's policy: one HTTP POST on the frozen key, catalogue service model and endpoint, with its verified output bound; no automatic retry or redirect. Each message the session sends logs `assistant.session.send {session, phase, turn, requestBytes, input, ms}`; the host's `messages` stage of a turn or an *Apply* logs its `requestBytes`, and `assistant.open` the opening's. A turn is one call where the provider declares no tools, and the loop above where it does; each call's Usage ledger is settled once. Cancellation and invalidation abort only owned work and reject late answers.

**The reply that streams.** Every model call of a catalog action's turn asks its provider for a stream (`stream: true` on `complete`); a provider that does not stream answers whole, as before. The turn's display is its control's `partial` text, appended by `ctx.partial` and never cleared during the turn: one segment a call, a blank line (`\n\n`) put before a later call's words where the display does not already end in one, so the words before a tool call stay on screen. Each accepted call's words settle its segment before the turn goes on — a whole answer appended, a streamed one's segment replaced by its final text, which wins over what was pushed (no refusal where they differ, `partialsMatched` logged); a refused answer's final text never replaces its segment, what it pushed staying as shown with no content. **A last answer with no words and no tool call** after tools that all succeeded in the turn ends it `ok`: the reply is the app's *Done.* (`assistantDone`) — the stored message's `content`, `assistant.turn`'s `reply` and what the model is told later — appended to the display under the words already shown, while that call's `assistant.turn.call` logs the model's own empty `reply` with `emptyAfterTools: true`. Once a tool of the turn has failed or been refused (`bad-call`, `error`), every later `assistant.turn.call` of the turn logs `toolFailed: true`, and an empty last answer then is `noWords` (*The assistant gave no answer. Try asking again.*), as an empty first answer is; an answer whose text is of the wrong type stays `badResult`, whatever its length otherwise. The reply carries `display` (what the person saw) beside `reply` (the last call's text, or *Done.* where it said nothing after its tools, what the model is told later and what *Apply* may finalize), `display` absent where the two are equal. A message keeps the same split: `AssistantMessage.display` beside `content`, `toJson` still `{role, content}`. A turn stopped, timed out or failed after text was shown keeps that text, its trailing blank lines trimmed, as an assistant message with `display` and empty `content`; a message with no content is left out wherever the conversation is serialized, by one filter applied the same way every turn, so the unfinished prose is never told to the model, a finish never reads it, and the backend's kept tool exchanges — the pre-tool words among them, once — still meet the person's messages they are keyed by. The session exposes the running turn's `partial` (empty while idle) and does not notify on it: the dock's transcript is not rebuilt for a partial, only the growing bubble `assistant.partial` above the busy line, a finished message showing its `display`. **Stop while a model call is in flight** aborts its network waits and sends an End for its credit operation once, independently of the turn’s cancellation (§6.6) — `endOperations(…, reason: 'stopped')`, not awaited, so the dock is idle at once; the background receipt waits for that End before reading its settled charge, without keeping the dock busy; receipts of earlier completed calls continue independently of Stop; the website’s operation lifecycle remains authoritative; on credit a streamed operation closed without its final usage is charged its hold; on the person's own key nothing is asked. The turn logs `assistant.turn.first {turn, call, ms}` once, at its first partial; `assistant.turn.call` adds `partials` and `shown` (whether any was shown, `partials > 0` — what reached the screen, apart from whether the HTTP answer was a stream, which the HTTP door's lines say), and `firstMs` and `partialsMatched` where the call streamed; `assistant.turn` adds `partials`, `shown` and `display`, the text shown; `assistant.turn.stopped {turn, call, display, onCredit}`, then the usage helper's `usage.end` or `usage.endFailed` and the account's `account.portal.end`; the session logs `assistant.session.display {session, kept, display, error?}` where a message with a display is added — the session id and the text as shown. Not guarded, by design: no retry of an End, no automatic restart receipt reader, no check of the partials against the final text beyond the logged boolean.

**Credit admission failures.** The dock names the failed step and distinguishes an unreachable payment server (with its transport error), a refusal (with its code), and insufficient credit. Earlier completed work remains. *Try again* sends an ordinary new turn, `Continue from where you stopped.`, with completed exchanges retained. It is offered while the composer is empty; a drafted correction keeps its words for ordinary Send. Nothing is retried automatically.

**The note in the dock, an answer cut off, a provider's own words.** While a turn runs, the dock shows the call's note under the busy line (`assistant.note`), in the theme's quiet style (`bodySmall`, `onSurfaceVariant`, italic), at most two lines, wrapping; the composer's room keeps those two lines free for the whole busy turn, so a long note never overflows the docked band, and a provider that sends no note shows the busy line alone. Beside the busy line the dock shows the seconds the turn has run, `m:ss` (`assistant.seconds`), ticking each second whether a note comes or not, counted from the session's `turnStartedAt` — kept with the running turn, so a dock rebuilt or reopened keeps the count — so that a silent stretch is visibly alive. A provider whose stream opens items says so as they open: `fo-openai` notes *Thinking…* as a reasoning item opens, though it may bring no summary, which the host shows in the person's language (`assistantThinking`), and each function call's alias and its number in the answer as the call opens, which the host names by its command (`create-entity · 2`), a summary's sentence replacing either where one comes, each logged `openai.note {text, source: reasoning|tool|summary}`; a chat-style stream (`fo-openrouter`, `fo-xai`) has no item-open event and notes its visible reasoning and each tool call once its name arrives, and an empty reasoning stretch there notes nothing, the seconds being the signal. Each change of what it shows is one `assistant.dock` line — `note.shown {session, call, text, ms}`, `note.cleared {session, call, text, cause, ms}` with the dock's cause, `cleared` where the seam emptied or `ended` where the turn went (the host's own cause is on `plugins.note`) — never one per rebuild. **An answer cut off at its output length** is told by the provider before it decodes the answer, from its terminal evidence (a `length` finish, or an `incomplete` response for `max_output_tokens`), and refused `cutOff` where tools were offered or the answer holds calls or no words: a cut after whole calls, inside an argument and with nothing read the same. The first provider failure ends the turn, as it does; a provider with no words shows the sentence alone. **A change not applied.** Where a write the model sent was refused by its type's record (`shapes` in the tool's answer), the dock shows one line above its error line, *Change not applied: <paths>* (`assistant.notice`); it reads *— corrected* only once a later successful call of the same write (`update-entity`, `create-entity`; a read such as `export`, or a call with no content, never) to the same target — an update's `id`, a creation's type and name —, its `content` an object, covers each refused path exactly: the same key path, a block by its id or, a new one, its anchor, a list that replaces whole by the list; for a key its record lacks, that key under `metadata` at the same place, or the block sent again without it; `metadata` alone, another block, an empty object or a path the refused content gave no way to name again (a block with neither id nor anchor) never does, while a `content` that was no object is covered by that later write's object, and any other answer leaves it as it was (`noticeAfter`, `AssistantSession.changeNotice`), and `assistant.notice {session, turn, target, paths, corrected, ms}` logs each change of it. The model's nudge is the tool answer it already receives; nothing is retried or repaired.

**The native voice session under the state's contracts** (`realtime_session.dart`, `assistant_voice_host.dart`, `native_conversation_session.dart`). What the session sends is the binding's: the WebSocket endpoint's model and the WebRTC call's model are read from `binding.model`, the configured voice from `binding.voice` (`RealtimeProtocol.endpointFor`, `configure`, `connectOpenAiWebRtc`), and the audio format stays the protocol's — WebRTC negotiates OpenAI's, Grok's PCM is what `configure` asks for — which `audioFormat` names. `NativeConversationSession` is the state's `ConversationSession` over the same session — snapshot, captions and Usage read from its notifier, its six operations given typed outcomes (a refused microphone is *not ready*, a missing key *unfunded*, a route this device lacks *unsupported*). The door's `open(binding)` answers the session the gesture readied for that binding, and a not-ready session for any other binding; the normal composition replaces this bridge. **The one microphone owner** (§7.2): Start takes a fresh `MicrophoneOwner('assistant')` from the arbiter synchronously after the key check and before any resource — the PCM player and capture, or the permission request and the native peer inside `connect`, whose order is unchanged — and a refusal ends the attempt with `mic_busy` naming the holder, before a Usage record, a device or a socket exists. The owner is released, with the host's slot, once End has awaited every release; a release that failed is logged with its error (`voice.release.failed`) and gives them back as well, but the session ends in error `voiceRelease` — the dialog says the audio could not be fully released and to close FilmOpen before another conversation, since the platform may still hold the device — `released` stays false and the adapter's End answers *not ready*; `voice.released` names the failed releases, the phase and the conversation's messages. **Finish** (`finish`, §7.2's contract): input stopped — the peer's input disabled, or the PCM capture stopped — then one `input_audio_buffer.commit` on the voice wire, `response.cancel` only while a response is in progress and once per response (the provider refuses a cancel with none; a response created during the drain is cancelled as soon as it is known, and Finish's own cancel after input shutdown does not repeat it), local playback cleared; then the admitted captions drain for at most five seconds from Finish itself, the gate admitting commit acknowledgements, caption events, truncation acknowledgements, `response.done`'s Usage and errors, and dropping new responses, spoken output and a new turn's start (a caption of speech heard before input stopped is admitted); then End, the transcript frozen with every partial caption labelled incomplete. On the WebRTC voice wire Finish's commit is the only manual one, so an empty-commit refusal (`error` with code `input_audio_buffer_commit_empty`, read by its code alone) answers it: the drain ends early once that refusal has arrived and no caption is pending — no committed item without its completion, no turn still heard or awaiting its commit — since a committed acknowledgement cannot be told from the semantic VAD's automatic ones. Grok's Finish is End with its captions labelled; a Finish before the session is ready is End. End and Close during the drain win at once: the drain settles and the one End runs. `interrupt` cancels a response in progress, once per response (a second Interrupt on it, or Finish after it, sends no second cancel); on the PCM route it clears local playback, on WebRTC the audio already in the provider's output buffer plays out. Every acknowledged commit counts as owing a response, Finish's own included, and a response begun during the drain is accounted before the gate though its output is dropped: a response never reported keeps the conversation's total unknown (§6.7) rather than priced short. Limits, recorded: a response created between `response.create` and its `response.created` is not cancelled; remote WebRTC audio already flowing is not muted during the drain or by `interrupt`; a failed caption (`…transcription.failed`) during the drain ends the session as it always does. **No cap of the app's** (§7.2's contract): a conversation runs until the person's Finish or End, or the provider or the connection ends it; `voice.start` logs `cap_ms: none`. A `sessionCap` given to the session — none in the app — finishes it through its own Finish, the same drain, the transcript kept, and `capReached` says so; a Finish already under way is the person's; nothing reconnects. The session checks its validity and the cap, and tells the dialog's clock, once a second (`voice.cap` logged when the cap is reached); only the PCM route polls its player's device position, every 100 ms, telling listeners when the phase turns to listening, and a failed read is logged (`voice.playback.failed`) and ends the session as `voicePlayback`.

**The conversation on credit** (`assistant_voice_host.dart`, `realtime_webrtc.dart`, `realtime_session.dart`). Where the chosen provider has no saved key and OpenAI's native WebRTC peer would carry the call, `readVoiceFunding` asks the funding seam (`ProviderFunding.funding('openai', 'conversation')`); its `CreditFunding` is the call's, with no key — for a chosen Grok the call runs as OpenAI's (the binding, the peer and the Usage record OpenAI's, `voice.funding` saying `reason: fallback` with `selected: xai`), and `voice.provider` names the saved Speech service, the route asked for and the one started — written once the context still holds, so that a Start refused as stale leaves no route logged as started — so that a Grok the dialog set aside where it has no route shows in the log too; the saved choice unchanged and a stored Grok key used as before; a call with no peer is never on credit, and without credit the refusal is the missing key's as before. The host mints the operation's id, a v4 UUID, on the gesture. `connectOpenAiWebRtcOnCredit` makes the offer the key's call makes and posts the same multipart `sdp` and `session`, with no redirect, to `https://<kFilmOpenDomain>/v1/portal/realtime` with the seam's `portalHeaders` and the id in `X-FilmOpen-Operation`, in place of OpenAI's URL and the key; the answer's raw SDP from a 200 or 201, bounded at 64 KiB, is the call's. No portal headers is `credentials`; any other status is `voiceStartRefused:<code>` — the string `error` of the website's error envelope (`{error, says}`; `says`, a sentence for a person, is never read as the code; the body is logged whole) where it is a safe token, `unknown` where it is not, `status-<n>` where the body names none — kept through the cleanup (unless the cleanup itself is uncertain, `voiceConnectionUncertain`), so that the dialog says *FilmOpen could not start the conversation (<code>).*; a `401` of the portal credential (`no-portal-token`, `bad-portal-token`) lets it go once (`portalRefused`) and nothing is sent again. On credit no key is read: the Usage record's route is `filmopen.ai` with no key, the captions have no record of their own, a running record keeps its units with no cost and the unknown basis, and the session's one End of an answered start (a 200 or 201, marked on the trace before the answer is installed, so that a Close racing the installation still ends it) — whatever ended it: Finish, End, Close, a disconnect, disposal — ends the operation (`ProviderFunding.end`) and reads its receipt, once each (a start the website refused or never answered sends nothing more: the website's sweep settles it), after the releases of End have run and before the terminal record, whose cost is the receipt's `chargedCents` (USD, `charged`, its operation and receipt id on the record), `pending` where the receipt read came back unsettled. The dialog's billing line for OpenAI says the saved key pays where there is one and the credit, captions included, where there is not; Grok's is the key's alone. **Its log, on both roads**: `voice.gesture` marks the Start press (the route asked for, `ms: 0`); **The voice session's tools** (`voice_tools.dart`, `realtime_session.dart`, `realtime_protocol.dart`). An OpenAI session declares the app's commands (§7.3) as its tools; a Grok session declares none and logs `voice.tools.unsupported` once, and a chosen Grok running as OpenAI on credit is an OpenAI session. The table is made once, at configure, from `CommandRegistry.all` — every command, exposed or not, since the caller is the app itself — and never changes during the session, so a call always resolves to the command it was declared for; a command registered later is not declared to it. Each command is a `function` tool named `c<index>_<name>` (its position from 1, every character outside `[a-zA-Z0-9_-]` turned into `_`, cut to 64 characters), with its description whole and its input schema without `session` and `operation`. Every registered command is declared, with no count or size of the app's — a provider that takes less refuses in its own words — and `voice.tools.declared {count, bytes}` says what was; the tools themselves, as sent, are in `voice.session.config`'s message. A `response.function_call_arguments.done` is recorded in its response's turn, never run by the event pump, which never awaits a command; a malformed one ends the session as `voiceProtocol`, and one arriving after its response's `response.done` is logged `voice.toolCall.late` and dropped. The `ToolTurnRunner` runs the calls in arrival order, one at a time, on its own future: an unknown alias or arguments that are not a JSON object answer `{"error":"bad-call"}` with no dispatch; an effectful command gets `session` and `operation` = `voice-` and a digest of the provider's call id, so a repeated call is answered from the ledger and runs once, while a read-only command gets its arguments as sent; each runs through `CommandRegistry.call` with caller `voice`, a 30-second deadline — which bounds admission, the registry refusing a dispatch or an effect after it, not the wait for a command already running, since every command answers within its own bound — and the session's guard. **The guard** holds while the session is not closed and not finishing, the call's response is not interrupted, and no interruption — speech starting, or an explicit interrupt, which blocks its response as speech does — has come since its turn's first call arrived, so a call outliving its response's `response.done` is stopped too. It is read before a dispatch, by the registry's `admit` inside an effectful command, and again before the output: a call stopped after its effect was admitted sends nothing, and its answer stays in the ledger, never replayed to repair the lost output. The output is a `function_call_output` item carrying the result's `structured` as JSON, else its text, whole, with no bound of the app's. **The seal**: a response's `response.done`, once its Usage is counted, seals its turn — unless its status is `failed` or `incomplete`, which is logged `voice.response.failed` with the response's id, its status and its `status_details` whole and ends the session as `voiceProvider` with that Usage kept and nothing sealed, so no continuation follows; once every call of a sealed turn has answered or been dropped, one `response.create` follows, owed in the Usage accounting as every response is, and only where an output was sent and the guard still holds. The phase follows the runner's remaining work: while any call is queued or running it stays *thinking* rather than inviting the person to speak, and a turn that ends with no response hands the turn back (*listening*) only when the runner holds nothing more and no response is under way. Each call logs `voice.toolCall {call, callId, responseId, asked, arguments, alias, source, name, effectful}` (`callId` and `responseId` the provider's, which name the operation's replay and the turn's interruption), the registry's own lines, then `voice.toolCall.output {call, outcome, bytes, sent, reason?, output, callMs}` (`output` what the model is sent, whole); a turn logs `voice.turn {response, calls}` at its seal and `voice.turn.done {response, responseCreated, idle, reason?, turnMs}`; a call arriving during Finish's drain, or to a session that declared no tools, logs `voice.toolCall.dropped {reason}`; an explicit interrupt logs `voice.interrupt`; an unexpected throw in the runner logs `voice.toolCall.failed` with its call, type and the error's message in `error`, and the next call still runs. One function, `runToolCall`, runs a call of either road — the bad call, the liveness read before the dispatch, `session` and `operation`, the registry call and its output, whole — and each road logs it under its own events. Not guarded, by design: a command running when the turn is interrupted completes, and a lost output is not retried. A `navigate` moves the screen, after which a field-bound conversation ends as `stale`, as before.

The source binding accepts the original material content or the captured draft's own normal autosave. For a voice conversation, another source change invalidates the session even while the form has unsaved edits; save timestamps and normal retired-key cleanup do not invalidate its own save. The transport reports a host-only admission flag: only an explicitly unadmitted request refunds the local turn counter. A timeout or unknown result retains its turn, and a still-settling backend refuses a new call without consuming another turn.

A plugin-returned diagnostic code is kept only as a bounded token (a lowercase letter, then at most 39 letters or underscores) — a code ending in `/finalizerTargetMismatch` kept as that reason — anything else becoming `failed`, so no sentence of the conversation, nothing beyond one such word, can become a persisted Usage error code.

An OAuth slot refreshes an expired access token before the HTTP door sends its request. The door adds its Bearer header after logging the request, and names its usage by the slot rather than token characters. A refresh response with a 4xx status other than 429 clears the credential and key record and requires sign-in again. A 429, a 5xx or another unsuccessful response fails the call and keeps both records. No failed refresh selects credit or retries the request.

A text route is chosen from the declared slots and stored metadata: a configured local server remains local; otherwise a signed-in slot precedes a configured program, then stored copied keys in manifest order, then FilmOpen credit. The binding pins that route and passes it to `complete` as `route` with `funding` and its `slot`, `program` or `key`. A refusal ends that route without another attempt on a different one. An OAuth block with `sends_output_cap: false` gives the assistant policy no output cap. Settings reads the host’s chosen route from the plug-in summary, and the dock reads its offered route. Both show a full readiness sentence; an OAuth route uses its block’s label, falling back to the manifest slot label. Key-slot views carry that plan label, manifest authentication and the existing record’s account/expiry without opening the credential store.

A signed-in HTTP slot opens token-only plan Usage with the OAuth block’s label. Text process calls open plan Usage on the ledger they run on, including interrupt’s fresh ledger; only their answer’s account label replaces the record’s label. Local assistant HTTP opens local Usage after policy admission, one record chain per model call. Both routes retain tokens without pricing or credit operations and log the opening decision and terminal record.
